# PRD 작성 + 기술 결정(ADR) — prd.md

> 단계 2 프로세스 가이드. (단계 1: `interview.md`, 단계 3: `issues.md`)
> 이 문서는 **절차 정의**이며, 실제 산출물은 `docs/result/prd/*.md`에 따로 생성한다.
> 아래 "입력 / 산출물"의 `docs/features/{name}/` 경로는 강의 원문 표기다.
> 우리 프로젝트의 실제 경로는 `issues.md`의 "우리 프로젝트의 실제 경로"를 참고한다.

## 목적

요구사항·디자인·기술 결정·범위를 하나의 문서로 통합해 "이 기능에 대해 궁금하면 여기만 보면 된다"는 단일 기준점을 만든다.

## 입력

- `docs/features/{name}/spec-fixed.md`
- `docs/features/{name}/design.md` (존재하면 참조)
- 코드베이스 (기존 패턴 참조)

## 핵심 활동

### 2-1. PRD 뼈대 생성 (기술 결정은 TODO로 비워둠)

PRD 구조:

- **개요** — 기능의 목적과 범위
- **사용자 스토리** — 사용자 관점의 흐름
- **기술 결정** — 어떤 구조 위에 올릴 것인가 (여기서 ADR 작성)
- **Out of Scope** — 이번에 하지 않을 것
- **용어 정의** — spec-fixed.md의 Ubiquitous Language 동기화

### 2-2. 아키텍처 3안 제안 & 비교

AI에게 최소 3가지 안을 제안받고, **아래 7가지 고정 기준**으로 비교한다:

| #   | 기준                 | 설명                                           |
| --- | -------------------- | ---------------------------------------------- |
| 1   | 데이터 구조          | 어떤 형태로 데이터를 저장/표현하는가           |
| 2   | API 레이어 변경지점  | 기존 API에서 무엇이 바뀌는가                   |
| 3   | 상태관리 변경지점    | Context/Store에서 무엇이 추가되는가            |
| 4   | 핵심 동작            | 이 기능의 가장 중요한 동작이 어떻게 구현되는가 |
| 5   | 컴포넌트 구조        | 어떤 컴포넌트가 추가/수정되는가                |
| 6   | 기존 패턴과의 일관성 | 코드베이스의 기존 관습과 얼마나 맞는가         |
| 7   | 테스트 용이성        | 단위 테스트, E2E 테스트 작성이 쉬운가          |

비교 결과를 표로 정리한 뒤 **사용자가 선택**한다.

```
[GATE] 사용자가 3안 중 하나를 선택할 때까지 대기
```

### 2-3. 선택한 안을 ADR 4요소로 PRD "기술 결정" 섹션에 작성

해당 기술을 왜 하기로 했는지 기록해야 AI도 어긋나지 않는다.

```markdown
### 기술 결정 제목

**Context** — 이 결정이 필요한 맥락. 무엇을 풀고 있는가.

**Decision** — 무엇을 선택했는가.

**Alternatives** — 거부한 안과 **각각의 거부 이유**. (이유 없는 거부 금지)

**Consequences** — 트레이드오프. **장점뿐 아니라 단점도 반드시 명시**한다.
```

### 2-4. Out of Scope 작성

"하지 않을 것"을 구체적으로 나열한다. AI에게 특히 중요한 이유:

- 명시하지 않으면 AI가 맥락을 확장 해석해 범위 초과 구현을 한다
- 예: "태그 색상 커스터마이징", "태그 자동 추천", "태그 기반 검색" 등

```
[GATE] 사용자가 Out of Scope을 읽고 확정할 때까지 대기
```

## 이 프로젝트에서의 적용 메모

> 아래는 원문이 아니라, 우리 프로젝트 상황에 맞춰 덧붙인 실행 메모다.

### spec-fixed.md와의 관계

| 구분            | 답하는 질문                             | 예시 (공고 버전 관리)                                                                                    |
| --------------- | --------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `spec-fixed.md` | **무엇을** 만드는가 (제품 규칙)         | "필수항목 6개가 바뀌면 version +1, 신청자는 `PENDING_REACCEPT`로 전환"                                   |
| `prd.md`        | **어떤 구조**로, **왜** 그렇게 골랐는가 | "버전 이력을 스냅샷 테이블에 저장. diff JSON·이벤트 소싱은 각각 이런 이유로 기각. 단점은 저장 용량 증가" |

핵심 가치는 **Alternatives(거부한 안과 이유)** 다. 근거가 없으면 사람도 AI도 이미 기각한 안을 다시 검토하거나 임의로 바꾼다.

### 현재 상태 (2026-08-17)

`docs/result/spec-fixed.md`가 프로젝트 전체를 한 장에 담고 있어 PRD 항목 일부가 이미 채워져 있다.

| PRD 항목          | 상태                                                    |
| ----------------- | ------------------------------------------------------- |
| 용어 정의         | 완료 — 동기화만                                         |
| 기술 결정         | 부분 — 결정은 있으나 ADR 형식(특히 Alternatives)이 없음 |
| Out of Scope      | 부분 — §6.4.3, §12.1에 흩어져 있음                      |
| 개요              | 부분                                                    |
| 사용자 스토리     | **없음**                                                |
| 아키텍처 3안 비교 | **없음**                                                |

따라서 2단계는 백지에서 쓰는 것이 아니라 **3안 비교와 ADR을 얹는 작업**이다.
