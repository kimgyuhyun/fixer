## 1. 개요

### 목적

가입자가 화면에서 직접 서명하고, 그 서명이 병합된 PDF 동의서를 위조 불가능한 형태로 보관한다.

### 왜 별도 도메인인가

가입 플로우의 한 단계처럼 보이지만, 다루는 것이 **파일·해시·법적 증거**로 회원 도메인과 성격이 완전히 다르다. 저장소·보관 정책·CSS 예외까지 따로 걸린다.

### 범위

- 서명 캔버스 (터치·마우스)
- `pdf-lib`로 서명 PNG를 템플릿 PDF에 병합
- 병합 PDF 저장 + SHA-256 해시 기록
- 동의서 조회 / 관리자 열람
- 동의서 템플릿 버전 관리

### 핵심 제약

**원본 서명 PNG는 병합 직후 폐기한다.** 남겨두면 재사용·위조 위험이 생긴다. (spec-fixed §2.3)

---

## 2. 사용자 스토리

- **가입자로서** 마우스나 손가락으로 직접 서명하고, 마음에 안 들면 지우고 다시 그리고 싶다.
- **가입자로서** 서명한 동의서가 실제로 어떻게 생겼는지 확인한 뒤 제출하고 싶다. 무엇에 동의하는지 모르고 누르고 싶지 않다.
- **가입자로서** 나중에 내가 동의한 문서를 다시 볼 수 있기를 원한다.
- **운영자로서** 분쟁이 생겼을 때 "이 사람이 이 시각에 이 내용에 동의했다"를 증명할 수 있어야 한다.
- **운영자로서** 동의서 문구를 개정해도 기존 동의서가 그대로 보존되기를 원한다. 과거 동의를 새 문구로 소급하면 증거 능력이 사라진다.

### ADR-AGR-1 · 좌표 변환을 아예 하지 않는다

**Context**
서명 캔버스는 화면 좌표(좌상단 원점, px)이고 PDF는 문서 좌표(좌하단 원점, pt)다. 게다가 `devicePixelRatio`와 화면 폭이 기기마다 다르다. 어디서 정규화하느냐에 따라 "서명이 엉뚱한 위치에 박히는" 버그가 어디서 나는지가 달라진다.

**Decision**
**좌표를 주고받지 않는다.**

- **템플릿 PDF가 서명 자리를 들고 있다.** 서명이 들어갈 사각형(x, y, w, h — PDF 좌표)을 템플릿 메타데이터에 기록한다
- **클라이언트는 고정 px 캔버스에서 서명 PNG만 만들어 보낸다.** 좌표는 계산하지 않는다
- **서버가 그 PNG를 사각형에 맞춰 넣는다.** 종횡비를 유지하며 사각형 안에 맞춘다

`devicePixelRatio`는 §12대로 **캔버스를 선명하게 그리는 데만** 쓴다. 서버로 보내는 PNG는 논리 크기로 정규화한다 — dPR이 2인 기기와 1인 기기가 같은 크기의 PNG를 보낸다.

**변환 지점이 서버 한 곳뿐이므로 어긋날 자리가 없다.** 문서와 좌표가 같은 파일(템플릿)에 있어 함께 움직인다.

**Alternatives**

- **클라이언트가 좌표를 계산해 보낸다** — 기각. 조작하면 서명이 엉뚱한 조항 위에 박히고, 서버가 검증하려면 같은 계산을 다시 해야 해서 클라이언트 계산이 무의미하다. `devicePixelRatio`와 화면 크기가 기기마다 달라 "타당한 좌표인가"를 판정할 기준도 없다.
- **캔버스를 문서 위에 겹쳐 상대 위치를 쓴다** — 기각. 화면 폭에 따라 문서 렌더 크기가 달라져 같은 서명이 기기마다 다른 위치에 박힌다. §12가 "rem/%로는 서명이 PDF에서 어긋난 위치에 박힘"이라고 이미 경고한 경로다.

**Consequences**

- 서명 위치를 바꾸려면 템플릿 메타데이터만 고친다. 코드를 안 건드린다
- 서명 칸이 여러 개인 템플릿도 사각형을 여러 개 두면 그대로 된다
- **캔버스 종횡비와 사각형 종횡비가 다르면 서명이 사각형 안에서 남는 공간이 생긴다.** 템플릿의 사각형을 캔버스와 비슷한 비율로 잡아야 보기 좋다
- 클라이언트가 보내는 PNG 크기가 커지면 업로드가 무거워진다. 캔버스 논리 크기에 상한을 둔다

**이 결정을 다시 여는 조건** — 사용자가 서명 위치를 직접 끌어서 정하는 요구가 생기면. 그때는 좌표가 입력값이 되므로 검증 규칙을 새로 설계해야 한다.

### ADR-AGR-2 · PDF 병합은 서버에서 한다

**Context**
`pdf-lib`는 브라우저와 Node 양쪽에서 돈다. 어디서 병합하느냐에 따라 **신뢰 경계**와 서명 PNG의 이동 경로가 갈린다. 동의서는 분쟁 시 증거로 쓰이므로 "누가 만든 문서인가"가 중요하다.

**Decision**
**서버(Nest)에서 병합한다.** 클라이언트는 서명 PNG만 올린다.

```
브라우저:  캔버스 → 서명 PNG  →  업로드
서버:      템플릿 PDF + PNG  →  pdf-lib 병합  →  최종 PDF 저장  →  PNG 폐기
```

§2.3의 **"병합된 최종 PDF만 저장한다. 원본 서명 PNG는 병합 직후 폐기"** 를 지킬 수 있는 유일한 위치다.

**Alternatives**

- **클라이언트에서 병합** — 기각. PNG를 폐기했는지 서버가 확인할 방법이 없다. 완성된 PDF를 받아 저장하면 그 내용이 우리 템플릿인지 검증할 수 없다.
- **하이브리드(클라이언트 미리보기 + 서버 최종)** — 기각. 만드는 코드가 두 벌이 되고, 둘이 어긋나면 "화면에서 본 것과 저장된 것이 다르다"가 된다. 동의서에서 그건 분쟁 소재다. 미리보기가 필요하면 **서버가 만든 PDF를 그대로 보여준다.**

**Consequences**

- 서버가 문서를 만드는 유일한 주체다. 저장된 PDF는 항상 우리 템플릿에서 나온 것이다
- 병합이 서버 CPU를 쓴다. 동의서는 가입 흐름에서 1회뿐이라 부담이 크지 않다
- **업로드된 PNG를 검증해야 한다.** 크기·형식·픽셀 수 상한을 두지 않으면 거대한 이미지로 서버를 밀 수 있다
- 서명 직후 병합이 실패하면 사용자는 다시 서명해야 한다. PNG를 폐기하는 정책상 재시도를 위해 들고 있을 수 없다

**이 결정을 다시 여는 조건** — 없다고 본다. 클라이언트 병합은 신뢰 경계를 넘는 문제라 성능 사유로 되돌릴 성질이 아니다.

### ADR-AGR-3 · 도메인이 논리 키를 정하고 저장소가 매핑한다

**Context**
MVP는 로컬 볼륨, 향후 S3/MinIO다(§4). 지금 인터페이스를 잘못 잡으면 옮길 때 도메인 코드를 고치게 된다. §9는 파기 시 **"동의서 PDF 파일 → 삭제 후 해시만 보존"** 을 요구하므로 삭제와 해시가 인터페이스에 있어야 한다.

**Decision**
**도메인이 논리 키를 정하고, 저장소가 실제 위치로 매핑한다.**

```ts
export interface FileStore {
  /** 저장하고 내용 해시를 돌려준다. 해시는 파기 후에도 남길 값이다 (§9) */
  put(key: string, bytes: Buffer): Promise<{ sha256: string; bytes: number }>;
  get(key: string): Promise<Buffer>;
  /** 없는 키를 지워도 성공이다. 파기 배치가 멱등해야 한다 */
  delete(key: string): Promise<void>;
}
```

- 논리 키는 도메인이 만든다: `agreements/{agreementId}.pdf`
- 로컬 구현은 `{FILE_STORAGE_ROOT}/agreements/{id}.pdf`로, S3 구현은 같은 문자열을 객체 키로 쓴다
- **`put`이 해시를 돌려준다.** §9의 "삭제 후 해시만 보존"을 하려면 저장 시점에 계산해 둬야 한다. 삭제 후에는 계산할 원본이 없다

`FILE_STORAGE_ROOT`는 **배포 디렉터리 밖**을 가리킨다. 안에 두면 재배포 때 업로드 파일이 통째로 사라진다.

**Alternatives**

- **저장소가 키를 만들어 돌려준다** (`put(bytes) → key`) — 기각. S3로 옮길 때 키 체계가 바뀌면 이미 DB에 박힌 키를 마이그레이션해야 한다. 도메인이 키를 정하면 매핑만 바꾸면 된다.
- **Prisma에 바이너리 컬럼으로 저장** — 기각. 백업 크기가 폭증하고, §9의 "삭제 후 해시만 보존"을 하려면 행을 UPDATE해야 해서 불변 기록의 결과 어긋난다.

**Consequences**

- 옮길 때 `FileStore` 구현체 하나만 새로 쓴다. 도메인 코드는 그대로다
- 논리 키가 곧 사람이 읽을 수 있는 경로라 운영 중 파일을 찾기 쉽다
- **로컬 볼륨은 서버가 여러 대가 되면 공유 스토리지가 필요하다.** 단일 서버 전제이며, 늘리는 시점이 S3로 옮길 시점이다
- `delete`를 멱등하게 만들었으므로 파기 배치를 두 번 돌려도 안전하다

**이 결정을 다시 여는 조건** — 서버가 두 대 이상이 되면 그 시점에 S3/MinIO 구현체를 붙인다. 인터페이스는 그대로 쓴다.

### ADR-AGR-4 · 템플릿은 파일, 메타데이터는 DB

**Context**
§2.3이 **"템플릿이 개정되면 `templateVersion`을 올리고 기존 동의서는 그대로 보존"** 이라고 정했다. 남은 것은 템플릿 PDF 자체를 어디에 둘지, 그리고 개정과 기존 동의서를 어떻게 잇는지다.

**Decision**
**템플릿 PDF는 저장소의 파일로, 메타데이터는 DB에 둔다.**

```
apps/api/assets/agreement-templates/v1.pdf   ← git으로 이력 관리
apps/api/assets/agreement-templates/v2.pdf

AgreementTemplate  (DB)
  version         Int      @unique
  fileKey         String
  sha256          String              // 파일이 바뀌었는지 확인용
  signatureBox    Json                // ADR-AGR-1의 사각형
  isActive        Boolean             // 새 서명에 쓰는 버전은 하나
  activatedAt     DateTime

Agreement          (DB)
  templateVersion  Int                // 서명 시점의 버전. 절대 안 바뀐다
  pdfKey           String             // 병합된 최종 PDF
  pdfSha256        String             // 파기 후에도 남길 값 (§9)
```

**개정은 새 버전 추가일 뿐이다.** 기존 `Agreement` 행은 손대지 않는다 — 이미 병합된 PDF를 들고 있으므로 옛 템플릿이 없어도 그 문서는 온전하다.

**재동의를 받을지는 이 결정의 범위 밖이다.** 약관이 실제로 바뀔 때 법적으로 판단할 일이고, 구조가 그 판단을 막지 않는다. `templateVersion`으로 "누가 어느 버전에 서명했는지"를 뽑을 수 있으므로 재동의 대상을 골라내는 것은 가능하다.

**Alternatives**

- **템플릿 PDF를 DB에 저장** — 기각. 템플릿은 개발자가 검토하고 교체하는 것이라 git 이력이 더 적합하다. DB에 두면 누가 언제 왜 바꿨는지가 코드 리뷰를 안 거친다.
- **템플릿만 파일로 두고 DB 기록을 안 남긴다** — 기각. 가장 단순하지만 어떤 동의서가 어떤 템플릿에서 나왔는지 추적이 끊긴다. §2.3이 `templateVersion`을 요구한 이유가 그 추적이다.

**Consequences**

- 템플릿 교체가 코드 리뷰를 거친다. 약관 문구 변경이 조용히 배포되지 않는다
- **옛 템플릿 파일을 영구히 보관하지 않아도 된다.** 서명 시점에 병합된 PDF가 이미 있으므로 템플릿은 라벨일 뿐이다
- 활성 버전이 하나라는 규칙을 코드가 지켜야 한다. `isActive`가 둘이면 어느 것으로 서명되는지 불확실해진다
- **서명 자리(`signatureBox`)가 템플릿에 묶여 있다.** 템플릿을 바꾸면 사각형도 함께 바꿔야 하고, 안 바꾸면 서명이 엉뚱한 곳에 박힌다. 새 버전을 활성화하기 전에 실제로 한 번 서명해 확인하는 절차가 필요하다

**이 결정을 다시 여는 조건** — 관리자가 화면에서 템플릿을 업로드하는 요구가 생기면. 그때는 DB 저장으로 옮기고 검토 절차를 코드 밖에 만들어야 한다.

## 4. Out of Scope

| 항목                                | 이유                                                             |
| ----------------------------------- | ---------------------------------------------------------------- |
| 공인전자서명 / 인증서 기반 서명     | 법적 효력 등급이 올라가지만 인증기관 계약 필요. MVP 범위 밖      |
| 타임스탬프 기관(TSA) 연동           | 위와 동일                                                        |
| 서명 원본 PNG 보관                  | **의도적으로 폐기** (재사용·위조 위험). 병합 PDF + 해시만 남긴다 |
| 동의서 내용의 사용자별 커스터마이징 | 템플릿은 전원 동일                                               |
| PDF 내 텍스트 입력·체크박스 폼      | 서명 한 곳만                                                     |
| 동의서 이메일 자동 발송             | 사이트에서 조회만                                                |
| 다중 서명 (양자 서명)               | 가입 동의서는 단독 서명                                          |
| 서명 이미지 벡터화 / 필적 검증      | 과함                                                             |
| PDF 전자서명(디지털 서명) 필드 삽입 | 해시 기록으로 무결성 확인을 대체                                 |

## 5. 용어 정의

| 용어        | 코드 식별자       | 정의                                    |
| ----------- | ----------------- | --------------------------------------- |
| 동의서      | `Agreement`       | 서명이 병합된 PDF 및 그 메타데이터      |
| 템플릿 버전 | `templateVersion` | 동의서 문구 개정 차수                   |
| 무결성 해시 | `sha256`          | 병합 PDF의 SHA-256. 위조 여부 판정 근거 |

## 6. CSS 예외 (확정)

`css-standards` 규약에서 **예외를 허용하는 두 화면 중 두 곳이 모두 이 도메인**이다. (spec-fixed §10)

| 화면        | 예외                                         | 이유                                                           |
| ----------- | -------------------------------------------- | -------------------------------------------------------------- |
| 서명 캔버스 | 고정 px 캔버스 + `devicePixelRatio` 스케일링 | rem/%로는 터치 좌표가 어긋나 PDF에 서명이 틀어진 위치로 박힌다 |
| PDF 뷰어    | 원본 종횡비 고정 컨테이너                    | 문서 비율 왜곡 방지                                            |
