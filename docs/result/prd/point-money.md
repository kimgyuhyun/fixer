# PRD — 포인트 · 결제 · 환전 (point-money)

> 담당: **공동 (원장 코어)** / **B 김규현** (결제·환불·`HOLD`·`RELEASE`·`PAYOUT`) / **A 최동훈** (환전)
> 상위 사양: `docs/result/spec-fixed.md` §6, §11.5
> 상태: **2-1 뼈대 완료 / 기술 결정 TODO**

---

## 1. 개요

### 목적

실제 돈이 포인트로 들어와서(충전), 공고에 묶이고(잠금), 일한 사람에게 넘어가고(지급), 다시 현금으로 나가는(환전) 전 과정을 **한 건도 어긋나지 않게** 기록한다.

### 왜 가장 위험한가

버그가 나면 사용자가 돈을 잃는다. 다른 도메인은 화면을 다시 그리면 되지만 여기는 원장이 틀어지면 수동으로 맞춰야 하고, 그 과정에서 신뢰가 무너진다.

### 왜 공유 커널인가

원장 유형 7개 중 5개를 B가, 2개를 A가 호출한다. 어느 한쪽 소유로 두면 상대는 남의 코드를 통해서만 돈을 만지게 된다. **돈은 버스팩터가 1이면 안 된다.** (roadmap §1.1)

### 범위

- `PointTransaction` 원장 (7개 유형)
- 포트원 결제창·웹훅 기반 충전, 환불
- `HOLD` / `RELEASE` / `PAYOUT` 도메인 연결
- 계좌 등록·검증, 환전 요청, 관리자 승인 화면
- 모드 전환 인터페이스 (`AccountVerifier`, `ExchangeProvider`)

## 2. 사용자 스토리

### 충전

- **구인자로서** 공고를 올리려면 먼저 포인트를 충전해야 한다는 걸 이해하고, 필요한 금액을 바로 채우고 싶다.
- **구인자로서** 결제했는데 포인트가 안 들어오는 일이 없기를 원한다. 네트워크가 끊겨도, 새로고침을 해도, 결제는 한 번만 반영되어야 한다.

### 잠금 · 지급

- **구인자로서** 공고를 올리면 그만큼 포인트가 묶이는 걸 알고 싶다. 잔액이 부족하면 등록 전에 알려줘야 한다.
- **구인자로서** 6명 모집에 3명만 찼으면 **나머지 3명분이 자동으로 돌아오기를** 원한다. 따로 신청하고 싶지 않다.
- **구직자로서** 일을 마치면 약속한 포인트가 확실히 들어오기를 원한다.

### 환전

- **구직자로서** 쌓인 포인트를 현금으로 받고 싶다.
- **구직자로서** 내 계좌가 제대로 등록됐는지 확인받고 싶다. 엉뚱한 계좌로 갈까 봐 불안하다.
- **관리자로서** 환전 요청자 목록을 보고 승인한 뒤, 직접 이체하고 완료를 찍고 싶다.
- **운영자로서** 나중에 실송금 API를 붙일 때 **화면과 도메인 코드를 다시 안 짜기를** 원한다.

### ADR-PAY-7 · 환불은 오래된 결제 건부터 소진한다

**Context**
구인자는 미리 충전하고 그 잔액으로 공고를 올린다(§6.3). 그래서 잔액과 결제 건이 1:1이 아니다. 문제는 **환불이 잔액을 줄이는 일이 아니라 특정 카드 결제 건을 취소하는 일**이라는 데 있다 — 어느 `paymentId`에 얼마를 취소할지 정해야 하고, 카드로 들어온 돈은 그 카드로만 돌아간다.

여기에 둘이 얽힌다. **카드 취소에는 기한이 있고**(원거래로부터 일정 기간, 계약에 따라 다름), **근로자 지급에는 기한이 없다**(우리가 이미 들고 있는 돈에서 나가는 계좌 이체라 카드와 무관하다).

**Decision**
**환불은 남은 결제 건 중 `createdAt`이 가장 오래된 것부터 소진한다(FIFO).** 잠금(`HOLD`)과 지급(`PAYOUT`)도 같은 순서로 소진한다.

| 항목        | 결정                                                                                          |
| ----------- | --------------------------------------------------------------------------------------------- |
| 부분환불    | 허용. 마지막 lot에서 끝수를 맞추는 데 필요하다                                                |
| 소진 순서   | 환불·잠금·지급 **모두 FIFO**                                                                  |
| lot 잔여    | 컬럼으로 두지 않고 **원장에서 계산**한다. 원장 행이 `sourcePaymentId`를 참조한다              |
| 취소 기한   | `Payment.refundableUntil`을 지금 만들고 값은 비운다. 기한이 지난 lot은 FIFO 순서에서 건너뛴다 |
| 근로자 지급 | **기한 없음.** `refundableUntil`은 환불 경로에서만 본다                                       |

**왜 FIFO인가 — 취향이 아니다.** 카드 취소 기한이 오래된 건부터 먼저 만료된다. 오래된 것을 먼저 쓰면 취소 불가로 굳는 금액이 최소가 된다. 최신 것부터 쓰면 오래된 건이 잔액에 남아 있다가 기한이 지나 **"잔액은 있는데 환불이 안 되는" 금액**이 된다.

**Alternatives**

- **부분환불 금지 (`PAY` 또는 `REFUND` 둘 중 하나)** — 기각. lot 추적이 아예 필요 없어 가장 단순하지만 "5만원 충전 후 2만원만 환불"이 불가능하다. 전액 취소 후 재충전하면 카드 취소에 며칠 걸리는 동안 잔액이 0이라 공고를 못 올린다. 1,000원 단위 여러 건으로 쪼개는 방법은 카드 수수료가 건당 붙어 성립하지 않는다.
- **소비는 lot을 안 건드리고 환불만 lot에서 뽑는다** — 기각. lot 잔여 합계와 실제 잔액이 영구히 어긋난다. `min()`으로 막으면 사고는 안 나지만 **"얼마 환불 가능?"에 답이 두 개 나온다.** §6.1의 "진실의 원천은 항상 원장"과 정면으로 어긋난다.
- **충전을 없애고 공고 등록 시 그 금액만 결제** — 기각. 이 ADR이 통째로 필요 없어지는 안이다(결제 건 = 공고 1:1이므로 FIFO·lot·`HOLD`가 다 사라진다). 사양이 충전으로 정해져 있고(§6.3, 이슈 #28), 공고를 반복해 올리는 구인자가 매번 카드를 꺼내는 마찰이 크다고 판단했다. **다만 되돌리기 가장 어려운 기각이므로 김규현이 볼 첫 지점이다.**

**Consequences**

- 환불이 카드 취소 기한과 맞물려 돌아간다. 취소 불가로 굳는 금액이 최소가 된다
- 숫자가 한 벌이다. lot 잔여도 잔액도 원장에서 나온다
- **환불 한 번에 카드 취소가 여러 번 나갈 수 있다.** lot 두 개에 걸치면 PG 호출이 두 번이고, 중간에 하나가 실패하면 부분만 취소된 상태가 된다. **환불을 여러 취소의 묶음으로 다루고 각 취소의 성공·실패를 개별 기록해야 한다** — 카드사 호출을 되돌릴 방법이 없으므로 원자적으로 만들 수 없다
- lot 잔여를 원장에서 계산하므로 조회가 무겁다. `sourcePaymentId` 인덱스가 필요하고, 느려지면 캐시를 `ADR-PAY-1`에서 함께 다룬다
- **기한이 지난 lot이 잔액에 남는다.** 화면에서 그 사실을 알려야 하고, 그 금액의 정리 방법은 실결제 전환 시 정한다

**이 결정을 다시 여는 조건**

- **김규현이 이견을 내면** — PRD가 공동 결정으로 정해 둔 도메인이다
- 실결제 후 취소 기한이 짧아 "환불 불가 잔액"이 자주 생기면 → 충전 상한을 두거나 공고별 결제를 재검토
- 구인자 한 명의 결제 건이 수백 건이 되어 환불 화면이 느려지면 → lot 스냅샷 도입

### ADR-PAY-1 · 잔액은 원장에서 계산하고, 캐시는 틀리면 버린다

**Context**
§6.1이 "진실의 원천은 항상 원장, 조회 성능은 `User.cachedBalance`로 보완"까지 정했다. 남은 것은 **캐시와 원장이 어긋났을 때 어떻게 복구하느냐**다.

**Decision**
**캐시가 원장과 다르면 캐시를 버리고 원장으로 다시 채운다.** 원장을 캐시에 맞추는 일은 절대 하지 않는다.

- 원장 쓰기와 같은 트랜잭션에서 `cachedBalance`를 갱신한다. 트랜잭션이 실패하면 둘 다 안 바뀐다
- **금전 판정(잔액 검증, 환불 가능액)은 캐시를 보지 않고 원장을 합산한다.** 캐시는 화면 표시용이다
- 하루 1회 배치가 전 회원의 원장 합계와 캐시를 대조해 다른 행을 찾아 캐시를 덮어쓰고, **어긋난 사실을 로그에 남긴다.** 배치는 §8.2대로 advisory lock을 건다
- 어긋남이 발견되면 그건 버그 신호다. 조용히 고치고 넘어가지 않고 기록한다

**Alternatives**

- **캐시를 진실로 쓰고 원장은 이력용** — 기각. 캐시가 틀리면 잔액이 틀리고, 원장과 대조해도 어느 쪽이 맞는지 판단 근거가 없다. §6.1의 "잔액 컬럼을 직접 UPDATE 하지 않는다"와 정면으로 어긋난다.
- **스냅샷 + 증분** (월말 잔액을 박아두고 그 뒤 증분만 합산) — 기각. 원장이 수백만 행이 되면 필요하지만 지금은 이르다. 스냅샷이 틀리면 그 시점 이후 전부가 틀리고, 스냅샷을 다시 만드는 절차가 또 필요하다. **행 수가 문제가 될 때 도입한다.**
- **캐시를 아예 두지 않는다** — 기각하지 않았지만 채택도 안 했다. 매번 합산이 가장 안전하나 §6.1이 이미 캐시를 두기로 정했다. 캐시를 금전 판정에서 배제했으므로 안전성은 같다.

**Consequences**

- 금전 판정이 항상 원장을 합산하므로 캐시가 틀려도 돈이 틀리지 않는다
- 캐시가 틀리는 것은 **버그의 증상**으로 다뤄진다. 자동 복구되지만 로그가 남아 원인을 찾을 수 있다
- **판정마다 원장을 합산하므로 회원당 원장 행이 많아지면 느려진다.** `PointTransaction(userId, createdAt)` 인덱스가 필수다
- 대조 배치가 전 회원을 훑으므로 회원이 늘면 시간이 늘어난다. 마지막 대조 시각을 기록해 증분만 보는 방식으로 나중에 줄일 수 있다

**다시 여는 조건** — 원장 합산이 응답 시간을 해치면 스냅샷 + 증분을 도입한다.

### ADR-PAY-2 · 조건부 UPDATE로 막는다. 별도 잠금을 쓰지 않는다

**Context**
같은 회원에게 충전과 잠금이 동시에 들어오면 잔액 검증이 깨질 수 있다. 읽고 나서 쓰는 사이에 틈이 있기 때문이다.

**Decision**
**§4.4가 정원 초과에 쓴 것과 같은 패턴을 쓴다 — 조건부 UPDATE 한 문장.**

```sql
UPDATE "User" SET "cachedBalance" = "cachedBalance" - :amount
WHERE id = :userId AND "cachedBalance" >= :amount
```

- 영향받은 행이 0이면 잔액 부족이다. 거절한다
- 이 문장 자체가 원자적이라 행 잠금도 직렬화 격리도 필요 없다
- 같은 트랜잭션에서 원장 행을 `INSERT`한다. **둘이 함께 성공하거나 함께 실패한다**
- `cachedBalance`를 조건에 쓰는 것은 §6.1과 어긋나지 않는다 — **판정의 근거는 원장 합계이고, 이 UPDATE는 그 판정을 원자적으로 만드는 장치**다. 캐시가 틀렸다면 `ADR-PAY-1`의 배치가 잡고, 그 사이 잘못 거절될 수는 있어도 **없는 돈이 나가지는 않는다**

**Alternatives**

- **`SELECT ... FOR UPDATE` 행 잠금** — 기각. 동작하지만 트랜잭션이 길어지면 다른 요청이 대기한다. 조건부 UPDATE로 같은 결과를 얻으면서 잠금 시간이 문장 하나로 끝난다.
- **`SERIALIZABLE` 격리** — 기각. 직렬화 실패로 재시도가 잦아지고, 재시도 로직이 모든 원장 쓰기 경로에 붙는다. 얻는 안전성은 조건부 UPDATE와 같다.
- **애플리케이션 레벨 뮤텍스** — 기각. 서버가 두 대가 되면 즉시 깨진다.

**Consequences**

- 저장소가 여러 대가 되어도 DB 한 곳에서 판정하므로 그대로 동작한다
- §4.4와 같은 패턴이라 코드를 읽는 사람이 두 가지를 배우지 않는다
- **잔액 부족을 "행 0개"로 판정하므로 왜 거절됐는지가 응답에 안 담긴다.** 필요하면 거절 후 잔액을 한 번 더 조회해 안내 문구를 만든다
- 캐시가 실제보다 낮으면 **있는 돈인데 거절**될 수 있다. 사고는 아니지만 사용자에게는 버그로 보이므로 `ADR-PAY-1`의 대조 배치가 중요해진다

**다시 여는 조건** — 한 회원의 원장 쓰기가 초당 수십 건이 되면(현실적으로 없다) 경합이 문제가 될 수 있다.

### ADR-PAY-3 · 유니크 인덱스 하나로 멱등을 보장한다

**Context**
포트원 웹훅은 재전송된다. 중복으로 `CHARGE`가 들어가면 곧바로 금전 사고다. §6.1이 `idempotencyKey` 유니크 인덱스로 잠정 결정했다.

**Decision**
**`PointTransaction.idempotencyKey`에 유니크 인덱스를 걸고, 그 제약 위반을 "이미 처리됨"으로 해석한다.**

- 키는 포트원이 주는 결제 건 식별자에서 만든다. 우리가 생성하지 않는다 — 우리가 만들면 재전송 때 같은 키가 나오는 것을 보장할 수 없다
- 삽입을 시도하고 **유니크 위반이 나면 성공으로 응답한다.** 웹훅에 200을 주지 않으면 포트원이 계속 재전송한다
- 먼저 조회해서 있으면 건너뛰는 방식은 쓰지 않는다. 조회와 삽입 사이에 틈이 있어 동시 재전송 두 건이 모두 통과할 수 있다
- **DB 제약이 최후 방어선이다.** 애플리케이션 검사는 그 앞에서 대부분을 걸러내는 편의일 뿐이다

**Alternatives**

- **별도 수신 로그 테이블에 먼저 기록** — 기각. 로그 삽입과 원장 삽입이 두 트랜잭션이면 사이에 실패할 수 있고, 한 트랜잭션이면 유니크 인덱스와 같은 일을 테이블 하나 더 두고 하는 셈이다.
- **Redis 분산락** — 기각. §11이 "추가 인프라 0"을 목표로 하고 스케줄러도 advisory lock으로 해결했다. 락이 만료되면 중복이 통과하는 구멍도 남는다.
- **먼저 `SELECT`로 확인 후 `INSERT`** — 기각. 조회와 삽입 사이의 틈으로 동시 재전송이 통과한다. 이게 정확히 §4.4가 경고한 패턴이다.

**Consequences**

- 중복 충전이 DB 제약으로 막힌다. 애플리케이션 버그가 있어도 뚫리지 않는다
- 웹훅 처리가 단순하다. 삽입하고, 유니크 위반이면 200을 준다
- **유니크 위반과 다른 DB 오류를 구분해야 한다.** 전부 성공으로 처리하면 진짜 실패를 놓친다. Prisma의 `P2002`만 "이미 처리됨"으로 본다
- 키를 포트원 식별자에서 만들므로 **포트원이 그 값을 재전송마다 같게 준다는 전제**에 의존한다. 실결제 전환 시 문서로 확인해야 한다

**다시 여는 조건** — 포트원이 재전송마다 다른 식별자를 준다면 키 생성 규칙을 다시 설계한다.

### ADR-PAY-5 · Nest DI 토큰을 환경변수로 갈아끼운다

**Context**
"사업자등록 후 환경변수만 바꾸면 전환"이 이 프로젝트의 명시적 목표다(§6.4.2). 계좌 검증과 송금 두 지점을 인터페이스로 분리하고 구현체를 고르는 방법을 정해야 한다.

**Decision**
**서비스는 인터페이스만 알고, `AuthModule`이 하는 것과 같은 방식으로 모듈이 구현체를 꽂는다.**

```ts
{
  provide: AccountVerifier,
  useFactory: (config: ConfigService) =>
    config.get('ACCOUNT_VERIFY_MODE') === 'portone'
      ? new PortOneAccountVerifier(config)
      : new StubAccountVerifier(),
  inject: [ConfigService],
}
```

- **도메인 코드에 `if (mode === ...)`가 등장하지 않는다.** 분기는 모듈 한 곳뿐이다
- 이미 `ConsoleMailProvider`가 같은 자리에 있다(`auth.module.ts`). 새 패턴을 도입하는 게 아니라 있는 패턴을 따르는 것이다
- 테스트는 모듈을 거치지 않고 가짜 구현을 직접 주입한다. 지금 `LoginService` 테스트가 그렇게 한다

**Alternatives**

- **서비스 안에서 환경변수를 읽어 분기** — 기각. 분기가 도메인 로직에 섞이고, 테스트가 환경변수를 조작해야 한다. 모드가 늘면 분기가 여러 곳에 퍼진다.
- **어댑터 레지스트리** (모드 문자열 → 구현체 맵) — 기각. 구현체가 셋 이상이면 값을 하지만 지금은 둘(`stub`/`portone`)이다. 맵을 두면 등록 누락이 런타임 오류가 된다.

**Consequences**

- 전환이 환경변수 한 줄이다. 도메인 코드·DB 스키마·화면은 그대로다(§6.4.2의 목표)
- `ConsoleMailProvider`와 같은 모양이라 배울 것이 없다
- **모드를 잘못 넣으면 조용히 `stub`으로 떨어진다.** 운영에서 그러면 계좌 검증이 무조건 통과한다. `ConsoleMailProvider`가 운영에서 예외를 던지는 것과 같은 방어가 `StubAccountVerifier`에도 필요하다
- 팩토리가 `ConfigService`에 의존하므로 모듈 테스트가 조금 번거롭다. 서비스 테스트는 영향 없다

**다시 여는 조건** — 구현체가 셋 이상이 되면 레지스트리를 재검토한다.

### ADR-PAY-4 · 부분 확정 (전환 시점만)

`HOLD` → `PAYOUT`/`RELEASE`의 **시점**은 이 논의에서 정했다. **트랜잭션 경계는 아직 미정이다.**

| 시점           | 원장      | 환불 가능?          |
| -------------- | --------- | ------------------- |
| 공고 `OPEN`    | `HOLD`    | ❌ 잠긴 동안 불가   |
| 모집 미달·취소 | `RELEASE` | ✅ 다시 가능        |
| 완료 확인      | `PAYOUT`  | ❌ 영구히 불가      |
| 분쟁·규칙 위반 | `REJECT`  | ❌ 우리가 계속 보유 |

**잠금이 공고 `OPEN` 시점인 것이 핵심이다.** 완료 확인 시점에 잠그면 늦다 — 공고를 올려 모집 중인 동안 환불해 버리면 일한 사람에게 줄 돈이 없어진다.

"확인 버튼을 안 누르면?"이라는 악용 경로도 이 시점 때문에 닫힌다. 잠겨 있어 환불이 안 되므로 안 누르는 이득이 없다. **다만 며칠 뒤 자동 확인할지는 아직 정하지 않았다** — 근로자가 돈을 못 받는 상태가 방치되지 않도록 별도로 정해야 한다.

## 5. 용어 정의

| 용어      | 코드 식별자        | 정의                                     |
| --------- | ------------------ | ---------------------------------------- |
| 포인트    | `Point`            | 서비스 내부 화폐. **1포인트 = 1원**      |
| 원장      | `PointTransaction` | 포인트 증감 내역. **잔액은 원장의 합**   |
| 잠금      | `HOLD`             | 공고 등록 시 예산을 묶어두는 원장 유형   |
| 반환      | `RELEASE`          | 미체결분 잠금을 되돌리는 원장 유형       |
| 지급      | `PAYOUT`           | 업무 완료 시 구직자에게 넘어가는 것      |
| 환전      | `Exchange`         | 지급된 포인트를 **현금으로 바꾸는 절차** |
| 환전 요청 | `ExchangeRequest`  | 사용자가 환전을 요청한 기록              |

**금지어:** "차감" → **잠금 또는 지급** / "캐시·코인" → **포인트** / **"정산·출금" → 환전**

> **지급과 환전은 다른 것이다.** 지급은 구인자 포인트가 구직자 포인트로 넘어가는 것, 환전은 그 포인트를 현금으로 바꾸는 것. 섞어 쓰지 않는다.

### 원장 유형 (7개)

| type               | 부호 | 발생 시점           | 호출자 |
| ------------------ | ---- | ------------------- | ------ |
| `CHARGE`           | +    | 결제 웹훅 검증 성공 | B      |
| `REFUND`           | −    | 결제 취소           | B      |
| `HOLD`             | −    | 공고 `OPEN` 전환    | B      |
| `RELEASE`          | +    | 미체결분 반환       | B      |
| `PAYOUT`           | −/+  | 업무 완료 확인      | B      |
| `EXCHANGE_REQUEST` | −    | 환전 요청           | A      |
| `EXCHANGE_REVERT`  | +    | 환전 반려           | A      |
