# PRD — 포인트 · 결제 · 환전 (point-money)

> 담당: **공동 (원장 코어)** / **B 김규현** (결제·환불·`HOLD`·`RELEASE`·`PAYOUT`) / **A 최동훈** (환전)
> 상위 사양: `docs/result/spec-fixed.md` §6, §11.5
> 상태: **2-1 뼈대 완료 / 기술 결정 TODO**

---

## 1. 개요

### 목적

실제 돈이 포인트로 들어와서(충전), 공고에 묶이고(잠금), 일한 사람에게 넘어가고(지급), 다시 현금으로 나가는(환전) 전 과정을 **한 건도 어긋나지 않게** 기록한다.

### 왜 가장 위험한가

버그가 나면 사용자가 돈을 잃는다. 다른 도메인은 화면을 다시 그리면 되지만 여기는 원장이 틀어지면 수동으로 맞춰야 하고, 그 과정에서 신뢰가 무너진다.

### 왜 공유 커널인가

원장 유형 7개 중 5개를 B가, 2개를 A가 호출한다. 어느 한쪽 소유로 두면 상대는 남의 코드를 통해서만 돈을 만지게 된다. **돈은 버스팩터가 1이면 안 된다.** (roadmap §1.1)

### 범위

- `PointTransaction` 원장 (7개 유형)
- 포트원 결제창·웹훅 기반 충전, 환불
- `HOLD` / `RELEASE` / `PAYOUT` 도메인 연결
- 계좌 등록·검증, 환전 요청, 관리자 승인 화면
- 모드 전환 인터페이스 (`AccountVerifier`, `ExchangeProvider`)

## 2. 사용자 스토리

### 충전

- **구인자로서** 공고를 올리려면 먼저 포인트를 충전해야 한다는 걸 이해하고, 필요한 금액을 바로 채우고 싶다.
- **구인자로서** 결제했는데 포인트가 안 들어오는 일이 없기를 원한다. 네트워크가 끊겨도, 새로고침을 해도, 결제는 한 번만 반영되어야 한다.

### 잠금 · 지급

- **구인자로서** 공고를 올리면 그만큼 포인트가 묶이는 걸 알고 싶다. 잔액이 부족하면 등록 전에 알려줘야 한다.
- **구인자로서** 6명 모집에 3명만 찼으면 **나머지 3명분이 자동으로 돌아오기를** 원한다. 따로 신청하고 싶지 않다.
- **구직자로서** 일을 마치면 약속한 포인트가 확실히 들어오기를 원한다.

### 환전

- **구직자로서** 쌓인 포인트를 현금으로 받고 싶다.
- **구직자로서** 내 계좌가 제대로 등록됐는지 확인받고 싶다. 엉뚱한 계좌로 갈까 봐 불안하다.
- **관리자로서** 환전 요청자 목록을 보고 승인한 뒤, 직접 이체하고 완료를 찍고 싶다.
- **운영자로서** 나중에 실송금 API를 붙일 때 **화면과 도메인 코드를 다시 안 짜기를** 원한다.

### ADR-PAY-7 · 환불은 오래된 결제 건부터 소진한다

**Context**
구인자는 미리 충전하고 그 잔액으로 공고를 올린다(§6.3). 그래서 잔액과 결제 건이 1:1이 아니다. 문제는 **환불이 잔액을 줄이는 일이 아니라 특정 카드 결제 건을 취소하는 일**이라는 데 있다 — 어느 `paymentId`에 얼마를 취소할지 정해야 하고, 카드로 들어온 돈은 그 카드로만 돌아간다.

여기에 둘이 얽힌다. **카드 취소에는 기한이 있고**(원거래로부터 일정 기간, 계약에 따라 다름), **근로자 지급에는 기한이 없다**(우리가 이미 들고 있는 돈에서 나가는 계좌 이체라 카드와 무관하다).

**Decision**
**환불은 남은 결제 건 중 `createdAt`이 가장 오래된 것부터 소진한다(FIFO).** 잠금(`HOLD`)과 지급(`PAYOUT`)도 같은 순서로 소진한다.

| 항목        | 결정                                                                                          |
| ----------- | --------------------------------------------------------------------------------------------- |
| 부분환불    | 허용. 마지막 lot에서 끝수를 맞추는 데 필요하다                                                |
| 소진 순서   | 환불·잠금·지급 **모두 FIFO**                                                                  |
| lot 잔여    | 컬럼으로 두지 않고 **원장에서 계산**한다. 원장 행이 `sourcePaymentId`를 참조한다              |
| 취소 기한   | `Payment.refundableUntil`을 지금 만들고 값은 비운다. 기한이 지난 lot은 FIFO 순서에서 건너뛴다 |
| 근로자 지급 | **기한 없음.** `refundableUntil`은 환불 경로에서만 본다                                       |

**왜 FIFO인가 — 취향이 아니다.** 카드 취소 기한이 오래된 건부터 먼저 만료된다. 오래된 것을 먼저 쓰면 취소 불가로 굳는 금액이 최소가 된다. 최신 것부터 쓰면 오래된 건이 잔액에 남아 있다가 기한이 지나 **"잔액은 있는데 환불이 안 되는" 금액**이 된다.

**Alternatives**

- **부분환불 금지 (`PAY` 또는 `REFUND` 둘 중 하나)** — 기각. lot 추적이 아예 필요 없어 가장 단순하지만 "5만원 충전 후 2만원만 환불"이 불가능하다. 전액 취소 후 재충전하면 카드 취소에 며칠 걸리는 동안 잔액이 0이라 공고를 못 올린다. 1,000원 단위 여러 건으로 쪼개는 방법은 카드 수수료가 건당 붙어 성립하지 않는다.
- **소비는 lot을 안 건드리고 환불만 lot에서 뽑는다** — 기각. lot 잔여 합계와 실제 잔액이 영구히 어긋난다. `min()`으로 막으면 사고는 안 나지만 **"얼마 환불 가능?"에 답이 두 개 나온다.** §6.1의 "진실의 원천은 항상 원장"과 정면으로 어긋난다.
- **충전을 없애고 공고 등록 시 그 금액만 결제** — 기각. 이 ADR이 통째로 필요 없어지는 안이다(결제 건 = 공고 1:1이므로 FIFO·lot·`HOLD`가 다 사라진다). 사양이 충전으로 정해져 있고(§6.3, 이슈 #28), 공고를 반복해 올리는 구인자가 매번 카드를 꺼내는 마찰이 크다고 판단했다. **다만 되돌리기 가장 어려운 기각이므로 김규현이 볼 첫 지점이다.**

**Consequences**

- 환불이 카드 취소 기한과 맞물려 돌아간다. 취소 불가로 굳는 금액이 최소가 된다
- 숫자가 한 벌이다. lot 잔여도 잔액도 원장에서 나온다
- **환불 한 번에 카드 취소가 여러 번 나갈 수 있다.** lot 두 개에 걸치면 PG 호출이 두 번이고, 중간에 하나가 실패하면 부분만 취소된 상태가 된다. **환불을 여러 취소의 묶음으로 다루고 각 취소의 성공·실패를 개별 기록해야 한다** — 카드사 호출을 되돌릴 방법이 없으므로 원자적으로 만들 수 없다
- lot 잔여를 원장에서 계산하므로 조회가 무겁다. `sourcePaymentId` 인덱스가 필요하고, 느려지면 캐시를 `ADR-PAY-1`에서 함께 다룬다
- **기한이 지난 lot이 잔액에 남는다.** 화면에서 그 사실을 알려야 하고, 그 금액의 정리 방법은 실결제 전환 시 정한다

**이 결정을 다시 여는 조건**

- **김규현이 이견을 내면** — PRD가 공동 결정으로 정해 둔 도메인이다
- 실결제 후 취소 기한이 짧아 "환불 불가 잔액"이 자주 생기면 → 충전 상한을 두거나 공고별 결제를 재검토
- 구인자 한 명의 결제 건이 수백 건이 되어 환불 화면이 느려지면 → lot 스냅샷 도입

### ADR-PAY-4 · 부분 확정 (전환 시점만)

`HOLD` → `PAYOUT`/`RELEASE`의 **시점**은 이 논의에서 정했다. **트랜잭션 경계는 아직 미정이다.**

| 시점           | 원장      | 환불 가능?          |
| -------------- | --------- | ------------------- |
| 공고 `OPEN`    | `HOLD`    | ❌ 잠긴 동안 불가   |
| 모집 미달·취소 | `RELEASE` | ✅ 다시 가능        |
| 완료 확인      | `PAYOUT`  | ❌ 영구히 불가      |
| 분쟁·규칙 위반 | `REJECT`  | ❌ 우리가 계속 보유 |

**잠금이 공고 `OPEN` 시점인 것이 핵심이다.** 완료 확인 시점에 잠그면 늦다 — 공고를 올려 모집 중인 동안 환불해 버리면 일한 사람에게 줄 돈이 없어진다.

"확인 버튼을 안 누르면?"이라는 악용 경로도 이 시점 때문에 닫힌다. 잠겨 있어 환불이 안 되므로 안 누르는 이득이 없다. **다만 며칠 뒤 자동 확인할지는 아직 정하지 않았다** — 근로자가 돈을 못 받는 상태가 방치되지 않도록 별도로 정해야 한다.

## 4. Out of Scope

| 항목                                  | 이유                                                      |
| ------------------------------------- | --------------------------------------------------------- |
| **실제 계좌 송금**                    | 사업자등록 필요. MVP는 관리자 수동 이체 (spec-fixed §6.4) |
| **계좌 실명 실조회**                  | 위와 동일. MVP는 형식 검사 후 자동 `VERIFIED`             |
| 원천징수 / 세금계산서 / 지급명세서    | 사업자 영역                                               |
| 환전 수수료 계산                      | 없음                                                      |
| 포인트 유효기간 / 소멸                | 없음                                                      |
| 포인트 선물 / 회원 간 이전            | 악용 위험                                                 |
| 정기 결제 / 자동 충전                 | 건별 충전만                                               |
| 쿠폰 / 프로모션 / 적립                | 없음                                                      |
| 부분 환불 UI (사용자 직접)            | 관리자 처리만                                             |
| 다중 통화                             | 원화만                                                    |
| 이체 내역 대사(reconciliation) 자동화 | 관리자 육안 확인                                          |
| 포인트 통계 대시보드                  | 목록·내역 조회까지만                                      |

## 5. 용어 정의

| 용어      | 코드 식별자        | 정의                                     |
| --------- | ------------------ | ---------------------------------------- |
| 포인트    | `Point`            | 서비스 내부 화폐. **1포인트 = 1원**      |
| 원장      | `PointTransaction` | 포인트 증감 내역. **잔액은 원장의 합**   |
| 잠금      | `HOLD`             | 공고 등록 시 예산을 묶어두는 원장 유형   |
| 반환      | `RELEASE`          | 미체결분 잠금을 되돌리는 원장 유형       |
| 지급      | `PAYOUT`           | 업무 완료 시 구직자에게 넘어가는 것      |
| 환전      | `Exchange`         | 지급된 포인트를 **현금으로 바꾸는 절차** |
| 환전 요청 | `ExchangeRequest`  | 사용자가 환전을 요청한 기록              |

**금지어:** "차감" → **잠금 또는 지급** / "캐시·코인" → **포인트** / **"정산·출금" → 환전**

> **지급과 환전은 다른 것이다.** 지급은 구인자 포인트가 구직자 포인트로 넘어가는 것, 환전은 그 포인트를 현금으로 바꾸는 것. 섞어 쓰지 않는다.
