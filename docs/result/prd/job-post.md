# PRD — 공고 (job-post)

> 담당: **B (김규현)**
> 상위 사양: `docs/result/spec-fixed.md` §3, §11.2, §11.6
> 상태: **2-1 뼈대 완료 / ADR 5건 확정 완료**

---

## 1. 개요

### 목적

구인자가 일거리를 등록하고, 그 내용이 바뀌었을 때 이미 신청한 사람과의 계약 조건이 조용히 달라지지 않도록 보장한다.

### 왜 이 도메인이 가장 어려운가

**버전 정책** 때문이다. planner.md에서 유일하게 "정의가 미흡하다"고 표시된 항목이고, 잘못 설계하면 나중에 공고 테이블과 신청 테이블을 동시에 뜯어야 한다.

### 범위

- 카테고리 (테이블 + seed + 플레이스홀더 문구)
- 공고 CRUD, 상태머신, 소프트 삭제
- **버전 이력 및 필수항목 변경 감지**
- 공고 목록·검색·필터 (`FilterableList` 공통 컴포넌트 포함)
- 관리자 공고 관리 화면

---

## 2. 사용자 스토리

### 등록

- **구인자로서** 카테고리를 고르면 그 업종에서 꼭 적어야 할 내용이 안내되기를 원한다. 뭘 써야 할지 몰라 부실한 공고를 올리고 싶지 않다.
- **구인자로서** 가입 주소가 기본으로 채워지되 다른 장소도 추가할 수 있기를 원한다. 매번 주소를 다시 입력하기 싫다.

### 수정

- **구인자로서** 오탈자를 고칠 때는 아무 일도 안 생기고, 시급이나 시간을 고칠 때만 지원자에게 다시 확인받기를 원한다. 사소한 수정으로 지원자를 잃고 싶지 않다.
- **구직자로서** 내가 신청한 조건이 바뀌면 즉시 알고, **무엇이 어떻게 바뀌었는지** 보고 싶다.

### 탐색

- **구직자로서** 내 동네·업종·시급으로 공고를 걸러 보고 싶다.
- **구직자로서** 필터를 걸어둔 목록을 새로고침하거나 링크로 공유해도 그대로이기를 원한다.

### 마감

- **구인자로서** 시작 3시간 전에 인원이 안 찼으면 알림을 받고 연장·삭제·유지를 고르고 싶다.
- **관리자로서** 문제 공고를 검색해 강제 취소할 수 있어야 한다.

### ADR-JOB-1 · 버전 이력을 전체 스냅샷으로 저장한다

**Context**
필수항목 6개가 바뀌면 `version += 1`이고, `Application.appliedVersion`이 그 시점을 가리킨다. 이 이력으로 두 가지를 해야 한다. ① 신청자에게 변경 전/후 **diff 표시** ② "내가 동의한 조건이 무엇이었나"의 **계약 복원**. 어떤 모양으로 저장할지가 미정이었다.

**Decision**
`JobPostVersion` 테이블에 버전마다 **필수항목 6개 전부를 정규 컬럼으로** 남긴다. v1은 공고 생성 시 함께 만들고, `JobPost` 본체는 조회 성능을 위해 항상 최신 값을 들고 있다.

**Alternatives**

- **변경 필드만 diff JSON으로 저장** — 거부. diff 표시만 보면 가장 낫지만, 계약 복원을 하려면 v1부터 모든 diff를 순서대로 적용해야 한다. **중간 diff 하나가 잘못 기록되면 그 이후 모든 버전의 복원이 틀어진다.** `appliedVersion`은 화면용 숫자가 아니라 분쟁 시 근거가 되는 계약 내용이므로, 이 위험을 저장 공간과 바꿀 수 없다. 또 `Json` 컬럼은 Prisma가 `JsonValue`로만 알아서 "zod 스키마 하나가 타입을 책임진다"는 `packages/shared` 원칙이 반쯤 깨진다.
- **이벤트 소싱** — 거부. 이 규모에 과하다. 이벤트 소싱은 감사 추적이 제품의 핵심 가치일 때 값을 하는데, 우리에게 필요한 추적은 스냅샷 테이블 하나로 충분하다. 조회마다 재생 또는 프로젝션이 끼어들어 API 전체가 무거워지고, 저장소에 전례가 없어 2인 팀이 막혔을 때 참조할 코드가 없다.

**Consequences**

- ✅ 계약 복원이 `WHERE version = 2` 한 줄이다. 분쟁 대응이 단순하다.
- ✅ 스키마가 자기 설명적이라 SQL로 바로 읽히고, Prisma 타입이 그대로 산다.
- ✅ 테스트 픽스처가 행 하나라 단순하다.
- ❌ **diff 계산 코드를 직접 써야 한다.** 두 버전을 읽어 필드별로 비교하는 로직이 필요하다. diff JSON 방식이었다면 공짜였다.
- ❌ 저장량이 버전 수에 비례한다. 필수항목이 6개로 고정이고 공고당 2~3버전 전제라 감내 가능하다고 판단했다. **공고 하나가 수십 번 수정되는 사용 패턴이 관측되면 이 결정을 다시 연다.**

### ADR-JOB-2 · 필수항목 변경을 서비스 계층에서 감지한다

**Context**
"필수항목 6개가 바뀌면 version을 올리고, 부가항목만 바뀌면 그대로"를 어디서 판정할지 미정이었다. 이 판정이 새면 신청자가 모르는 사이 조건이 바뀌거나(위험), 오탈자 하나에 지원자 전원이 재동의 대기가 된다.

**Decision**
`JobPostService.update()` 안에서 `VERSIONED_FIELDS` 상수 배열을 순회하며 기존 값과 새 값을 비교한다. 비교 로직은 순수 함수로 분리해 DB 없이 단위 테스트한다.

**Alternatives**

- **Prisma 확장(`$extends`)으로 가로채기** — 거부. "누락이 구조적으로 불가능"하다는 장점은 인정하지만, **버전 증가는 부수 효과가 큰 동작**이다. 지원자 전원을 `PENDING_REACCEPT`로 내리고 알림을 보낸다. 이런 동작이 update 호출에 암묵적으로 따라붙으면 "왜 지원자가 전부 재동의 대기가 됐지?"를 추적하기 어렵다. 저장소에 확장 사용 전례도 없다.
- **DB 트리거** — 거부. 로직이 TypeScript 밖으로 나간다. `planner.md`가 TypeScript를 고른 이유가 "AI에게 맡길 때 타입 오류로 절반을 거른다"인데, 트리거는 그 이점을 정면으로 버린다. Testcontainers 없이는 검증도 불가능하고 디버깅이 어렵다.

**Consequences**

- ✅ 판정 로직이 코드에 다 보인다. 버전이 왜 올랐는지 추적이 쉽다.
- ✅ 순수 함수라 DB 없이 빠르게 단위 테스트한다.
- ❌ **필수항목을 7번째로 추가할 때 상수 배열 갱신을 사람이 기억해야 한다.** 이 위험은 `issues.md` #15의 AC("필수항목 6개 각각, 하나씩 고치면 매번 version이 오른다")가 6개 필드를 전부 도는 테스트로 막는다. 필드를 추가하면 이 테스트도 함께 늘려야 한다.
- ❌ 앱을 우회한 직접 SQL은 잡지 못한다. 운영 DB에 직접 DDL/DML을 실행하지 않는다는 기존 규칙에 의존한다.

### ADR-JOB-3 · 상태 전이를 전이 테이블로 관리한다

**Context**
공고 상태가 6개(`DRAFT`/`OPEN`/`CLOSED`/`COMPLETED`/`CANCELLED`/`EXPIRED`)이고, 전이 조건에 시간·인원·포인트가 얽힌다. 가능한 전이 조합은 30개이며 그중 일부만 허용된다.

**Decision**
`{ from, to, guard }` 목록을 `packages/shared`에 상수로 두고, 모든 상태 변경이 공용 `transition()` 함수를 통과하게 한다. 표에 없는 전이는 자동 거부된다.

**Alternatives**

- **메서드별 분기** — 거부. 허용된 전이가 `cancel()`, `close()`, `complete()` 등에 흩어져 있어 **"지금 어떤 전이가 허용되는가"를 한눈에 볼 수 없다.** 새 상태를 추가할 때 빠뜨리는 곳이 생기고, 테스트도 메서드마다 따로 써야 한다.
- **상태머신 라이브러리(XState)** — 거부. 잘 만든 도구지만 우리 전이는 조건이 단순하고 병렬 상태나 계층 상태가 없다. 의존성 추가와 2인 팀의 학습 비용을 낼 만한 이득이 없다.

**Consequences**

- ✅ 허용된 전이가 한 곳에 표로 있어 전체 규칙을 한눈에 본다.
- ✅ 전이 표 자체를 테이블 테스트로 한 번에 검증한다.
- ✅ **`Application`의 10개 상태머신에 같은 패턴을 재사용한다.** `ADR-APP-4`는 이 결정을 그대로 따른다.
- ❌ 전이 하나를 추가할 때 표와 guard 함수 **두 곳**을 손대야 한다. 메서드별 분기였다면 한 곳이면 됐다.
- ❌ guard가 포인트·알림 같은 부수 효과를 부르면 표가 "선언적"이라는 인상과 실제 동작이 어긋날 수 있다. **guard는 판정만 하고 부수 효과는 호출부에 둔다**는 규칙을 함께 지킨다.

### ADR-JOB-4 · 목록 필터의 진실은 URL 하나다

**Context**
검색·필터 화면이 7개다(사용자 공고 목록 1 + 관리자 목록 6). `spec-fixed.md` §11.2가 "새로고침·공유해도 필터가 유지된다"와 "필터 칩 개별 해제"를 요구한다.

**Decision**
`useSearchParams()`로 읽고 `router.replace()`로 쓴다. 컴포넌트는 필터 로컬 상태를 갖지 않는다. 서버 컴포넌트는 `searchParams`를 직접 받아 목록을 조회한다.

**Alternatives**

- **로컬 상태 + URL 동기화** — 거부. 상태가 두 곳(`useState`, URL)에 있어 **둘이 어긋나는 순간이 반드시 생긴다.** 특히 뒤로가기에서 URL은 바뀌었는데 로컬 상태가 그대로인 버그가 흔하고, 목록 7개에 각각 동기화 코드를 써야 한다.
- **서버 상태 라이브러리(TanStack Query)** — 거부. 캐싱은 관리자 화면에서 값을 하겠지만 지금 필요한 건 "필터 걸고 조회"뿐이다. 의존성이 늘고 URL 유지는 여전히 따로 구현해야 한다. **다만 이 결정이 나중의 도입을 막지 않는다** — 캐싱이 아쉬워지면 URL 방식 위에 얹을 수 있다.

**Consequences**

- ✅ 진실이 한 곳이라 "상태와 URL이 어긋나는" 버그 종류 자체가 없다.
- ✅ 서버 컴포넌트가 `searchParams`를 직접 받아 초기 로딩이 빠르다.
- ✅ E2E가 URL만 검증하면 된다.
- ❌ **필터를 바꿀 때마다 라우팅이 발생한다.** 타이핑 검색은 디바운스(300ms)로 눌러야 하고, 안 눌러두면 글자마다 요청이 나간다.
- ❌ 필터 상태가 URL에 노출되므로 파라미터 이름이 사실상 공개 API가 된다. 나중에 바꾸면 공유된 링크가 깨진다.

### ADR-JOB-5 · 복합 인덱스 + 오프셋 페이징

**Context**
필터 조합이 6개(카테고리, 시/도, 시/군/구, 상태, 기간, 검색어)다. 인덱스를 정하려면 데이터 규모 전제를 먼저 못 박아야 한다.

**전제 규모 (MVP 1년):** 공고 누적 10만 건 이하, 활성(`OPEN`) 공고 1천 건 이하, 회원 1만 명 이하.

**Decision**
자주 쓰는 필터 조합에 복합 인덱스를 걸고 `LIMIT/OFFSET`으로 페이징한다. `pg_trgm` GIN 인덱스는 지금 도입하지 않는다.

**Alternatives**

- **키셋(커서) 페이징** — 거부. 깊은 페이지 성능은 낫지만 **전체 건수를 셀 수 없다.** 관리자 목록 6개가 전부 "총 152건"을 표시해야 하므로 요구와 맞지 않는다. "3페이지로 바로 가기"도 불가능하다.
- **`pg_trgm` 선제 도입** — 보류. 회원 1만 명 규모에서 `LIKE '%김%'`은 순차 스캔으로도 수십 밀리초다. **지금 넣지 않아도 나중을 막지 않는다** — 필요해지면 인덱스만 추가하면 되고 쿼리 코드는 그대로다.

**Consequences**

- ✅ 관리자 화면의 전체 건수 표시 요구를 충족한다.
- ✅ "21건 중 2페이지에 1건" 같은 AC를 그대로 테스트한다.
- ❌ **전제 규모를 크게 넘으면(활성 공고 수만 건) 깊은 페이지가 느려진다.** 그때 키셋으로 바꾸려면 API 파라미터와 페이징 컴포넌트를 함께 고쳐야 한다.
- ❌ 인덱스가 쓰기 성능을 조금 깎는다. 공고는 읽기가 압도적으로 많아 감내한다.

**인덱스 초안** — Green 단계에서 `EXPLAIN`으로 실제로 타는지 확인하고 조정한다.

```sql
CREATE INDEX idx_jobpost_open_list
  ON "JobPost" (status, sido, sigungu, "categoryId", "createdAt" DESC)
  WHERE "deletedAt" IS NULL;

CREATE INDEX idx_jobpost_admin_list
  ON "JobPost" ("createdAt" DESC, status);

CREATE INDEX idx_jobpost_poster
  ON "JobPost" ("posterId", "createdAt" DESC);
```

## 4. Out of Scope

| 항목                               | 이유                                                |
| ---------------------------------- | --------------------------------------------------- |
| 지도 위 공고 표시 / 반경 검색      | 좌표는 저장하되 MVP는 시/도·시/군/구 필터까지만     |
| 공고 이미지 업로드                 | 텍스트만                                            |
| 공고 템플릿 저장·복제              | 반복 등록 편의 기능. MVP 이후                       |
| 공고 끌어올리기 / 광고 / 상단 노출 | 수익 모델 미정                                      |
| 카테고리 관리자 CRUD 화면          | seed로만 관리 (spec-fixed §3.1)                     |
| 카테고리 계층 구조 (대분류·중분류) | 단일 레벨                                           |
| 공고 검색 자동완성 / 연관 검색어   | 단순 부분 일치까지만                                |
| 공고 북마크 / 찜하기               | 없음                                                |
| 공고 조회수 / 통계 대시보드        | 없음                                                |
| 공고 내 구인자-구직자 채팅         | 별점만 쓰기로 한 서비스 방향과 어긋남               |
| 버전 되돌리기(rollback) 기능       | 이력은 남기되 과거 버전으로 복원하는 UI는 안 만든다 |
| 정기 공고 / 반복 일정              | 단건만                                              |

## 5. 용어 정의

| 용어      | 코드 식별자       | 정의                                                                                                                          |
| --------- | ----------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 공고      | `JobPost`         | 일거리 게시물                                                                                                                 |
| 공고 버전 | `JobPost.version` | 필수항목 수정 시 +1 되는 정수                                                                                                 |
| 필수항목  | _(개념)_          | `workAddress`, `workStartAt`, `workEndAt`, `rewardPerPerson`, `headcount`, `requiredDescription` — **이 6개만 버전을 올린다** |
| 확정 인원 | `acceptedCount`   | 상태가 `ACCEPTED` 이상인 신청 수                                                                                              |

**금지어:** "게시글 / 구인글" → **공고**

### 상태머신 (확정)

```
DRAFT ──▶ OPEN ──┬──▶ CLOSED ──▶ COMPLETED
                 ├──▶ CANCELLED
                 └──▶ EXPIRED
```
