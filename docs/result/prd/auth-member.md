## 1. 개요

### 목적

서비스의 모든 행위 주체인 `User`를 만들고, 그 계정의 생명주기(가입 → 사용 → 비활성화 → 재활성화 또는 파기)를 관리한다.

### 왜 가장 먼저인가

다른 모든 도메인(공고·신청·포인트·제재·평점)이 `User`를 FK로 참조한다. 이 스키마가 흔들리면 전부 흔들린다.

### 범위

- 이메일 인증 기반 가입
- JWT 인증 및 보호 라우팅
- 주소 등록 (카카오 우편번호 + 좌표)
- 비밀번호 재설정 (변경은 차단)
- 탈퇴(비활성화) / 재활성화 / 개인정보 파기
- 관리자 회원 목록·상세 화면

### 범위 밖

전자서명·동의서는 `agreement` PRD가 다룬다. 가입 플로우의 5번째 단계로 호출만 한다.

## 2. 사용자 스토리

### 가입

- **구직자로서** 이메일 인증을 거쳐 가입하고 싶다. 실제로 받을 수 있는 주소여야 재동의 요청·제재 알림이 도달하기 때문이다.
- **가입자로서** 주소를 직접 타이핑하지 않고 검색해서 넣고 싶다. 오타가 있으면 근무지가 엉뚱한 곳으로 잡힌다.

### 인증

- **회원으로서** 로그아웃한 뒤 뒤로가기를 눌러도 내 정보가 보이지 않기를 원한다. 공용 PC에서 쓸 수 있기 때문이다.
- **회원으로서** 비밀번호를 잊어도 계정을 되찾고 싶다. 포인트 잔고가 묶여 있기 때문이다.

### 계정 종료

- **탈퇴하려는 회원으로서** 포인트가 남아 있으면 탈퇴가 막히기를 원한다. 실수로 돈을 잃고 싶지 않다.
- **탈퇴하려는 회원으로서** 진행 중인 일이 있으면 탈퇴가 막히기를 원한다 — 반대로 **구인자로서는**, 수락한 사람이 탈퇴로 사라지지 않기를 원한다.
- **돌아온 사용자로서** 예전 계정이 살아나기를 원한다. 쌓아둔 평점을 잃고 싶지 않다.

### 관리자

- **관리자로서** 이름·주소로 회원을 검색해 상세를 열고, 평점·거래 이력·제재 이력을 한 화면에서 보고 싶다. 분쟁 문의가 오면 그 사람의 이력을 즉시 확인해야 한다.

### ADR-AUTH-1 · Refresh 토큰을 로그인 세션당 한 행으로 둔다

**Context**
`spec-fixed.md` §2.5가 Access(JWT 15분)와 Refresh(14일, `RefreshToken` 테이블에 해시 저장)를 이미 정했다. 남은 것은 행의 단위였다 — 계정당 하나인가, 로그인 세션당 하나인가. 그리고 갱신할 때 토큰을 회전(rotation, 갱신마다 새 토큰을 발급하고 옛 것을 폐기)시킬 것인가. 이 하나가 다중 기기 로그인 가능 여부와 탈취 토큰 탐지 가능 여부를 함께 결정한다.

**Decision**
**로그인할 때마다 `RefreshToken` 행을 하나 추가한다.** `userId`에는 유니크를 걸지 않고 `tokenHash`에 건다. 회전은 하지 않는다 — 발급된 Refresh 토큰은 14일 동안 값이 바뀌지 않는다.

- 로그인 = `create`
- 갱신 = `findUnique(tokenHash)` 후 만료 확인
- 로그아웃 = `delete(tokenHash)` — 그 기기만 끊긴다
- 전체 무효화(비밀번호 재설정·비활성화) = `deleteMany(userId)`

사실 이 결정은 사양이 이미 담고 있었다. §2.4의 "해당 사용자의 **모든** Refresh 토큰 무효화"와 §2.6의 "**모든** Refresh 토큰 삭제"는 회원당 토큰이 여럿 존재할 때만 성립하는 문장이다.

**Alternatives**

- **계정당 행 하나 (`userId @unique`, 로그인 시 덮어쓰기)** — 기각. 휴대폰에서 로그인하면 PC가 조용히 로그아웃된다. 사양 어디에도 그런 제약이 없는데 구조가 제약을 만들어낸다. "모든 Refresh 토큰"이라는 사양 문구와도 어긋나고, 이력을 쌓는 `ADR-AUTH-4`의 결과도 아니다.
- **세션당 행 + 회전 + 재사용 탐지 (`usedAt`·`replacedById`)** — 기각. 얻는 것은 탈취 탐지 하나인데 대가가 셋이다. 갱신 경로에 트랜잭션이 필요하고, 행이 기기당 14일에 약 1,300개까지 쌓이며, 무엇보다 **탭 두 개가 같은 순간 갱신하면 정상 사용자가 강제 로그아웃된다.** 이걸 막으려 유예 시간을 넣는 순간 탐지 정확도가 떨어져 애초의 목적이 흐려진다. 사양에도 AC에도 회전 요구가 없다.

**Consequences**

- 휴대폰과 PC에 동시 로그인이 된다. 로그아웃은 그 기기만 끊는다.
- `codeHash`(`EmailVerification`)와 같은 모양이라 기존 패턴과 결이 맞는다.
- **탈취된 Refresh 토큰이 최대 14일간 유효하고, 탐지할 방법이 없다.** 완화 요소는 셋이다 — httpOnly 쿠키라 XSS로 못 빼가고, Access가 15분이라 곧 갱신을 타야 하며, 비밀번호 재설정 시 전량 무효화가 탈출구다. 그래도 못 잡는다는 사실은 그대로다.
- 만료 행 정리 주체를 정해야 한다. #39(개인정보 파기 배치)에 얹는다.

**이 결정을 다시 여는 조건**

- 실제 계정 탈취 신고가 관측되면 → 회전으로 올린다. 같은 테이블에 `usedAt`·`replacedById` 두 컬럼을 더하는 일이다.
- 관리자 강제 로그아웃 요구가 생기면 → 재검토 불필요. `deleteMany(userId)`로 이미 된다.
- 한 계정 돌려쓰기가 문제가 되면 → 동시 세션 수 상한을 위에 얹는다. 행 수를 세면 된다.

3안 비교 원본은 `docs/result/adr/auth-member.md`에 있다.

### ADR-AUTH-2 · 주소를 분해해 `UserAddress` 테이블에 저장한다

**Context**
카카오 우편번호 팝업이 돌려준 주소를 어떤 모양으로 저장할지. 단일 문자열로 통째로 두면 관리자 화면의 시/도 → 시/군/구 필터를 걸 수 없고, 분해해서 저장하면 카카오 응답 형식에 종속된다.

**Decision**
**분해해서 저장한다.** 3안 비교가 필요 없었다 — 사양과 AC가 이미 답을 담고 있다.

- `spec-fixed.md` §2 흐름 4: "도로명주소·지번·우편번호 저장, 카카오 로컬로 `lat`/`lng` 변환 저장"
- `spec-fixed.md` §3: "`UserAddress` 테이블, 라벨 지정" — 테이블 이름까지 정해져 있다
- `spec-fixed.md` §11: 관리자 필터가 "주소지(**시/도 → 시/군/구**)"
- 이슈 #3 AC2: "시/도·시/군/구가 **분해되어** 저장된다"

관리자 필터가 두 단계 지역 선택을 요구하는 이상 분해는 선택이 아니라 요건이다. 통 문자열에 `LIKE`를 걸면 "경기도 광주시"와 "광주광역시"가 함께 걸린다.

`UserAddress`는 회원당 여러 행을 허용한다. 근무 주소의 기본값이 가입 주소이되 추가 등록·선택이 가능해야 하기 때문이다(§3). 라벨로 구분한다.

**Alternatives**

- **단일 문자열로 통째 저장** — 기각. 관리자 지역 필터를 걸 수 없다. 사양이 요구하는 기능이 아예 불가능해진다.
- **분해하되 좌표를 필수로** — 기각. 이슈 #3 AC3이 "좌표 변환 API가 실패해도 주소는 저장되고 저장 자체는 성공한다"고 못박았다. 좌표는 거리 검색과 지역 필터를 위한 것이지 가입을 막을 이유가 아니다. `lat`/`lng`는 nullable이다.

**Consequences**

- 카카오 응답 형식에 종속된다. 카카오가 필드를 바꾸면 파싱 지점을 고쳐야 한다. 파싱을 한 곳에 모아 그 지점을 하나로 유지한다.
- 좌표가 비어 있는 행이 존재할 수 있다. 거리 검색·지역 필터는 그런 행을 어떻게 다룰지 각자 정해야 한다.
- 회원당 여러 주소가 쌓인다. 기본 주소를 가리키는 방법이 필요하다.

**이 결정을 다시 여는 조건**

- 카카오 외 주소 공급자를 함께 쓰게 되면 → 파싱 계층을 인터페이스 뒤로 뺀다. 저장 구조 자체는 그대로 둘 수 있다.
- 시/군/구보다 더 잘게(읍/면/동) 필터해야 하면 → 컬럼을 더한다. 분해해 뒀으므로 확장이지 재설계가 아니다.

3안 비교 원본은 `docs/result/adr/auth-member.md`에 있다.

### ADR-AUTH-4 · 인증 코드를 발급 이력 테이블에 쌓는다

**Context**
이메일 인증 코드에 규칙이 넷 걸린다. 만료 10분, 재발송 쿨다운 60초, 시간당 5회 발송 제한, 그리고 확정된 시도 3회 제한. 이 넷을 어디서 어떻게 판정할지가 미정이었다.

**Decision**
`EmailVerification` 테이블에 **발급할 때마다 행을 추가**한다. 이메일당 여러 행이 쌓이고, 유효한 코드는 "가장 최근의, 소비되지 않은, 만료되지 않은" 행 하나다. 쿨다운은 최근 행의 `createdAt`으로, 시간당 5회는 최근 1시간 내 행 수로 판정한다. 코드는 해시로 저장한다.

**Alternatives**

- **이메일당 1행 upsert** — 거부. 행이 하나라 조회는 단순하지만 "시간당 5회"를 카운터와 윈도우 시작 시각으로 직접 관리해야 한다. 윈도우가 언제 리셋되는지가 코드에 숨고, 경계 버그가 나기 쉽다. 발급 이력이 남지 않아 스팸 패턴 추적도 불가능하다.
- **Redis TTL** — 거부. 만료가 자동이라는 장점이 있지만 `spec-fixed.md`에서 의도적으로 제외한 의존성이다(§8.2에서 advisory lock으로 Redis를 대체했다). 서버 재시작 시 발급된 코드가 전부 소실되고, 시간 경계 테스트가 어렵다.

**Consequences**

- ✅ **"시간당 5회"가 행 세기로 끝난다.** `Penalty`의 180일 롤링 5건과 **같은 판정 패턴**이라 저장소에 방식이 하나로 유지된다
- ✅ 테스트에서 원하는 시각의 행을 직접 꽂으면 경계 검증이 끝난다
- ✅ 발급 이력이 남아 스팸·이상 패턴을 추적할 수 있다
- ❌ **행이 계속 쌓인다.** 개인정보 파기 배치(#39)에 정리 대상으로 얹는다
- ❌ "유효한 코드는 최신 행 하나"라는 규칙을 코드가 지켜야 한다. 옛 행을 실수로 조회하면 이미 대체된 코드가 통과한다 — 이 케이스를 테스트로 못 박는다

## 5. 용어 정의

> `spec-fixed.md` §0에서 동기화. 이 PRD에서 새로 만드는 용어는 없다.

| 용어     | 코드 식별자     | 정의                                       |
| -------- | --------------- | ------------------------------------------ |
| 회원     | `User`          | 서비스 가입자. 역할 구분 없는 단일 엔티티  |
| 구인자   | `poster`        | 공고를 등록한 `User` (관계상의 역할)       |
| 구직자   | `worker`        | 공고에 신청한 `User` (관계상의 역할)       |
| 비활성화 | `deactivatedAt` | 탈퇴한 회원. 소프트 삭제 상태. 로그인 불가 |
| 관리자   | `role = ADMIN`  | 별도 테이블 아님                           |

**금지어:** "탈퇴 회원 / 삭제 회원" → **비활성화 회원**
