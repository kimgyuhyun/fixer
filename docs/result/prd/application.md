## 1. 개요

### 목적

구직자의 지원부터 구인자의 수락(= 계약 체결), 그리고 취소까지의 상태 전이를 관리한다. **이 도메인이 "누가 누구와 무엇을 약속했는가"의 진실을 갖는다.**

### 왜 까다로운가

세 가지가 동시에 걸린다.

1. **정원 제어** — 동시 요청에 정원이 초과되면 포인트 원장이 깨진다
2. **버전 충돌** — 공고가 바뀌면 이미 수락된 계약도 재동의 대기로 내려가야 한다
3. **취소 판정** — 무상 취소 창(수락 +2시간) 안팎에 따라 제재 여부가 갈린다

### 범위

- 지원 / 철회
- 구인자 승인제 수락·거절
- 정원 초과 방지
- 재동의(`PENDING_REACCEPT`) 흐름 및 diff 확인
- 취소 규칙 및 무상 취소 창 판정
- 업무 완료 확인

## 2. 사용자 스토리

### 지원 · 수락

- **구직자로서** 마음에 드는 공고에 지원하고, 수락되기 전까지는 자유롭게 철회하고 싶다.
- **구인자로서** 지원자들의 평점을 보고 골라서 수락하고 싶다. 선착순이면 사람을 고를 수 없다.
- **구인자로서** 6명을 뽑기로 했으면 실수로든 시스템 오류로든 7명이 확정되지 않기를 원한다. 인원이 넘으면 잠긴 포인트보다 지급할 돈이 많아진다.
- **구직자로서** 수락되면 즉시 알림을 받고 싶다. 다른 일자리를 계속 찾아야 할지 판단해야 한다.

### 변경 대응

- **구직자로서** 수락된 뒤 조건이 바뀌면 자동으로 계약이 유지되지 않기를 원한다. 시급이 내려갔는데 모르고 나가는 일이 없어야 한다.
- **구직자로서** 바뀐 조건이 마음에 안 들어 거절할 때 **불이익이 없기를** 원한다. 내 잘못이 아니다.
- **구인자로서** 오탈자 하나 고쳤다고 지원자를 전부 잃고 싶지 않다.

### 취소

- **양측 모두** 수락 직후 짧은 시간 안에는 실수를 되돌릴 수 있기를 원한다.
- **구인자로서** 당일에 사람이 안 나오면 그 사실이 기록되기를 원한다.

### `ADR-APP-1` — 정원 초과 방지 동시성 제어 ✅ 확정 (#18)

**결정: `JobPost.acceptedCount` 비정규화(정규화된 원본 대신 계산 결과를 따로 들고 있는 것) 카운터에 조건부 UPDATE.** `spec-fixed.md` §4.4의 잠정안을 그대로 확정한다.

수락은 **한 트랜잭션 안의 두 조건부 UPDATE**이고, 둘 다 1행을 갱신했을 때만 커밋한다.

1. `Application SET ACCEPTED, acceptedAt WHERE id = ? AND status = 'APPLIED'`
2. `JobPost SET acceptedCount + 1 WHERE id = ? AND acceptedCount < headcount`

**신청 갱신이 먼저다.** 카운터를 먼저 올리면 정원이 찬 공고에서 중복 수락했을 때 "정원이 찼다"고 답하게 된다 — 실제 이유는 그게 아닌데. 순서를 바꾸면 두 실패가 서로 구분된다.

#### 기각한 안

| 안                         | 기각 이유                                                                                                                                              |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `COUNT(*)` 서브쿼리로 판정 | READ COMMITTED에서 두 트랜잭션이 똑같은 수를 보고 **둘 다 통과한다.** §4.4가 그린 그림 그대로다. 컬럼이라야 UPDATE가 락을 잡은 뒤 조건을 다시 평가한다 |
| `SELECT ... FOR UPDATE`    | 동작은 하지만 잠금 구간이 길다. 조건부 UPDATE는 한 문장으로 끝난다                                                                                     |
| 유니크 슬롯 인덱스         | 자리마다 행을 만들어야 하고, 취소 후 빈 자리를 재사용하는 규칙이 #20에 종속된다                                                                        |

#### 유보였던 "부분 취소 후 카운터 정합성"에 대한 답

**#18은 올리기만 한다.** 내리는 쪽은 취소를 실제로 만드는 이슈(#19 거절·#20 취소·#21 재동의)가 같은 조건부 UPDATE로 내린다.

#18에서 감소를 미리 만들면 호출자가 없는 코드가 남고, 그 코드는 #20이 무상 취소 창을 정하기 전까지 **언제 불려야 하는지 알 수 없다.**

#### 이 결정이 강제하는 것

- **카운터가 진실이다.** `AcceptedCounter.countAccepted`도 행을 세지 않고 이 컬럼을 읽는다. 둘을 다 두면 화면에 보이는 수와 정원을 막는 수가 갈릴 수 있다
- 그 대가로 **`acceptedCount`와 `ACCEPTED` 행 수가 일치하는지**를 통합 테스트가 지킨다 (`application.integration.test.ts`)
- 정원이 차도 **공고를 자동으로 `CLOSED`로 바꾸지 않는다.** 취소가 생기면 되열어야 하는데 그 규칙이 #20에 있다

### `ADR-APP-5` — 업무 완료 확인 주체와 트리거 ✅ 확정 (#23)

**결정: 구인자가 공고 단위로 확인한다.** 확인하는 순간 확정 인원분이 `PAYOUT`되고 나머지는 `RELEASE`된다.

Out of Scope가 이미 "완료 확인은 구인자 확인으로 갈음"으로 정해둔 것을 그대로 확정한다. 출퇴근 체크도 GPS도 없으므로 **시스템이 일이 끝났는지 알 방법이 없다.**

#### 기각한 안

| 안                                | 기각 이유                                                                                                                  |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 근무 종료 시각이 지나면 자동 완료 | 일이 실제로 됐는지와 시각이 지난 것은 다르다. 노쇼(#24)가 그 차이다. 자동 완료는 **안 온 사람에게도 돈을 보낸다**          |
| 구인자·구직자 양자 확인           | 구직자가 확인을 안 하면 돈이 영원히 묶인다. 미확인을 처리할 기한과 이의제기 절차가 또 필요한데, 분쟁 조정은 Out of Scope다 |

#### 이 결정이 강제하는 것

- **확인 단위는 공고다.** 신청 하나씩 완료할 수 없다 — 그러면 `RELEASE`할 잔여를 언제 계산할지가 정해지지 않는다
- 구인자가 확인을 안 하면 **돈이 묶인 채로 남는다.** 미확인 공고를 강제 처리하는 규칙은 지금 없다. 관리자 강제 취소(#35)가 유일한 탈출구다
- 노쇼로 표시된 인원을 지급에서 빼는 것은 **#24가 이어받는다.** #23은 `ACCEPTED`만 센다

## 4. Out of Scope

| 항목                                  | 이유                                       |
| ------------------------------------- | ------------------------------------------ |
| 출퇴근 체크 / QR 인증 / GPS 출근 확인 | 완료 확인은 구인자 확인으로 갈음           |
| 근무 시간 실측 및 시간당 정산         | 건당 고정 보상만                           |
| 구인자-구직자 메시지·연락처 교환      | 별점만 쓰기로 한 방향과 어긋남             |
| 지원 시 자기소개서 / 첨부파일         | 지원은 버튼 하나                           |
| 대기자 명단 (waitlist)                | 정원이 차면 그냥 마감                      |
| 자동 매칭 / 추천                      | 구인자가 직접 고름                         |
| 계약서 생성 (공고별 개별 동의서)      | 가입 시 동의서 하나로 갈음                 |
| 부분 취소 시 대체 인원 자동 모집      | 구인자가 수동으로 다시 수락                |
| 노쇼 이의제기 / 분쟁 조정 프로세스    | 관리자 제재 해제로 갈음 (`penalty-rating`) |

## 5. 용어 정의

| 용어         | 코드 식별자        | 정의                                           |
| ------------ | ------------------ | ---------------------------------------------- |
| 신청         | `Application`      | 구직자가 공고에 지원한 기록                    |
| 수락         | `ACCEPTED`         | 구인자가 승인한 것. **이 순간이 계약 체결**    |
| 재동의       | `PENDING_REACCEPT` | 공고 버전이 올라 신청자의 재확인이 필요한 상태 |
| 무상 취소 창 | _(개념)_           | 수락 시각 +2시간. 이 안의 취소는 무패널티      |

**금지어:** "매칭 / 체결" → **수락**

### 상태머신 (확정)

```
APPLIED ──┬──▶ ACCEPTED ──┬──▶ COMPLETED
          │               ├──▶ CANCELLED_FREE      (수락 +2h 이내)
          │               ├──▶ CANCELLED_PENALTY   (2h 초과)
          │               └──▶ NO_SHOW
          ├──▶ REJECTED
          ├──▶ WITHDRAWN                            (수락 전 철회, 무패널티)
          │        └──▶ APPLIED                     (재지원, #17)
          └──▶ PENDING_REACCEPT ──┬──▶ (이전 상태로 복귀)
                                  └──▶ CANCELLED_BY_VERSION_CHANGE
```
