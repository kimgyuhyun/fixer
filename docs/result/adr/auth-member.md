## 이미 확정되어 3안 비교 대상이 아닌 것

`spec-fixed.md` §2.5가 이미 정한 것들이다. **아래는 선택지가 아니다.**

- Access 토큰: JWT, **15분**, httpOnly + Secure + SameSite=Lax 쿠키
- Refresh 토큰: **14일**, `RefreshToken` 테이블에 **해시로** 저장
- 로그아웃 시 서버에서 삭제
- 비밀번호 재설정 시 해당 사용자의 **모든** Refresh 토큰 무효화 (§2.4)
- 비활성화 시 모든 Refresh 토큰 삭제 (§2.6)

남은 결정은 하나다. **행을 어떤 단위로 두고, 갱신할 때 토큰을 바꿀 것인가.**

# ADR-AUTH-1 · 인증 토큰의 저장·갱신·무효화 구조

## 결정할 것

`RefreshToken` 행을 **계정당 하나**로 둘지 **로그인 세션당 하나**로 둘지, 그리고 갱신할 때 **토큰을 회전(rotation, 갱신할 때마다 새 토큰을 발급하고 옛 것을 폐기)** 시킬지.

이 하나가 세 가지를 동시에 결정한다 — 다중 기기 로그인이 되는가, 탈취된 토큰을 탐지할 수 있는가, 강제 로그아웃을 어떤 단위로 할 수 있는가.

---

## 안 A · 계정당 행 하나

`RefreshToken.userId`에 유니크를 건다. 로그인하면 기존 행을 덮어쓴다.

```prisma
model RefreshToken {
  id         String   @id @default(cuid())
  userId     String   @unique          // ← 계정당 하나
  tokenHash  String
  expiresAt  DateTime
  createdAt  DateTime @default(now())
  user       User     @relation(fields: [userId], references: [id])
}
```

| 기준            | 내용                                                                                  |
| --------------- | ------------------------------------------------------------------------------------- |
| 1 데이터 구조   | 가장 단순. 행 수가 회원 수를 넘지 않는다                                              |
| 2 API 변경지점  | `upsert` 한 번. 갱신은 `findUnique(userId)` 후 만료 확인                              |
| 3 상태관리      | 해당 없음 (httpOnly 쿠키라 프론트가 토큰을 들지 않는다)                               |
| 4 **핵심 동작** | **휴대폰에서 로그인하면 PC가 로그아웃된다.** 마지막 로그인만 살아남는다               |
| 5 컴포넌트 구조 | `middleware.ts` 하나. 셋 다 같다                                                      |
| 6 기존 패턴     | `ADR-AUTH-4`의 "이력을 쌓는다"와 **정면으로 어긋난다.** 덮어쓰기라 이력이 남지 않는다 |
| 7 테스트 용이성 | 가장 쉽다. 상태가 하나뿐이라 경우의 수가 적다                                         |

**#5 AC1**(로그아웃 시 서버 토큰 삭제)은 `delete(userId)` 한 줄. **#6 AC2**(전체 무효화)도 같은 한 줄이다 — 행이 애초에 하나뿐이라 "모든"이 자동으로 성립한다.

## 안 B · 로그인 세션당 행 하나, 회전 없음

로그인할 때마다 행을 추가한다. 유니크는 `tokenHash`에 건다.

```prisma
model RefreshToken {
  id         String   @id @default(cuid())
  userId     String                     // ← 유니크 아님. 여러 행 허용
  tokenHash  String   @unique
  expiresAt  DateTime
  createdAt  DateTime @default(now())
  user       User     @relation(fields: [userId], references: [id])

  @@index([userId])
}
```

| 기준            | 내용                                                                                                                 |
| --------------- | -------------------------------------------------------------------------------------------------------------------- |
| 1 데이터 구조   | 행이 (회원 × 기기)만큼. 만료 행을 치우는 정리가 필요하다 (#39 파기 배치에 얹으면 된다)                               |
| 2 API 변경지점  | 로그인 = `create`, 갱신 = `findUnique(tokenHash)`, 로그아웃 = `delete(tokenHash)`, 전체무효화 = `deleteMany(userId)` |
| 3 상태관리      | 해당 없음                                                                                                            |
| 4 **핵심 동작** | **휴대폰과 PC에 동시에 로그인된다.** 로그아웃은 그 기기만 끊는다                                                     |
| 5 컴포넌트 구조 | `middleware.ts` 하나                                                                                                 |
| 6 기존 패턴     | `ADR-AUTH-4`와 같은 모양이다 — 행을 쌓고 유효한 것을 고른다. `codeHash`처럼 `tokenHash`로 저장                       |
| 7 테스트 용이성 | 쉽다. "다른 기기 토큰은 안 지워진다"를 검증할 케이스가 하나 늘 뿐이다                                                |

**#5 AC4**(로그아웃된 토큰으로 갱신 시도 → 거절)가 자연스럽다. 행이 지워졌으므로 `findUnique`가 못 찾는다.

## 안 C · 세션당 행 + 회전 + 재사용 탐지

안 B에 더해, 갱신할 때마다 **새 Refresh 토큰을 발급하고 옛 것을 폐기**한다. 이미 쓴 토큰이 다시 들어오면 탈취로 간주하고 그 사용자의 세션을 전부 끊는다.

```prisma
model RefreshToken {
  id           String    @id @default(cuid())
  userId       String
  tokenHash    String    @unique
  expiresAt    DateTime
  usedAt       DateTime?               // ← 회전으로 폐기된 시각
  replacedById String?                 // ← 이 토큰을 대체한 행
  createdAt    DateTime  @default(now())
  user         User      @relation(fields: [userId], references: [id])

  @@index([userId])
}
```

| 기준            | 내용                                                                                                                                   |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 1 데이터 구조   | 행이 (회원 × 기기 × 갱신횟수)만큼 쌓인다. 15분마다 갱신이면 **14일에 기기당 약 1,300행**. 정리가 필수다                                |
| 2 API 변경지점  | 갱신 경로에 트랜잭션이 필요하다. 옛 행 `usedAt` 기록 + 새 행 생성이 원자적이어야 한다                                                  |
| 3 상태관리      | 해당 없음                                                                                                                              |
| 4 **핵심 동작** | **탈취된 토큰을 탐지한다.** 도둑과 주인이 같은 토큰을 쓰면 둘 중 나중이 재사용으로 걸려 전 세션이 끊긴다                               |
| 5 컴포넌트 구조 | `middleware.ts` 하나                                                                                                                   |
| 6 기존 패턴     | 이력을 쌓는다는 점은 `ADR-AUTH-4`와 맞는다. 다만 트랜잭션이 등장하는 첫 사례라 `signup.service.ts`의 단순함과는 결이 다르다            |
| 7 테스트 용이성 | **가장 어렵다.** 동시 갱신 경합(탭 두 개가 같은 순간 갱신)을 재현해야 하고, 그걸 막을 유예 시간(grace window)까지 설계·테스트해야 한다 |

동시 갱신 경합이 실제 문제인 이유: 탭 두 개가 같은 만료 토큰으로 동시에 갱신하면, 둘 중 하나는 "이미 쓴 토큰"으로 판정되어 **정상 사용자가 강제 로그아웃된다.** 이걸 막으려면 "폐기 후 N초 이내 재사용은 봐준다"는 유예를 넣어야 하고, 그 순간 재사용 탐지의 정확도가 떨어진다.

## 추천: **안 B**

두 가지 이유다.

**첫째, 안 A는 사양과 충돌한다.** `spec-fixed.md` §2.5는 "로그아웃 시 서버에서 삭제"라고만 쓰지만, A를 고르면 *다른 기기에서 로그인하는 것*만으로도 기존 기기가 조용히 로그아웃된다. 동네 일거리 중개 서비스에서 휴대폰으로 공고를 보다 PC에서 이어 보는 흐름이 막히는데, 이건 아무 데도 적혀 있지 않은 제약이다. 사양에 없는 제약을 구조가 만들어내면 나중에 버그로 신고된다.

**둘째, 안 C가 지금 사는 것이 현재 요구와 안 맞는다.** C가 얻는 것은 토큰 탈취 탐지 하나인데, 그 대가로 트랜잭션·유예 시간·동시 갱신 경합이 한꺼번에 들어온다. Access 토큰이 15분이라 탈취 창도 이미 좁다. **B에서 C로 올라가는 건 같은 테이블에 컬럼 두 개를 더하는 일이고, C에서 B로 내려오는 건 그렇지 않다.**

### 이 안을 골랐을 때 감수하는 것

**탈취된 Refresh 토큰이 최대 14일간 유효하다.** 회전이 없으므로 도둑이 토큰을 계속 써도 서버는 정상 갱신과 구분하지 못한다. 사용자가 로그아웃하거나 비밀번호를 재설정해야 끊긴다.

세 가지가 완화 요소이긴 하다 — 토큰이 httpOnly 쿠키라 XSS로 못 빼가고, Access가 15분이라 탈취해도 곧 갱신을 타야 하며, 재설정 시 전량 무효화(#6 AC2)가 탈출구로 있다. 그래도 **탐지는 못 한다**는 사실은 그대로다.

**그리고 만료 행 정리가 숙제로 남는다.** 안 A는 행이 회원 수만큼이라 방치해도 되지만, B는 기기 수만큼 쌓인다. 큰 양은 아니지만 치우는 주체를 정해야 한다 — #39(개인정보 파기 배치)에 얹는 것이 자연스럽다.

### 이 결정을 다시 여는 조건

- 실제 계정 탈취 신고가 관측되면 → **C로 올린다** (`usedAt`·`replacedById` 컬럼 추가 + 유예 설계)
- 관리자가 특정 회원을 즉시 강제 로그아웃해야 하는 요구가 생기면 → B에서 `deleteMany(userId)`로 이미 가능하다. **재검토 불필요**
- "한 계정을 여러 명이 돌려쓴다"는 부정 사용이 문제가 되면 → 동시 세션 수 상한을 B 위에 얹는다 (행 수를 세면 된다). 이것도 A로 되돌아갈 이유는 아니다

## 선택: 안 B (확정 2026-09-01)

**3안 비교가 사실상 불필요했다.** `spec-fixed.md`가 이미 답을 담고 있었다.

- §2.4 "재설정 성공 시 해당 사용자의 **모든** Refresh 토큰 무효화"
- §2.6 "비활성화 시 **모든** Refresh 토큰 삭제"

"모든"이라는 말은 회원당 토큰이 여럿 존재할 때만 의미가 있다. 계정당 하나(안 A)라면 쓸 이유가 없는 단어다. 그리고 회전(안 C)은 사양에도, 이슈 #4·#5·#6의 AC 어디에도 요구가 없다.

**이 비교표는 폐기하지 않고 남긴다.** 나중에 "왜 회전을 안 넣었지"를 물으면 위의 C 항목이 그대로 답한다 — 동시 갱신 경합과 유예 시간의 대가를 알고도 안 산 것이다.

ADR 4요소는 `docs/result/prd/auth-member.md` §3에 옮겨 적었다.
