# ADR-JOB-1 · 버전 이력 저장 구조

> **이 프로젝트 전체에서 가장 중요한 구조 결정.**
> 잘못 고르면 `JobPost`와 `Application` 두 테이블을 동시에 뜯어야 한다.

## 맥락

`spec-fixed.md` §3.4에서 확정된 것:

- 필수항목 6개(`workAddress`, `workStartAt`, `workEndAt`, `rewardPerPerson`, `headcount`, `requiredDescription`)가 바뀌면 `version += 1`
- `Application.appliedVersion`이 스냅샷으로 저장되어, 공고 버전과 다르면 `PENDING_REACCEPT`
- 신청자에게 **변경 전/후 diff**를 보여줘야 한다

정해지지 않은 것: **그 이력을 어떤 모양으로 저장하는가.**

여기서 반드시 답해야 하는 두 질문이 있고, 세 안의 우열이 이 둘에서 갈린다.

1. **diff 표시** — "v2에서 v3로 뭐가 바뀌었나"를 어떻게 뽑는가
2. **계약 복원** — "내가 동의한 v2의 조건이 정확히 무엇이었나"를 어떻게 뽑는가

두 번째가 중요한 이유: `appliedVersion`은 단순한 숫자가 아니라 **그 사람이 동의한 계약 내용**이다. 분쟁이 생기면 "이 사람은 시급 12,000원 조건에 동의했다"를 증명할 수 있어야 한다.

---

## 안 A — 전체 스냅샷 테이블

버전이 오를 때마다 **필수항목 6개 전부**를 한 행으로 남긴다.

```prisma
model JobPostVersion {
  id                  String   @id @default(cuid())
  jobPostId           String
  version             Int

  // 필수항목 6개를 정규 컬럼으로 그대로 복사
  workAddress         String
  workStartAt         DateTime
  workEndAt           DateTime
  rewardPerPerson     Int
  headcount           Int
  requiredDescription String

  createdAt           DateTime @default(now())

  jobPost             JobPost  @relation(fields: [jobPostId], references: [id])

  @@unique([jobPostId, version])
}
```

- v1은 공고 생성 시 함께 만든다. 이후 필수항목이 바뀔 때마다 v2, v3…
- `JobPost` 본체는 항상 **최신 값**을 들고 있다 (조회 성능을 위해)

## 안 B — 변경 필드만 저장 (diff JSON)

바뀐 필드의 before/after만 JSON으로 남긴다.

```prisma
model JobPostChange {
  id        String   @id @default(cuid())
  jobPostId String
  version   Int      // 이 변경으로 도달한 버전
  changes   Json     // { "rewardPerPerson": { "from": 12000, "to": 15000 } }
  createdAt DateTime @default(now())

  @@unique([jobPostId, version])
}
```

- 저장량이 가장 작다
- `changes`는 zod 스키마로 감싸서 타입을 잡는다 (DB는 그냥 `jsonb`)

## 안 C — 이벤트 소싱

공고에 일어난 모든 일을 이벤트로 남기고, 현재 상태는 이벤트를 재생해서 얻는다.

```prisma
model JobPostEvent {
  id         String   @id @default(cuid())
  jobPostId  String
  seq        Int
  type       String   // CREATED | FIELDS_UPDATED | CLOSED | CANCELLED | COMPLETED
  payload    Json
  occurredAt DateTime @default(now())

  @@unique([jobPostId, seq])
}
```

- 버전 이력뿐 아니라 **상태 전이까지** 같은 구조로 담긴다
- 조회 성능을 위해 별도 프로젝션 테이블이 필요해진다

| # | 기준 | 안 A · 전체 스냅샷 | 안 B · diff JSON | 안 C · 이벤트 소싱 |
|---|---|---|---|---|
| 1 | **데이터 구조** | 정규 컬럼 6개 × 버전 수. 스키마가 자기 설명적이라 SQL로 바로 읽힌다 | 행 1개 + `jsonb`. 가장 작지만 DB 레벨 타입 안전성이 없다 | 이벤트 스트림 + 프로젝션. 테이블이 2배가 되고 동기화 책임이 생긴다 |
| 2 | **API 변경지점** | `GET /job-posts/:id/versions/:v` 가 단순 조회 하나 | 특정 버전 전문을 뽑으려면 v1부터 순회 재구성 필요 | 모든 조회 경로에 재생 또는 프로젝션 조회가 끼어든다 |

## 추천: **안 A (전체 스냅샷)**

**결정적 이유는 4번 기준의 "계약 복원"이다.**

안 B는 diff 표시만 놓고 보면 가장 낫다. 하지만 이 서비스에서 `appliedVersion`은 화면에 뭘 그릴지를 정하는 값이 아니라 **그 사람이 동의한 계약 내용**이다. 분쟁이 생겼을 때 "이 구직자는 시급 12,000원, 근무 3시간 조건에 동의했다"를 한 번의 쿼리로 답할 수 있어야 한다.

안 B로 그걸 하려면 v1부터 모든 diff를 순서대로 적용해야 하고, **중간 diff 하나가 잘못 기록되면 그 이후 모든 버전의 복원이 틀어진다.** 돈과 계약이 걸린 데이터에서 이 위험은 저장 공간 절약과 바꿀 만한 것이 아니다.

저장량 걱정은 실제로 크지 않다. 필수항목이 6개로 고정이고, 공고 하나가 수십 번 수정되는 서비스가 아니다. 공고 1건당 평균 2~3버전을 가정하면 추가 저장량은 무시할 수준이다.

안 C는 이 규모에 과하다. 이벤트 소싱은 감사 추적이 제품의 핵심 가치일 때 값을 하는데, 우리에게 필요한 감사 추적은 `JobPostVersion` 하나로 충분히 커버된다.

**안 A를 골랐을 때 감수하는 것:** diff 계산 코드를 직접 써야 한다(두 행 비교). 안 B는 그게 공짜다.

# ADR-JOB-2 · 필수항목 변경 감지 위치

## 맥락

"필수항목 6개가 바뀌면 `version += 1`, 부가항목만 바뀌면 그대로"를 **어디서 판정하는가.**

이 판정이 새면 두 가지 사고가 난다.

- **올려야 하는데 안 올린 경우** — 신청자가 모르는 사이 조건이 바뀐다 (더 위험)
- **안 올려도 되는데 올린 경우** — 오탈자 하나 고쳤다고 지원자 전원이 재동의 대기가 된다

## 세 가지 안

**안 A — 서비스 계층에서 명시적 비교**
`JobPostService.update()` 안에서 기존 값과 새 값을 필드별로 비교한다. `VERSIONED_FIELDS` 상수 배열을 순회.

**안 B — Prisma 확장(`$extends`)에서 가로채기**
`JobPost` update 쿼리를 확장으로 가로채 자동으로 version을 올린다. 서비스 코드는 version을 몰라도 된다.

**안 C — DB 트리거**
Postgres 트리거로 UPDATE 시 필수항목 변화를 감지해 version을 증가시킨다.

## 7가지 기준 비교

| # | 기준 | 안 A · 서비스 계층 | 안 B · Prisma 확장 | 안 C · DB 트리거 |
|---|---|---|---|---|
| 1 | 데이터 구조 | 변화 없음 | 변화 없음 | 트리거 함수가 마이그레이션에 들어간다 |
| 2 | API 변경지점 | `update()`에 비교 로직 20줄쯤 추가 | 서비스는 그대로. 확장 설정 파일이 하나 생김 | 서비스도 확장도 그대로 |
| 3 | 상태관리 | 해당 없음 (서버 전용) | 해당 없음 | 해당 없음 |
| 4 | **핵심 동작**<br>누락 없는 판정 | 코드에 다 보인다. 필드 추가 시 상수 배열에 넣는 것을 잊을 수 있다 | 모든 update가 자동으로 지나가므로 **누락이 구조적으로 불가능** | 트리거가 확실히 잡는다. 앱을 우회한 SQL도 잡힌다 |
| 5 | 컴포넌트 구조 | 해당 없음 | 해당 없음 | 해당 없음 |
| 6 | 기존 패턴 일관성 | ✅ `health.controller.ts`처럼 로직이 서비스에 드러나 있다 | 🟡 저장소에 Prisma 확장 사용 전례가 없다 | ❌ 로직이 TypeScript 밖으로 나간다 |
| 7 | 테스트 용이성 | ✅ 순수 함수로 뽑으면 DB 없이 단위 테스트 가능 | 🟡 확장을 태워야 하므로 통합 테스트 필요 | ❌ Testcontainers 없이는 검증 불가. 트리거 디버깅이 어렵다 |

## 추천: **안 A (서비스 계층)**

안 B의 "누락이 구조적으로 불가능"은 매력적이지만, **버전 증가는 부수 효과가 큰 동작**이다. 지원자 전원을 `PENDING_REACCEPT`로 내리고 알림을 보낸다. 이런 동작이 update 호출에 암묵적으로 따라붙으면, 나중에 "왜 지원자가 전부 재동의 대기가 됐지?"를 추적하기 어려워진다.

안 A의 누락 위험은 **테스트로 막는다.** `issues.md` #15에 이미 AC가 있다.

> "필수항목 6개 각각, 하나씩 고치면 매번 version이 오른다"

이 테스트가 6개 필드를 전부 돈다.

안 C는 `planner.md`가 TypeScript를 고른 이유("AI에게 맡길 때 타입 오류로 절반을 거른다")와 정면으로 어긋난다. 로직이 타입 시스템 밖으로 나가면 그 이점을 잃는다.

**안 A를 골랐을 때 감수하는 것:** 필수항목을 7번째로 추가할 때 상수 배열을 갱신해야 한다는 것을 사람이 기억해야 한다.

# ADR-JOB-3 · 공고 상태 전이 관리 방식

## 맥락

상태 6개(`DRAFT`/`OPEN`/`CLOSED`/`COMPLETED`/`CANCELLED`/`EXPIRED`)이고, 전이 조건에 **시간·인원·포인트**가 얽힌다. `OPEN → CLOSED`는 정원 충족 또는 시작 시각 도달이고, `OPEN → CANCELLED`는 포인트 `RELEASE`를 동반한다.

## 세 가지 안

**안 A — 상태 컬럼 + 서비스 메서드별 분기**
`cancel()`, `close()`, `complete()` 각 메서드가 자기 전제 조건을 직접 검사한다.

**안 B — 전이 테이블 + 공용 `transition()` 함수**
`{ from, to, guard }` 목록을 상수로 두고, 모든 전이가 한 함수를 통과한다.

**안 C — 상태머신 라이브러리 (XState 등)**

## 7가지 기준 비교

| # | 기준 | 안 A · 메서드별 분기 | 안 B · 전이 테이블 | 안 C · 라이브러리 |
|---|---|---|---|---|
| 1 | 데이터 구조 | `status` enum 컬럼 하나 | 동일 + 전이 정의 상수 | 동일 + 머신 정의 |
| 2 | API 변경지점 | 메서드마다 검사 코드 반복 | 각 메서드가 `transition()` 한 줄 호출 | 액터 생성·전이 발송 코드 |
| 3 | 상태관리 | 프론트는 `status` 문자열만 받음 | 동일 | 동일 (서버 전용으로 쓸 경우) |
| 4 | **핵심 동작**<br>잘못된 전이 차단 | 각 메서드를 다 봐야 전체 규칙을 안다. 새 상태 추가 시 빠뜨리기 쉽다 | **허용된 전이가 한 곳에 표로 있다.** 표에 없으면 자동 거부 | 가장 엄격하지만 우리 요구를 넘어선다 |
| 5 | 컴포넌트 구조 | 해당 없음 | 해당 없음 | 해당 없음 |
| 6 | 기존 패턴 일관성 | ✅ 지금 코드가 이 스타일 | ✅ `packages/shared`에 상수를 두는 방식과 잘 맞는다 | ❌ 의존성 추가. 2인 팀에 학습 비용 |
| 7 | 테스트 용이성 | 🟡 메서드 단위 테스트를 6개 상태 × 조건만큼 | ✅ **전이 표 자체를 테이블 테스트로** 한 번에 검증 | 🟡 라이브러리 실행 컨텍스트 필요 |

## 추천: **안 B (전이 테이블)**

상태가 6개면 가능한 전이 조합은 30개다. 안 A는 그중 허용된 것만 코드 여기저기에 흩어놓기 때문에, **"지금 어떤 전이가 허용되는가"를 한눈에 볼 수 없다.** 새 상태를 추가할 때 빠뜨리는 곳이 생긴다.

안 B는 전이 표를 `packages/shared`에 상수로 두고, `Application`의 상태머신(10개 상태)도 같은 패턴으로 재사용할 수 있다. **`ADR-APP-4`가 같은 문제를 다루므로 여기서 정한 방식이 그쪽에도 적용된다.**

안 C는 XState가 잘 만든 도구지만, 우리 전이는 조건이 단순하고 병렬 상태나 계층 상태가 없다. 의존성과 학습 비용을 낼 만큼의 이득이 없다.

**안 B를 골랐을 때 감수하는 것:** 전이 하나를 추가할 때 표와 guard 함수 두 곳을 손대야 한다. 안 A는 메서드 하나만 고치면 된다.

# ADR-JOB-4 · `FilterableList` 검색·필터 상태 관리

> **이 결정은 화면 7개에 영향을 준다.** 사용자 공고 목록 1개 + 관리자 목록 6개
> (회원, 블랙리스트, 환전 요청, 공고 관리, 포인트 내역, 감사 로그)

## 맥락

`spec-fixed.md` §11.2에서 확정된 요구:

- 이름 부분 일치 검색 (디바운스 300ms)
- 필터: 주소지(시/도 → 시/군/구), 카테고리, 상태, 기간
- 검색어와 필터는 AND 조합, 적용된 필터는 **칩으로 표시하고 개별 해제**
- **새로고침·공유해도 유지** (URL 쿼리스트링)
- 서버 사이드 페이징

## 세 가지 안

**안 A — URL 쿼리스트링이 단일 진실**
`useSearchParams()`로 읽고, 필터를 바꾸면 `router.replace()`로 URL을 갱신한다. 컴포넌트는 로컬 상태를 갖지 않는다.

**안 B — 로컬 상태 + URL 동기화**
`useState`로 필터를 들고, `useEffect`로 URL에 반영한다.

**안 C — 서버 상태 라이브러리 (TanStack Query 등)**
쿼리 키에 필터를 넣고 캐싱·리페치를 라이브러리에 맡긴다.

## 7가지 기준 비교

| # | 기준 | 안 A · URL 단일 진실 | 안 B · 로컬 + 동기화 | 안 C · 서버 상태 라이브러리 |
|---|---|---|---|---|
| 1 | 데이터 구조 | 쿼리 파라미터 스키마 하나 (zod) | 동일 + 클라 상태 타입 | 동일 + 쿼리 키 구조 |
| 2 | API 변경지점 | 목록 API가 쿼리 파라미터를 zod로 파싱 — 셋 다 동일 | 동일 | 동일 |
| 3 | **상태관리 변경지점** | **추가 상태 없음.** URL이 곧 상태 | `useState` + `useEffect` 동기화 코드가 목록마다 | `QueryClientProvider` 전역 설정 + 쿼리 키 관리 |
| 4 | **핵심 동작**<br>새로고침·공유 후 유지 | ✅ 구조적으로 보장. URL이 진실이니 어긋날 수가 없다 | 🟡 초기 마운트 시 URL→상태 복원 코드가 따로 필요하고, 뒤로가기에서 자주 어긋난다 | 🟡 캐싱은 좋지만 URL 유지는 별도로 구현해야 함 |
| 5 | 컴포넌트 구조 | `FilterableList` + `FilterChips` + `Pagination`. 전부 URL만 읽는 무상태 컴포넌트 | 동일하나 각 컴포넌트가 상태와 setter를 props로 받음 | 동일 + 쿼리 훅 |
| 6 | 기존 패턴 일관성 | ✅ Next.js App Router의 기본 방식. 서버 컴포넌트에서 `searchParams`를 그대로 받을 수 있다 | 🟡 클라이언트 컴포넌트를 강제한다 | ❌ 의존성 추가. 저장소에 전례 없음 |
| 7 | 테스트 용이성 | ✅ E2E가 URL만 검증하면 됨. "필터 걸고 새로고침하면 유지"가 그대로 테스트 | 🟡 상태와 URL 두 곳을 봐야 함 | 🟡 QueryClient 목킹 필요 |

## 추천: **안 A (URL 단일 진실)**

`issues.md` #13의 AC가 이걸 그대로 요구한다.

> "필터 적용 상태에서 새로고침하면 필터가 유지된다"
> "필터 칩 하나를 지우면 그 조건만 풀리고 나머지는 유지된다"

안 B는 상태가 두 곳(로컬, URL)에 있어서 **둘이 어긋나는 순간이 반드시 생긴다.** 특히 뒤로가기에서 URL은 바뀌었는데 로컬 상태가 그대로인 경우가 흔하다.

안 A는 진실이 한 곳뿐이라 이 버그 종류 자체가 존재하지 않는다. 그리고 Next.js App Router에서는 서버 컴포넌트가 `searchParams`를 직접 받으므로, 목록 조회를 서버에서 해서 초기 로딩도 빨라진다.

안 C의 캐싱은 관리자 화면에서 값을 하겠지만, 지금 필요한 건 "필터 걸고 조회"뿐이다. 캐싱이 아쉬워지면 그때 안 A 위에 얹을 수 있다 — **안 A는 안 C를 막지 않는다.**

**안 A를 골랐을 때 감수하는 것:** 필터를 바꿀 때마다 URL이 바뀌므로 라우팅이 발생한다. 타이핑 검색은 디바운스로 눌러야 하고, 안 눌러두면 글자마다 요청이 나간다.

# ADR-JOB-5 · 목록 조회 쿼리·인덱스 전략

## 맥락

필터 조합이 6개(카테고리, 시/도, 시/군/구, 상태, 기간, 검색어)다. **어떤 데이터 규모를 전제로 설계하는가**를 먼저 못 박아야 인덱스를 정할 수 있다.

**전제 규모 (MVP 1년):** 공고 누적 10만 건 이하, 활성(`OPEN`) 공고 1천 건 이하, 회원 1만 명 이하.
**이 전제가 틀리면 이 ADR을 다시 연다.**

## 세 가지 안

**안 A — 복합 인덱스 + 오프셋 페이징**
자주 쓰는 필터 조합에 복합 인덱스를 걸고, `LIMIT/OFFSET`으로 페이징한다.

**안 B — 키셋(커서) 페이징**
`WHERE (createdAt, id) < (?, ?)` 방식. 깊은 페이지에서도 성능이 일정하다.

**안 C — 검색 전용 인덱스(`pg_trgm` GIN) 선제 도입**
처음부터 부분 일치 검색용 GIN 인덱스를 건다.

## 7가지 기준 비교

| # | 기준 | 안 A · 복합 인덱스 + 오프셋 | 안 B · 키셋 페이징 | 안 C · pg_trgm 선제 도입 |
|---|---|---|---|---|
| 1 | 데이터 구조 | 인덱스 2~3개 추가 | 동일 + 커서 정렬 키 확정 필요 | 확장 설치 + GIN 인덱스 |
| 2 | API 변경지점 | `page`, `size` 파라미터 | `cursor`, `size` 파라미터 | 검색 쿼리만 바뀜 |
| 3 | 상태관리 | 페이지 번호가 URL에 (ADR-JOB-4와 맞물림) | 커서가 URL에 — **"3페이지로 바로 가기"가 불가능** | 해당 없음 |
| 4 | **핵심 동작**<br>필터 조합 조회 | 전제 규모에서 충분. `EXPLAIN`으로 인덱스를 타는지 확인 | 동일하나 무한스크롤에 더 맞다 | 검색만 빨라지고 필터는 그대로 |
| 5 | 컴포넌트 구조 | `Pagination` (페이지 번호) | `LoadMore` 또는 무한스크롤 | 변화 없음 |
| 6 | 기존 패턴 일관성 | ✅ **관리자 화면은 전체 건수 표시가 필요**하므로 오프셋이 맞다 | 🟡 관리자 목록에서 "총 152건"을 못 보여준다 | 🟡 지금 전례 없음 |
| 7 | 테스트 용이성 | ✅ "21건 중 2페이지에 1건" 같은 AC(#13)를 그대로 테스트 | 🟡 커서 경계 테스트가 까다롭다 | ✅ 인덱스 유무는 테스트 대상이 아님 |

## 추천: **안 A (복합 인덱스 + 오프셋)**, `pg_trgm`은 보류

관리자 목록 6개가 전부 **"총 몇 건"을 표시해야 한다.** 키셋 페이징은 전체 건수를 셀 수 없어서 이 요구와 맞지 않는다. 오프셋의 약점인 "깊은 페이지 느려짐"은 활성 공고 1천 건 전제에서는 발생하지 않는다.

`pg_trgm`은 **지금 넣지 않는다.** 회원 1만 명 규모에서 `LIKE '%김%'`은 순차 스캔으로도 수십 밀리초다. 필요해지면 인덱스만 추가하면 되고 **쿼리 코드를 고칠 필요가 없다** — 지금 도입하지 않는 것이 나중을 막지 않는다.

**걸 인덱스 (초안):**

```sql
-- 사용자 목록: 활성 공고를 지역·카테고리로 거르고 최신순
CREATE INDEX idx_jobpost_open_list
  ON "JobPost" (status, sido, sigungu, "categoryId", "createdAt" DESC)
  WHERE "deletedAt" IS NULL;

-- 관리자 목록: 상태 무관, 등록일 범위
CREATE INDEX idx_jobpost_admin_list
  ON "JobPost" ("createdAt" DESC, status);

-- 내 공고
CREATE INDEX idx_jobpost_poster
  ON "JobPost" ("posterId", "createdAt" DESC);
```

> 인덱스는 확정이 아니라 **초안**이다. Green 단계에서 `EXPLAIN`으로 실제로 타는지 확인하고 조정한다.

**안 A를 골랐을 때 감수하는 것:** 데이터가 전제를 크게 넘으면(활성 공고 수만 건) 깊은 페이지가 느려진다. 그때 키셋으로 바꾸려면 API 파라미터와 페이징 컴포넌트를 함께 고쳐야 한다.
