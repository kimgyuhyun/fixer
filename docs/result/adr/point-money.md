# ADR-PAY-7 · 환불은 오래된 결제 건부터 소진한다

## Context

구인자는 미리 충전하고 그 잔액으로 공고를 올린다(`spec-fixed.md` §6.3). 그래서 **잔액과 결제 건이 1:1이 아니다** — 여러 번 충전한 잔액이 하나로 섞여 있고, 그 중 일부를 환불해야 하는 상황이 생긴다.

문제는 환불이 "잔액을 줄이는 일"이 아니라는 데 있다. **환불은 특정 카드 결제 건을 취소하는 것**이라, 어느 `paymentId`에 얼마를 취소할지 반드시 정해야 한다. 카드로 들어온 돈은 그 카드로만 돌아간다.

실제 상황:

```
50,000원 결제  (오래된 것)
150,000원 결제
─────────────────────────
잔액 65,000  →  사용자가 55,000 환불 요청

어느 결제 건을 얼마나 취소하나?
```

여기에 두 가지가 더 얽힌다.

- **카드 결제 취소에는 기한이 있다.** 원거래로부터 일정 기간이 지나면 PG·카드사가 취소를 받지 않는다. 그 기간은 계약에 따라 달라 지금 확정할 수 없다.
- **근로자 지급은 기한이 없다.** 그 돈은 이미 우리 계좌에 들어와 있고, 지급은 카드 취소가 아니라 우리 자금에서 나가는 계좌 이체다. 카드 기한과 무관하다.

## Decision

**환불은 남은 결제 건 중 `createdAt`이 가장 오래된 것부터 소진한다 (FIFO).** 잠금(`HOLD`)과 지급(`PAYOUT`)도 같은 순서로 소진한다.

위 예시는 이렇게 처리된다.

```
잔액 65,000 = lot1 잔여 + lot2 잔여   (소비도 FIFO였으므로 오래된 것이 먼저 비어 있다)

55,000 환불 요청
  → 오래된 lot부터 전액 취소, 마지막 lot만 부분취소로 끝수를 맞춘다
  → 예: lot1에 50,000이 남아 있었다면 전액 취소 + lot2에서 5,000 부분취소
```

함께 정한 것 넷.

| 항목          | 결정                                                                                                                                         |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **부분환불**  | 허용한다. 마지막 lot에서 끝수를 맞추는 데 필요하다                                                                                           |
| **소진 순서** | 환불·잠금·지급 **모두 FIFO** (오래된 `createdAt` 먼저)                                                                                       |
| **lot 잔여**  | 컬럼으로 두지 않는다. **원장에서 계산한다** — 원장 행이 `sourcePaymentId`를 참조한다                                                         |
| **취소 기한** | `Payment.refundableUntil` 컬럼을 **지금 만들어 두고 값은 비운다.** 실제 기간은 PG 계약 시 확인한다. 기한이 지난 lot은 FIFO 순서에서 건너뛴다 |

**근로자 지급에는 기한을 두지 않는다.** 우리가 이미 들고 있는 돈에서 나가므로 카드 취소 기한과 무관하다. `refundableUntil`은 환불 경로에서만 본다.

### 왜 FIFO인가 — 취향이 아니다

**카드 취소 기한이 오래된 건부터 먼저 만료된다.** 오래된 것을 먼저 쓰면 기한이 임박한 것을 먼저 소진하는 셈이라, 취소 불가로 굳는 금액이 최소가 된다.

최신 것부터 쓰면(LIFO) 오래된 건이 잔액에 계속 남아 있다가 기한이 지나 **환불할 수 없는 잔액**이 된다. 사용자에게는 "잔액은 있는데 환불이 안 되는" 상태로 보인다.

## Alternatives

**기각 1 — 부분환불 금지 (결제 건은 `PAY` 또는 `REFUND` 둘 중 하나)**

가장 단순하다. lot 잔여를 추적할 필요가 아예 없다. 그러나 **"5만원 충전 후 2만원만 환불"이 불가능해진다.** 그걸 하려면 5만원을 전액 취소하고 3만원을 재충전해야 하는데, 카드 취소가 며칠 걸리는 동안 잔액이 0이라 공고를 올릴 수 없다. 충전을 1,000원 단위 여러 건으로 쪼개는 방법은 카드 수수료가 건당 붙어 성립하지 않는다.

**기각 2 — 소비는 lot을 건드리지 않고 환불만 lot에서 뽑는다**

예시 숫자가 직관적으로 나온다. 그러나 **lot 잔여 합계와 실제 잔액이 영구히 어긋난다.**

```
lot1 50,000 + lot2 150,000 = 200,000
135,000 소비 (lot 무관)
→ 실제 잔액 65,000, lot 잔여 합계는 여전히 200,000
```

환불할 때 `min(잔액, lot 잔여)`로 막으면 사고는 안 나지만, **"얼마 환불 가능?"에 답이 두 개 나온다.** 돈에서 숫자가 두 벌이면 어긋났을 때 어느 쪽이 맞는지 판단할 근거가 없다. `spec-fixed.md` §6.1이 "진실의 원천은 항상 원장"이라고 못박은 것과 정면으로 어긋난다.

**기각 3 — 충전을 없애고 공고 등록 시 그 금액만 결제한다**

이 ADR이 통째로 필요 없어지는 안이다. 결제 건이 공고와 1:1이 되므로 FIFO도, lot 추적도, `HOLD`도, 잔액 관리도 사라진다. 공고를 취소하면 그 공고의 결제를 취소하면 끝이다. 배달앱이 이 방식이다.

기각한 이유는 **사양이 충전으로 정해져 있고**(§6.3, 이슈 #28), 공고를 반복해서 올리는 구인자가 매번 카드를 꺼내는 마찰이 크다고 판단했기 때문이다. 결제가 실패하면 공고 등록 자체가 막히는 것도 부담이다.

**다만 이 기각은 지금이 마지막 기회였다.** 구현이 시작되면 되돌리는 비용이 커진다. 김규현이 이견이 있다면 여기가 가장 중요한 지점이다.

## Consequences

**좋아지는 것**

- 환불이 카드 취소 기한과 맞물려 돌아간다. 취소 불가로 굳는 금액이 최소가 된다
- 숫자가 한 벌이다. lot 잔여도 잔액도 원장에서 나오므로 어긋날 자리가 없다
- `refundableUntil` 자리를 미리 만들어 두므로 실결제 전환 시 스키마를 뜯지 않는다

**감수하는 것**

- **환불 한 번에 카드 취소가 여러 번 나갈 수 있다.** 55,000 환불이 lot 두 개에 걸치면 PG 호출이 두 번이다. 중간에 하나가 실패하면 부분만 취소된 상태가 되므로, **환불을 여러 취소의 묶음으로 다루고 각 취소의 성공·실패를 개별 기록**해야 한다. 한 번에 다 되거나 다 안 되게 만들 수는 없다 — 카드사 호출을 되돌릴 방법이 없기 때문이다
- **lot 잔여를 원장에서 계산하므로 조회가 무겁다.** `sourcePaymentId` 인덱스가 필요하고, 결제 건이 많은 구인자는 환불 화면이 느려질 수 있다. `cachedBalance`와 같은 방식의 캐시가 필요해지면 `ADR-PAY-1`에서 함께 다룬다
- **기한이 지난 lot이 잔액에 남는다.** 사용자에게는 "잔액은 있는데 환불이 안 되는" 금액이 생긴다. 화면에서 그 사실을 알려줘야 하고, 그 금액을 어떻게 정리할지(관리자 수동 이체 등)는 실결제 전환 시 정한다

**이 결정을 다시 여는 조건**

- **김규현이 이견을 내면** — PRD가 공동 결정으로 정해 둔 도메인이다
- 실결제 전환 후 카드 취소 기한이 예상보다 짧아 "환불 불가 잔액"이 자주 생기면 → 충전 상한을 두거나 기각 3(공고별 결제)을 재검토한다
- 구인자 한 명의 결제 건이 수백 건 단위로 쌓여 환불 화면이 느려지면 → lot 스냅샷을 도입한다

PRD §3의 6건은 그대로 남아 있다. 성격을 나눠 두면 다음에 누가 봐도 어디서 시작할지 안다.

| `ADR-PAY-6` 계좌번호 암호화                | **사람 판단 필요** | 관리자가 계좌를 열람하는 흐름이 달라진다. 키를 누가 들고 있을지가 운영 문제다                                          |

**기술 판단 4건(`1`·`2`·`3`·`5`)을 2026-09-03에 확정했다.** 넷 다 사양이 방향을 잡아 둔 것을 따랐고, 기각한 안과 이유는 PRD §3에 적었다. 관통하는 원칙은 하나다 — **진실을 한 곳에 두고, 추가 인프라를 들이지 않는다.**

**`ADR-PAY-6`은 여전히 미결이다.** 계좌번호 암호화 키를 누가 어디에 보관하느냐는 기술 선택이 아니라 운영 책임 문제다. 키를 잃으면 계좌를 전부 못 읽고, 털리면 계좌가 전부 샌다. **이슈 #30(계좌 등록·검증)이 여기서 막혀 있다.**

`ADR-PAY-4`의 트랜잭션 경계도 남았다. 시점(공고 `OPEN` → `HOLD`, 확인 → `PAYOUT`, 분쟁 → `REJECT`)은 정했으나, 공고 완료 처리와 원장 쓰기를 한 트랜잭션에 묶을지는 #23(B 몫)을 만들 때 정하는 편이 낫다 — 그 코드를 보면서 정해야 하는 문제다.
