## 0. 용어 정의 (Ubiquitous Language)

코드·DB·문서·대화에서 아래 단어만 사용한다. 동의어 사용 금지.

| 용어 | 코드 식별자 | 정의 |
|---|---|---|
| 회원 | `User` | 서비스 가입자. 역할 구분 없이 단일 엔티티 |
| 구인자 | `poster` | 공고를 등록한 `User`. 별도 테이블 아님, 관계상의 역할 |
| 구직자 | `worker` | 공고에 신청한 `User`. 별도 테이블 아님, 관계상의 역할 |
| 공고 | `JobPost` | 일거리 게시물 |
| 공고 버전 | `JobPost.version` | 필수항목 수정 시 +1 되는 정수 |
| 필수항목 | *(개념)* | 주소·금액·근무시간·필수 일거리 내용. 이것만 버전을 올린다 |
| 신청 | `Application` | 구직자가 공고에 지원한 기록 |
| 수락 | `ACCEPTED` | 구인자가 신청을 승인한 것. 이 순간이 **계약 체결** |
| 확정 인원 | `acceptedCount` | 상태가 `ACCEPTED` 이상인 신청 수 |
| 재동의 | `PENDING_REACCEPT` | 공고 버전이 올라 신청자의 재확인이 필요한 상태 |
| 무상 취소 창 | *(개념)* | 수락 시각 +2시간. 이 안의 취소는 무패널티 |
| 경고 | `Penalty` | 노쇼·당일취소 등으로 쌓이는 제재 기록 1건 |
| 제재 | `Suspension` | 경고 누적으로 발생한 이용 제한 (5일) |
| 포인트 | `Point` | 서비스 내부 화폐. 1포인트 = 1원 |
| 원장 | `PointTransaction` | 포인트 증감 내역. 잔액은 원장의 합 |
| 잠금 | `HOLD` | 공고 등록 시 예산을 묶어두는 원장 유형 |
| 반환 | `RELEASE` | 미체결분 잠금을 되돌리는 원장 유형 |
| 지급 | `PAYOUT` | 업무 완료 확인 시 구직자에게 넘어가는 원장 유형 |
| 환전 | `Exchange` | 지급된 포인트를 실제 현금으로 바꾸는 절차 |
| 환전 요청 | `ExchangeRequest` | 사용자가 환전을 요청한 기록 |
| 평점 | `Rating` | 거래 후 남기는 별점 (1~5) |
| 동의서 | `Agreement` | 서명이 병합된 PDF 및 그 메타데이터 |
| 관리자 | `role = ADMIN` | 별도 테이블 아님. `User.role`로 구분 |
| 블랙리스트 | *(개념)* | **자동 제재된 회원의 목록**. 별도 테이블 아니며 `Suspension` 조회의 다른 이름 |
| 제재 해제 | `releasedAt` | 관리자가 `Suspension`을 만료 전에 조기 종료한 것 |
| 비활성화 | `deactivatedAt` | 탈퇴한 회원. 소프트 삭제 상태 |

**금지어:** "게시글/구인글"(→ 공고), "매칭/체결"(→ 수락), "차감"(→ 잠금 또는 지급), "캐시/코인"(→ 포인트), "탈퇴/삭제 회원"(→ 비활성화 회원), **"정산/출금"(→ 환전)**.

> **지급과 환전은 다른 것이다.** 지급(`PAYOUT`)은 업무 완료 시 구인자 포인트가 구직자 포인트로 넘어가는 것이고, 환전(`Exchange`)은 그 포인트를 현금으로 바꿔 계좌로 받는 것이다. 둘을 섞어 쓰지 않는다.

## 2. 회원 / 인증

### 2.1 역할 모델
- **단일 계정 겸용.** `User` 하나로 구인·구직 모두 수행.
- 평점은 **역할별로 분리 집계**한다: `ratingAsPoster`, `ratingAsWorker`. 같은 사람이라도 "고용주로서"와 "일꾼으로서"의 신뢰도는 별개.

### 2.2 회원가입 흐름
1. 이메일 입력 → **6자리 난수 코드** 발송 (유효 10분, 재발송 60초 쿨다운, 시간당 5회 제한)
2. 코드 검증
3. 비밀번호 설정 (bcrypt cost 12)
4. 주소 입력 — 카카오 우편번호 팝업 → 도로명주소·지번·우편번호 저장, 카카오 로컬로 `lat`/`lng` 변환 저장
5. 동의서 PDF 표시 → 서명 캔버스 → 동의
6. `Agreement` 생성 후 가입 완료

### 2.3 동의서 / 전자서명
- `pdf-lib`로 템플릿 PDF에 서명 PNG를 병합.
- **병합된 최종 PDF만 저장한다.** 원본 서명 PNG는 병합 직후 폐기 (재사용·위조 위험 차단).
- DB에는 `filePath`(상대경로), `sha256`, `agreedAt`, `templateVersion`, `ip`, `userAgent` 기록.
- 저장 위치는 **배포 디렉토리 밖의 별도 볼륨**. 환경변수 `AGREEMENT_STORAGE_PATH`로 주입. DB에는 절대경로 저장 금지.
- 동의서 템플릿이 개정되면 `templateVersion`을 올리고 기존 동의서는 그대로 보존.

### 2.4 비밀번호 정책
- 마이페이지 내 "비밀번호 변경" 메뉴 **없음**.
- 로그인 화면 "비밀번호 찾기" → 이메일 인증 토큰(유효 30분, 1회용) → 재설정 허용.
- 재설정 성공 시 해당 사용자의 **모든 Refresh 토큰 무효화**.

### 2.5 로그인 / 로그아웃
- Access 토큰: JWT, 15분, httpOnly + Secure + SameSite=Lax 쿠키.
- Refresh 토큰: 14일, DB(`RefreshToken` 테이블)에 해시 저장. 로그아웃 시 서버에서 삭제.
- **"로그아웃 후 뒤로가기로 로그인 전용 페이지가 보이면 안 된다"** 요구 구현:
  - Next.js `middleware.ts`에서 쿠키 검사 → 미인증이면 서버 단 리다이렉트 (클라이언트 JS 우회 불가)
  - 보호 페이지 응답에 `Cache-Control: no-store, must-revalidate` 헤더 부착 (bfcache 방지)
  - 로그아웃 시 클라이언트 라우터 캐시 무효화

### 2.6 탈퇴 / 비활성화 (개인정보 파기 정책)

**물리 삭제하지 않는다.** 소프트 삭제로 비활성화한다.

- `User.deactivatedAt` 기록 → **로그인 불가**. 로그인 시도 시 "비활성화된 계정" 안내
- 관리자 회원 목록에는 **"비활성화" 배지**로 표시되어 계속 보인다 (분쟁·환전 이력 추적)
- 비활성화 시 모든 Refresh 토큰 삭제, 진행 중이 아닌 신청은 전부 `WITHDRAWN`

**탈퇴 보류 조건 — 아래 중 하나라도 해당하면 탈퇴를 막는다:**

| 조건 | 안내 문구 |
|---|---|
| 진행 중 계약 존재 (`ACCEPTED` 또는 공고 `CLOSED` 상태의 신청) | "진행 중인 일거리가 끝난 뒤 탈퇴할 수 있습니다" |
| `OPEN`/`CLOSED` 상태의 본인 공고 존재 | "등록한 공고를 마감한 뒤 탈퇴할 수 있습니다" |
| 포인트 잔액 > 0 | "남은 포인트를 환전한 뒤 탈퇴할 수 있습니다" |

> 근거: 돈이 묶인 채 계정이 잠기는 사고와, 탈퇴자가 약속한 일에 안 나오는 사고를 동시에 막는다. 잔액 소멸 방식은 실수 탈퇴 시 CS·분쟁 위험이 커서 기각.

**재가입 = 재활성화.** 비활성화 계정의 이메일로 가입을 시도하면 새 계정을 만들지 않고 "재활성화하시겠습니까?"로 안내한다.
- 이메일 유니크 제약을 그대로 유지할 수 있다
- **평점·경고 이력이 그대로 승계**되어, 경고를 4회 쌓은 사람이 탈퇴·재가입으로 이력을 세탁하는 것을 막는다
- 재활성화 시 이메일 인증을 다시 거친다

### 2.7 보관 / 파기 기간

**원칙: 법정 보관 의무가 있는 것은 법정 기간을 지키고, 그 외 개인정보는 비활성화 후 4개월에 파기한다.**

**보관 기간 상수 (MVP 적용값)** — `packages/shared/src/retention.ts` 한 곳에 모은다.

| 대상 | 상수 | 값 |
|---|---|---|
| 이름, 연락처, 주소, 계좌 정보, 서명 동의서 PDF | `RETENTION_PERSONAL_INFO` | **비활성화 후 4개월** |
| 계약·청약철회 기록 (공고, 신청, 수락/취소 이력) | `RETENTION_CONTRACT` | 5년 |
| 대금결제·재화공급 기록 (포인트 원장, 결제, 환전) | `RETENTION_PAYMENT` | 5년 |
| 소비자 불만·분쟁 처리 기록 (`Penalty`, `Suspension`, `AdminAuditLog`) | `RETENTION_DISPUTE` | 3년 |

- 파기는 **컬럼 단위 비식별 처리**로 수행한다. 행을 지우면 위 법정 보관 대상 기록의 FK가 깨진다.
  - 예: `name` → `"탈퇴회원"`, `email` → `deleted_{userId}@invalid`, `address`/`phone` → `NULL`, 계좌 정보 → 삭제, 동의서 PDF 파일 → 삭제 후 해시만 보존
- **파기된 계정은 재활성화할 수 없다.** 4개월 안에 돌아오면 재활성화, 이후는 신규 가입이다 (§2.6과 연결).
- 파기 배치는 일 1회 실행하며 advisory lock을 건다 (§8.2).

> 위 연수는 **테스트·개발용 적용값**이다. 실서비스 오픈 시 법정 기준으로 재확인하되, 값이 상수 한 곳에 모여 있어 **숫자만 바꾸면 끝난다.** 파기 로직·배치·스키마는 영향받지 않는다.
>
> 테스트에서는 상수를 주입해 짧은 값(분 단위)으로 바꿔 파기 배치를 검증한다. 상수를 코드 여기저기 흩어두지 않는 이유가 이것이다.

## 3. 공고 (JobPost)

### 3.1 카테고리
- `Category` 테이블로 관리 + Prisma seed로 초기값 주입.
- 컬럼: `name`, `slug`, `sortOrder`, `placeholderText`, `isActive`.
- `placeholderText`가 planner.md의 "카테고리별 유의사항 플레이스홀더"를 담당. 문구 수정에 재배포 불필요.
- 공고는 `categoryId` FK 참조.

### 3.2 필수 입력
- 카테고리, 제목, 근무 주소, 근무 시작/종료 일시, 모집 인원, 1인당 보상금(포인트), 상세 내용
- 자동 기록: `version`(기본 1), `createdAt`, `updatedAt`
- 근무 주소는 기본값이 가입 주소이되, **추가 주소 등록/선택 가능** (`UserAddress` 테이블, 라벨 지정)

### 3.3 상태머신

```
DRAFT ──▶ OPEN ──┬──▶ CLOSED ──▶ COMPLETED
                 ├──▶ CANCELLED
                 └──▶ EXPIRED
```

| 상태 | 의미 |
|---|---|
| `DRAFT` | 작성 중 (포인트 잠금 전) |
| `OPEN` | 모집 중. 포인트 `HOLD` 완료 |
| `CLOSED` | 모집 마감 (정원 충족 또는 시작 시각 도달) |
| `COMPLETED` | 업무 완료 확인됨. `PAYOUT` 실행됨 |
| `CANCELLED` | 구인자 취소 |
| `EXPIRED` | 미달 상태로 시작 시각 경과 |

- **물리 삭제 없음.** `deletedAt` 소프트 삭제 + 상태 관리.
- 삭제 가능 조건(planner.md): 신청자 0명 → 즉시 `CANCELLED` 가능. 수락자 존재 시 → 취소 시 경고 스택 누적.

### 3.4 버전 정책 (planner.md 미정의 항목 — 여기서 확정)

**버전을 올리는 필드 (필수항목):**
`workAddress`, `workStartAt`, `workEndAt`, `rewardPerPerson`, `headcount`, `requiredDescription`

**버전을 올리지 않는 필드:**
`title`, 부가 설명, 이미지, 연락 참고사항 등

**충돌 처리 흐름:**
1. `Application`은 생성 시 `appliedVersion`을 스냅샷으로 저장한다.
2. 공고의 필수항목이 수정되면 `version += 1`, 그리고 `JobPostVersion` 이력 테이블에 변경 전 스냅샷을 남긴다.
3. `appliedVersion < jobPost.version`인 모든 신청은 상태가 `PENDING_REACCEPT`로 전환된다. **신청 자체는 삭제되지 않는다.**
4. 신청자에게 알림 발송 + 화면에 **변경 전/후 diff** 표시.
5. 신청자가 재동의 → `appliedVersion`을 최신으로 갱신, 이전 상태로 복귀.
6. 신청자가 거절 → `CANCELLED_BY_VERSION_CHANGE`. **패널티 없음** (신청자 귀책 아님).
7. 이미 `ACCEPTED`였던 신청이 재동의 대기로 내려간 경우, 확정 인원에서 일시적으로 제외된다.

> 근거: planner.md "사용자가 신청한 공고의 버전과 비교하여 다르면 다시 확인하라고 한다"를 상태머신으로 옮긴 형태. 전원 자동 취소 방식은 구인자가 오탈자 하나 고치다 지원자를 전부 잃게 되어 기각.

## 4. 신청 / 수락 (Application)

### 4.1 매칭 방식
**구인자 승인제.** 선착순 자동 확정 아님.
- 신청자가 지원 → 구인자가 신청자 목록(평점 노출)에서 수락/거절
- 수락 순간이 계약 체결. `acceptedAt` 기록

### 4.2 상태머신

```
APPLIED ──┬──▶ ACCEPTED ──┬──▶ COMPLETED
          │               ├──▶ CANCELLED_FREE      (수락 +2h 이내)
          │               ├──▶ CANCELLED_PENALTY   (2h 초과)
          │               └──▶ NO_SHOW
          ├──▶ REJECTED
          ├──▶ WITHDRAWN                            (수락 전 철회, 무패널티)
          └──▶ PENDING_REACCEPT ──┬──▶ (이전 상태로 복귀)
                                  └──▶ CANCELLED_BY_VERSION_CHANGE
```

### 4.3 취소 규칙 (planner.md "2시간" 해석 확정)
- **무상 취소 창 = 수락 시각 + 2시간.** 이 안에서는 구인자·구직자 양쪽 모두 패널티 없이 취소 가능.
- 창을 넘긴 취소는 `Penalty` 1건 누적.
- 무단 불참은 `NO_SHOW`로 별도 기록되며 마찬가지로 `Penalty` 1건.

**구인자 취소 시 구직자 보상은 없다 (확정).**
구인자에게는 `Penalty`가 쌓이고, 잠긴 포인트는 `RELEASE`로 전액 반환된다. 구직자에게 별도 보상금은 지급하지 않는다.

> 근거: 보상이 있으면 양측이 짜고 취소를 반복해 포인트를 이전하는 악용이 가능하다. 실제 취업 시장에서도 채용 취소에 대한 금전 보상은 없다.

### 4.4 동시성 — 정원 초과 수락 방지

**왜 필요한가.** 구인자가 6명을 뽑을 생각인데 7명이 확정되는 상황은 정상 흐름에서는 생기지 않는다. 문제는 **수락 요청이 동시에 두 개 들어올 때**다.

```
현재 확정 5명, 정원 6명

요청 A: 확정 인원 조회 → 5     ┐ 둘 다 "5 < 6" 통과
요청 B: 확정 인원 조회 → 5     ┘
요청 A: INSERT → 6
요청 B: INSERT → 7   ← 정원 초과
```

읽기와 쓰기 사이에 틈이 있어 두 요청이 모두 "자리 있음"을 보고 통과한다. 화면에서 버튼을 비활성화해도 막히지 않는다 — 그건 브라우저 쪽이고 판정은 서버에서 일어난다.

**발생 경로:** 수락 버튼 연타(응답 지연 시 흔함), 탭/기기 두 곳에서 동시 수락, 타임아웃 후 클라이언트 재시도.

**피해가 인원 숫자에서 끝나지 않는 이유:** 공고 등록 시 6명분만 `HOLD`로 잠갔는데 지급 대상이 7명이 된다. 완료 처리 시 잠긴 금액보다 많이 지급해야 하므로 잔액이 음수가 되거나 지급이 실패한다. 7번째 사람은 일하고도 못 받고, 관리자가 원장을 수동으로 맞춰야 한다.

**구현 — 조건부 UPDATE 한 문장.**

```sql
UPDATE "JobPost" SET "acceptedCount" = "acceptedCount" + 1
WHERE id = ? AND "acceptedCount" < "headcount"
```

- 이 문장 자체가 원자적이라 별도 락이 필요 없다
- 영향받은 행이 0이면 정원이 찬 것 → 수락 거절 후 "이미 정원이 찼습니다" 반환
- 같은 트랜잭션에서 `Application` 상태도 조건부로 바꿔 중복 수락을 막는다:
  `UPDATE "Application" SET status='ACCEPTED' WHERE id=? AND status='APPLIED'`
- 두 UPDATE가 모두 1행을 갱신했을 때만 커밋한다

> `SELECT ... FOR UPDATE`로 `JobPost` 행을 잠그는 방식도 동작하지만, 조건부 UPDATE가 한 문장으로 끝나고 잠금 구간이 짧아 이쪽을 택한다.

**통합 테스트 필수 케이스:** 정원이 1자리 남은 공고에 수락 요청 2개를 동시에 보내 **정확히 1개만 성공**하는지 검증한다 (Testcontainers).

### 4.5 기타 제약
- 중복 신청 방지: `@@unique([jobPostId, userId])`.

## 5. 제재 (Penalty / Suspension)

- `Penalty` 테이블에 건별 기록: `userId`, `reason`(NO_SHOW / LATE_CANCEL / SAME_DAY_CANCEL / POSTER_CANCEL), `jobPostId`, `occurredAt`.
- **판정 기준: 최근 180일 롤링 윈도우 내 5건 이상 → 5일 제재.**
  - 레코드는 삭제하지 않는다 (분쟁 대응 근거).
  - 집계는 쿼리로만 수행 — 별도 배치 불필요.
- 제재 중 차단되는 행위: **공고 등록, 알바 신청.** 진행 중인 계약 이행·환전·조회는 계속 가능.
- 제재 발생 시 `Suspension` 레코드 생성(`startAt`, `endAt`) + 알림 발송.
- 제재 해제는 별도 작업 없이 `endAt` 경과로 자연 만료 (조회 시점 판정). **해제용 배치 잡은 없다.**

### 5.1 블랙리스트 (= 자동 제재 목록)

planner.md에서 뺀 "신고·블랙리스트" 기능을 되살리는 것이 아니다. **관리자가 자동 제재된 회원을 목록으로 보고 조기 해제하는 화면**을 뜻하며, 새 테이블 없이 `Suspension` 조회로 구현한다.

- `Suspension`에 `releasedAt`, `releasedBy`(관리자 `userId`), `releaseReason` 컬럼 추가
- 관리자 해제 시 `releasedAt`을 찍고, 제재 판정 쿼리는 `releasedAt IS NULL AND endAt > now()`만 유효 제재로 본다
- 해제하더라도 원본 `Penalty` 레코드는 유지한다 (이력 보존)
- 해제 시 해당 회원에게 알림 발송

## 6. 포인트 / 결제 / 환전

### 6.1 원장 모델
`PointTransaction` 테이블에 증감 내역만 append. **잔액 컬럼을 직접 UPDATE 하지 않는다.**

| type | 부호 | 발생 시점 |
|---|---|---|
| `CHARGE` | + | 포트원 결제 웹훅 검증 성공 시 |
| `HOLD` | − | 공고 `OPEN` 전환 시 (`headcount × rewardPerPerson`) |
| `RELEASE` | + | 미체결 인원분 반환 (취소·미달·정원 미충족) |
| `PAYOUT` | − (구인자) / + (구직자) | 업무 완료 확인 시 |
| `EXCHANGE_REQUEST` | − | 환전 요청 시 (환전 대기로 이동) |
| `EXCHANGE_REVERT` | + | 환전 요청 반려 시 |
| `REFUND` | − | 결제 취소 |

- 잔액 = 원장 합계. 조회 성능은 `User.cachedBalance` 캐시 컬럼으로 보완하되, **진실의 원천은 항상 원장**이다.
- 모든 원장 쓰기는 트랜잭션 안에서 수행하고, 쓰기 전 잔액 검증으로 음수 방지.
- 각 트랜잭션에 `idempotencyKey` 유니크 인덱스 — 웹훅 중복 수신 방어.

### 6.2 HOLD 방식 (부분 체결 대응)
- 공고 등록 시 전액을 `HOLD`로 잠근다.
- 완료 시점: 확정 인원분만 `PAYOUT`, 나머지는 `RELEASE`로 자동 반환.
- planner.md의 "6명 중 3명 경합" 시나리오가 특수 케이스 없이 자연 처리된다.

### 6.3 충전 (포트원 테스트 모드)
1. 클라이언트에서 결제창 호출 → `paymentId` 발급
2. **서버가 포트원 API로 결제 건 재조회하여 금액 대조** (클라이언트 응답을 신뢰하지 않음)
3. 웹훅 수신 → 서명 검증 → `idempotencyKey`로 중복 차단 → `CHARGE` 원장 기록
4. 실결제 전환 시 채널키/API키만 교체

### 6.4 환전 (확정 흐름)

> **MVP에는 실제 송금 기능이 없다.** 포트원 테스트 모드로는 계좌 송금도 계좌 실명조회도 실검증이 불가능하다. 따라서 MVP는 **환전 요청 목록을 관리자가 보고 승인하는 것까지만** 만든다. 실제 이체는 관리자가 은행 앱에서 직접 하고 시스템에는 "완료"만 찍는다.
>
> **설계 목표는 "지금 동작하는 것"이 아니라 "사업자등록 후 환경변수만 바꾸면 전환되는 것"이다.**

#### 6.4.1 흐름

1. **계좌 등록** — `ExchangeAccount`: 은행코드, 계좌번호(암호화 저장), 예금주명
2. **계좌 검증** — `verificationStatus`: `PENDING` → `VERIFIED` / `REJECTED`. 검증 완료 시 알림
3. **환전 요청** — `PAYOUT`된 지 **7일 경과**한 포인트에 한해, **5,000원 이상 & 10원 단위**로 요청
4. **관리자 승인** — `ExchangeRequest.status`: `REQUESTED` → `APPROVED` → `COMPLETED` / `REJECTED`
5. 반려 시 `EXCHANGE_REVERT`로 포인트 원복

#### 6.4.2 모드 분기 (환경변수)

두 지점을 인터페이스로 분리하고 환경변수로 구현체를 고른다. **도메인 로직·DB 스키마·화면은 두 모드에서 완전히 동일하다.**

| 인터페이스 | 환경변수 | MVP 값 | 전환 후 |
|---|---|---|---|
| `AccountVerifier` | `ACCOUNT_VERIFY_MODE` | `stub` | `portone` |
| `ExchangeProvider` | `EXCHANGE_MODE` | `manual` | `portone` |

**`StubAccountVerifier` (MVP)**
- 은행코드가 유효 목록에 있는지, 계좌번호가 숫자이며 자릿수가 맞는지 **형식만 검사**
- 통과하면 **즉시 `VERIFIED`**. 실명 대조는 하지 않는다
- 관리자 대기 단계를 만들지 않는 이유: 실서비스 흐름과 단계 수가 같아야 전환 시 화면을 안 고친다. E2E 테스트도 막히지 않는다

**`PortOneAccountVerifier` (전환 후)**
- 포트원 API로 회원 실명과 예금주명 대조. 불일치 시 `REJECTED` + 사유

**`ManualExchangeProvider` (MVP)**
- `APPROVED`로 바꾸는 것까지만 수행. 실제 송금 호출 없음
- 관리자가 은행 앱에서 이체한 뒤 화면에서 "이체 완료"를 눌러 `COMPLETED` 처리

**`PortOneExchangeProvider` (전환 후)**
- 승인 시 실송금 API 호출 → 응답으로 `COMPLETED` 자동 처리

> **전환 시 수정 범위:** 구현체 클래스 2개 추가 + 환경변수 2줄. 도메인 서비스, `ExchangeRequest` 상태머신, 사용자 화면, 관리자 화면은 손대지 않는다. 이것이 이 설계의 유일한 목적이다.

#### 6.4.3 MVP에서 만들지 않는 것

- 자동 송금 / 지급대행 연동
- 계좌 실명 실조회
- 원천징수·세금계산서
- 환전 수수료 계산

## 8. 알림 (Notification)

- `Notification` 테이블에 인앱 알림 저장. 헤더 벨 아이콘 + 미읽음 카운트
- 아래 건은 이메일 병행:
  - 재동의 요청 (공고 버전 변경)
  - 수락 / 거절
  - 모집 미달 (시작 3시간 전)
  - 제재 발생
  - 계좌 검증 완료
  - 환전 승인 / 완료 / 반려
- 발송 이력을 DB에 남겨 테스트에서 검증 가능하게 한다

### 8.1 스케줄 작업 (`@nestjs/schedule`, 1분 주기)

| 작업 | 조건 | 동작 |
|---|---|---|
| 모집 미달 알림 | `OPEN` && 시작 3시간 전 && 확정 인원 < 정원 | 구인자에게 "연장 / 삭제 / 유지" 선택 알림. **미응답 시 기본값은 유지** |
| 공고 마감 | 시작 시각 도달 | `OPEN` → `CLOSED` 또는 `EXPIRED` |
| 환전 가능 전환 | `PAYOUT` 후 7일 경과 | 환전 가능 표시 + 알림 |
| 개인정보 파기 | 비활성화 후 4개월 경과 | 컬럼 단위 비식별 처리 (§2.7). 일 1회 |

**제재 해제는 잡이 아니다.** `Suspension.endAt` 경과 여부를 조회 시점에 판정하므로 배치가 필요 없다.

### 8.2 중복 실행 방어 (2중)

서버를 여러 대로 늘리면 같은 잡이 동시에 돌아 알림이 두 번 갈 수 있다. 두 겹으로 막는다.

**1차 — 멱등성 (필수).** 각 잡의 대상 행에 `notifiedAt` / `closedAt` 같은 플래그를 두고, 조건절에 `IS NULL`을 넣어 갱신한다. 잡이 두 번 돌아도 두 번째는 대상이 0건이 된다. 이것만으로도 중복 발송은 나지 않는다.

**2차 — 분산락 (PostgreSQL advisory lock).**
- 잡 진입부에서 `pg_try_advisory_lock(jobKey)`를 시도하고, 실패하면 즉시 반환한다
- 종료 시 `pg_advisory_unlock`. 프로세스가 죽어도 세션 종료와 함께 자동 해제된다
- **Redis 등 추가 인프라가 필요 없다.** 이미 쓰는 Postgres만으로 진짜 분산락이 된다
- 잡 하나당 고정 정수 키를 `shared`에 상수로 정의한다

> BullMQ + Redis를 쓰지 않은 이유: 컨테이너와 워커 프로세스가 추가되는데, 2인 팀 MVP에서 얻는 것이 advisory lock 대비 크지 않다. 스케일아웃 규모가 커지면 그때 전환한다.

| 계층 | 도구 | 대상 |
|---|---|---|
| 유닛 | Vitest | 버전 diff 판정, 취소 패널티 판정, 경고 180일 집계, 포인트 잔액 계산 |

## 10. CSS 규약

`css-standards` 규약을 기본 적용: 리셋 1회, 모바일 우선(`min-width` 미디어쿼리), rem/%/flex/grid, 색·간격은 CSS 변수, 테이블은 정렬 규약(가변 텍스트=좌, 형식 자료=중앙, 숫자=우) + sticky 헤더 + 가로 스크롤.

**예외 허용 화면 (2곳만):**

| 화면 | 예외 내용 | 사유 |
|---|---|---|
| 서명 캔버스 | 고정 px 캔버스 + `devicePixelRatio` 스케일링 | 터치 좌표 정확도. rem/%로는 서명이 PDF에서 어긋난 위치에 박힘 |
| PDF 뷰어 | 원본 종횡비 고정 컨테이너 | 문서 비율 왜곡 방지 |

그 외 화면(공고 목록, 포인트 내역 테이블, 환전 화면, 지도 컨테이너 포함)은 예외 없이 규약을 따른다.

## 11. 관리자 (Admin)

### 11.1 관리자 계정
- 별도 테이블 없이 `User.role`(`USER` / `ADMIN`)로 구분한다.
- 최초 관리자는 Prisma seed로 생성. 화면에서 관리자를 만드는 기능은 두지 않는다.
- 관리자 라우트는 Nest Guard + Next.js middleware 양쪽에서 `role === ADMIN`을 검사한다.

### 11.2 공통 목록 규약 (모든 관리자 목록에 적용)

**모든 리스트 화면은 검색 + 필터를 반드시 갖춘다.** 개별 화면마다 다르게 만들지 않고 공통 컴포넌트 하나로 통일한다.

| 요소 | 규칙 |
|---|---|
| 검색 | 이름·이메일 부분 일치 검색. 디바운스 300ms |
| 필터 | 주소지(시/도 → 시/군/구), 카테고리, 상태, 기간(등록일·가입일) |
| 조합 | 검색어와 필터는 **AND 조합**. 적용된 필터는 칩(chip)으로 표시하고 개별 해제 가능 |
| 정렬 | 컬럼 헤더 클릭 정렬 (기본: 최신순) |
| 페이징 | 서버 사이드. 관리자 화면은 오프셋 페이징(전체 건수 표시 필요) |
| URL | 검색·필터 상태를 쿼리스트링에 반영해 새로고침·공유 시 유지 |
| 표 스타일 | `css-standards` 정렬 규약 + sticky 헤더 + 가로 스크롤 |

> 성능: 필터 대상 컬럼(`name`, `email`, `sido`, `sigungu`, `categoryId`, `status`, `createdAt`)에 인덱스를 건다. 이름 부분 일치는 데이터가 늘면 `pg_trgm` GIN 인덱스로 전환한다.

### 11.3 회원 관리

**회원 목록**
- 컬럼: 이름 / 이메일 / 가입일 / 구인자 평점 / 구직자 평점 / 경고 수(180일) / 상태
- 필터: 주소지, 가입 기간, 상태(정상 / 제재중 / **비활성화**)
- **비활성화 회원은 목록에서 사라지지 않고 "비활성화" 배지로 표시**된다

**회원 상세** (행 클릭 시 진입)
- 기본 정보: 이름·이메일·주소·가입일·동의서(PDF 열람)
- **평점 및 리뷰 목록**: 구인자/구직자 역할별 평균과 받은 별점 내역 (거래 상대·공고·일시)
- 거래 이력: 등록 공고 목록, 신청 이력
- 포인트: 잔액 및 원장 내역
- 제재 이력: `Penalty` 건별 목록(사유·시각·관련 공고), `Suspension` 이력
- 계좌: 등록 계좌 및 검증 상태 (계좌번호는 마스킹 표시)

### 11.4 블랙리스트 (제재 회원)
- 현재 제재 중인 회원 목록 (`releasedAt IS NULL AND endAt > now()`)
- 컬럼: 이름 / 제재 시작 / 제재 종료 / 사유 요약 / 누적 경고 수
- 검색·필터: 이름 검색, 제재 기간
- **제재 해제** 버튼 → 해제 사유 입력 필수 → `releasedAt`·`releasedBy`·`releaseReason` 기록 + 회원에게 알림
- 해제된 이력도 별도 탭에서 조회 가능 (누가 왜 풀었는지 추적)

### 11.5 환전 관리

**MVP 범위는 "환전 요청자 목록을 보고 승인하는 것"까지다.** 송금 자동화·이체 내역 대사·수수료 정산은 만들지 않는다.

- **환전 요청 목록** — 필터: 상태(`REQUESTED`/`APPROVED`/`COMPLETED`/`REJECTED`), 요청 기간, 금액 구간. 검색: 신청자 이름
- 컬럼: 신청자 / 요청 금액 / 은행·계좌(마스킹) / 예금주명 / 계좌 검증 상태 / 요청 일시 / 상태
- **승인** → `APPROVED`. 관리자가 은행 앱에서 직접 이체
- **이체 완료** → `COMPLETED`. 관리자가 수동으로 찍는다
- **반려** → 사유 입력 필수 → `EXCHANGE_REVERT`로 포인트 원복 + 신청자에게 알림
- 계좌번호 전체 열람은 별도 버튼(이체할 때만 필요) — 열람 사실도 감사 로그에 남긴다
- **모든 관리자 조치는 `AdminAuditLog`에 기록한다** (누가·언제·무엇을·왜)

> `EXCHANGE_MODE=portone`으로 전환되면 "승인" 한 번으로 `COMPLETED`까지 자동 진행된다. 화면은 그대로 두고 "이체 완료" 버튼만 숨긴다.

### 11.6 공고 관리
- 공고 목록 — 검색(제목·구인자명), 필터(카테고리, 주소지, 상태, 등록 기간)
- 상세: 버전 이력, 신청자 목록, 포인트 잠금/지급 내역
- 관리자 강제 취소(사유 필수, 잠긴 포인트 전액 `RELEASE`)

## 12. 미해결 항목

**없다. MVP 착수를 막는 결정은 모두 확정되었다.**

### 12.1 인지만 하고 구현하지 않는 것

아래는 "나중에 이런 게 필요하다"를 기록해두는 항목이다. **MVP에서는 만들지 않으며, 일정에도 넣지 않는다.** 셋 다 사업자등록 또는 실서비스 오픈이 선행 조건이라 지금은 손댈 수 없다.

| 항목 | 지금 해둔 대비 | 착수 조건 |
|---|---|---|
| 법정 보관 기간 정합 | `RETENTION_*` 상수 한 곳에 모음 (§2.7). 숫자만 교체 | 실서비스 오픈 전 |
| 관리자 2단계 인증 | 관리자를 `User.role`로만 구분 (§11.1). 인증 계층에 붙이면 됨 | MVP 이후 |
| 실송금 자동화 | `ExchangeProvider` + `EXCHANGE_MODE` 분기 (§6.4.2). 구현체 2개 추가 | 사업자등록 후 |

> 세 항목의 공통점: **지금 구조를 잘못 잡으면 나중에 크게 뜯어야 하지만, 구조만 맞으면 나중 작업은 작다.** 그래서 구현은 미루되 자리는 미리 비워뒀다.

### 해소된 항목

| 항목 | 결정 | 반영 위치 |
|---|---|---|
| 관리자 화면 범위 | 회원 목록/상세, 블랙리스트, 환전, 공고 + 공통 검색·필터 규약 | §11 |
| 계좌 실명 검증 | MVP는 `StubAccountVerifier`(형식 검사 → 자동 VERIFIED), 환경변수로 전환 | §6.4.2 |
| 실송금 여부 | **MVP에 송금 기능 없음.** 환전 요청 목록 + 승인까지만 | §6.4, §11.5 |
| 개인정보 파기 정책 | 소프트 삭제 → 로그인 차단 → 비활성화 후 4개월 파기 / 법정 대상은 법정 기간 | §2.6, §2.7 |
| 구직자 보상 여부 | **보상 없음** (악용 방지) | §4.3 |
| Cron 중복 실행 | 멱등성 + PostgreSQL advisory lock | §8.2 |
| 이메일 인프라 | Resend (`MailProvider` 인터페이스 뒤) | §1 |
| 용어: 정산/출금 vs 환전 | **환전(Exchange)으로 통일.** 지급(`PAYOUT`)과 구분 | §0 |
