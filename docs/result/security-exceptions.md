# 보안 예외 대장

`pnpm audit`이 잡았지만 **판단해서 수용한** 취약점을 기록한다.

이 파일이 없으면 CI의 audit 잡이 "아무도 안 보는 빨간 X"가 된다. 3개월 뒤엔 그 X가 배경이 되고, 진짜 위험이 섞여 들어와도 눈에 띄지 않는다. **넘어간 것과 넘어갈 만해서 넘어간 것을 구분하는 것**이 이 대장의 목적이다.

`/security-review`는 취약점을 분류하기 전에 **이 대장을 먼저 조회한다.** 여기 있으면 근거를 대고 ⚪로 넘기고, 없으면 새로 판단한다.

---

## 판정 기준

심각도 하나로 정하지 않는다. **빌드 도구의 high보다 요청 경로의 moderate가 더 급하다.**

| 도달 경로                                                    | 심각도          | 처리                                     |
| ------------------------------------------------------------ | --------------- | ---------------------------------------- |
| **운영 코드 경로** — 서버가 실제로 실행하는 코드             | critical · high | 🔴 **차단.** 고치기 전에 머지하지 않는다 |
| 운영 코드 경로                                               | moderate 이하   | 🟡 보고 후 다음 이슈로                   |
| **빌드·CLI 전용** — devDependency, 생성기, 린터, 테스트 도구 | 전부            | ⚪ 대장에 기록하고 넘어간다              |

빌드 도구의 취약점은 **개발 PC를 노리는 것이지 사용자를 노리는 것이 아니다.** 이걸 차단 기준에 넣으면 2인 팀에서 매주 막히고, 결국 `audit`을 꺼버린다. 껐다는 사실조차 잊는다.

### 자동 판별은 불가능하다

`pnpm audit --prod`가 도달 경로를 정확히 갈라주지 않는다. **peerDependency를 운영 트리로 세기 때문**이다. 아래 첫 항목이 정확히 그 경우다.

그래서 CI의 audit 잡은 **차단하지 않고 신호만 낸다.** 판정은 `/security-review`에서 사람이 한다.

---

## 운영 규칙

- **예외는 3건 이하로 유지한다.** 넘으면 "관리되고 있지 않다"는 신호다
- **재검토 날짜가 지나면 다시 판단한다.** 영구 면제가 아니다
- 해소되면 지우지 말고 **아래 "해소됨"으로 옮긴다.** 같은 것을 다시 조사하지 않기 위해서다

## 수용 중인 예외

> ⚠️ **현재 4건으로 "3건 이하" 규칙을 넘겼다.** (2026-09-05, `/security-review 17`)
>
> 넷 중 셋(1~3번)은 **원인이 하나다** — Prisma CLI와 Nest CLI가 개발 도구 묶음을
> 통째로 끌어오고, `pnpm audit`이 그걸 운영 트리로 센다. 항목이 늘어난 것이지
> 위험이 늘어난 것은 아니다.
>
> 다만 **4번(`qs`)은 성질이 다르다.** 유일하게 `devDependencies`를 거치지 않는
> 진짜 운영 경로이고, 배포되는 순간 수용 근거가 사라진다. 이 대장을 훑을 때
> 1~3번을 넘기더라도 **4번은 매번 읽어야 한다.**
>
> 규칙을 5건으로 늘리지 않고 그대로 둔다. 넘겼다는 사실 자체가 신호다.

### 1. `deepmerge-ts` < 8.0.0

| 항목          | 내용                                   |
| ------------- | -------------------------------------- |
| **심각도**    | high                                   |
| **패치 버전** | `>=8.0.0` (현재 설치 `7.1.5`)          |
| **권고 ID**   | GHSA-ggr8-5vv4-36mx                    |
| **판정**      | ⚪ 수용                                |
| **기록일**    | 2026-08-30                             |
| **재검토**    | Prisma 업데이트 시 또는 **2026-11-30** |

**의존 경로**

```
deepmerge-ts@7.1.5
└─ @prisma/config@7.9.1
   └─ prisma@7.9.1          ← apps/api의 devDependency
      └─ @prisma/client     ← prisma를 peerDependency로 선언
```

**수용 이유**

`@prisma/config`는 **CLI가 `prisma.config.ts`를 읽을 때** 쓰는 패키지다. 서버가 떠서 쿼리를 처리하는 경로에 있지 않다. `@prisma/client`의 실제 `dependencies`는 `@prisma/client-runtime-utils` 하나뿐이며, `prisma` CLI는 `peerDependencies`로만 선언돼 있다.

`pnpm audit --prod`에도 잡히는 것은 pnpm이 peerDependency를 운영 트리로 세기 때문이지, 런타임에 그 코드가 실행돼서가 아니다.

**우리가 직접 올릴 수 없다.** Prisma가 `@prisma/config`를 통해 끌어오는 전이 의존성이라, `pnpm overrides`로 강제하는 방법뿐인데 Prisma CLI가 깨질 위험이 있다.

**해소 조건**

- Prisma가 `@prisma/config`의 `deepmerge-ts`를 8 이상으로 올린 버전을 내면 그 버전으로 업데이트한다
- 그전에 `prisma`를 운영 경로에서 실제로 부르게 되면 **즉시 재판정한다** (지금은 CLI 전용)

**시도해볼 수 있는 것 (아직 안 함)**

```yaml
# pnpm-workspace.yaml
overrides:
  deepmerge-ts: '>=8.0.0'
```

의존성 변경은 사람이 판단할 일이라 적용하지 않았다. 적용한다면 `pnpm test`와 `pnpm --filter @fixer/api prisma:generate`가 모두 통과하는지 반드시 확인한다.

### 2. `mysql2` < 3.23.1 — **권고 2건**

| 항목          | 내용                                                            |
| ------------- | --------------------------------------------------------------- |
| **심각도**    | high 1건 + moderate 1건                                         |
| **패치 버전** | `>=3.23.1` (둘 다 덮는 버전)                                    |
| **권고 ID**   | GHSA-3f6p-5ww8-9rcr, GHSA-rgwj-5xj2-c3m3                        |
| **판정**      | ⚪ 수용                                                         |
| **기록일**    | 2026-09-02 · 2번째 권고 추가 2026-09-05 (`/security-review 18`) |
| **재검토**    | Prisma 업데이트 시 또는 **2026-11-30**                          |

| 권고 ID             | 심각도   | 내용                               | 패치     |
| ------------------- | -------- | ---------------------------------- | -------- |
| GHSA-3f6p-5ww8-9rcr | high     | 인증 플러그인 다운그레이드         | >=3.22.0 |
| GHSA-rgwj-5xj2-c3m3 | moderate | 압축 프로토콜의 zlib 압축 폭탄 DoS | >=3.23.1 |

**같은 항목으로 묶는다.** 패키지·의존 경로·수용 근거가 완전히 같아서 예외를 하나 더
세는 것은 위험이 늘었다는 잘못된 신호를 준다. 다만 **권고 ID를 둘 다 적어 둔다** —
스캔 결과에 `rgwj`가 뜨는데 대장에 `3f6p`만 있으면 다음 사람이 같은 추적을 다시 한다.

**의존 경로**

```
mysql2
└─ prisma@7.9.1            ← apps/api의 devDependency
   └─ @prisma/client       ← prisma를 peerDependency로 선언
```

**왜 수용하는가**

`deepmerge-ts`와 같은 이유다. Prisma CLI가 **모든 DB 드라이버를 함께 들고 오기 때문에**
설치되는 것이지, 우리는 PostgreSQL만 쓴다. `mysql2`가 운영 코드 경로에 들어가는
지점이 없다 — `apps/api/src/`에서 import하는 곳이 0건이고, 드라이버 어댑터도
`@prisma/adapter-pg`다.

CLI 전용 의존성이라 마이그레이션·생성 명령을 돌릴 때만 로드된다. 그 명령을 돌리는
주체는 개발자 본인이므로 외부 입력이 닿지 않는다.

### 3. `fast-uri` < 3.2.0

| 항목       | 내용                                              |
| ---------- | ------------------------------------------------- |
| **심각도** | high × 4 (host confusion 2건, SSRF 2건)           |
| **판정**   | ⚪ 수용                                           |
| **기록일** | 2026-09-05 (`/security-review 17`)                |
| **재검토** | Nest CLI · Prisma 업데이트 시 또는 **2026-12-05** |

**의존 경로** — 전부 `ajv`를 거친다. 도달하는 곳이 다섯 갈래인데 **모두 빌드·CLI다.**

```
fast-uri@3.1.5
├─ ajv@8.18.0 → @angular-devkit/core → @nestjs/schematics → @nestjs/cli   (devDep)
└─ ajv@8.20.0
   ├─ @commitlint/config-validator → @commitlint/cli                       (devDep)
   ├─ schema-utils → webpack / ts-loader                                   (devDep)
   └─ @prisma/streams-local → @prisma/dev → prisma@7.9.1                   (devDep)
```

**수용 이유**

`ajv`는 JSON 스키마 검증기고, 여기서는 **Nest CLI의 스키매틱·webpack의 로더 옵션 검증·commitlint의 설정 검증**에 쓰인다. 우리 서버는 런타임 검증에 zod를 쓰며 `ajv`를 부르는 곳이 `apps/api/src`에 0건이다.

마지막 갈래가 `prisma → @prisma/client → @fixer/api (dependencies)`로 이어져 운영 트리처럼 보이는데, **대장 1·2번과 같은 peerDependency 계산 착시다.** `@prisma/dev`는 개발용 도구이고 서버가 쿼리를 처리하는 경로에 없다.

SSRF·host confusion은 **URI를 파싱해 외부로 요청을 보낼 때** 문제가 된다. 빌드 도구가 파싱하는 URI는 우리가 쓴 설정 파일이지 외부 입력이 아니다.

**해소 조건**

- `@nestjs/cli`·`prisma`·`commitlint`가 `ajv`를 `fast-uri >= 3.2.0` 버전으로 올리면 그 버전으로 업데이트한다
- `ajv`를 운영 코드에서 직접 쓰게 되면 **즉시 재판정한다**

### 4. `qs` < 6.15.4 — **다른 셋과 성격이 다르다**

| 항목       | 내용                                            |
| ---------- | ----------------------------------------------- |
| **심각도** | moderate × 2                                    |
| **판정**   | 🟡 **수용하되 운영 경로다.** 배포 전 재판정     |
| **기록일** | 2026-09-05 (`/security-review 17`)              |
| **재검토** | **첫 배포 직전** 또는 2026-12-05 (먼저 오는 쪽) |

**의존 경로** — 위 셋과 달리 **`devDependencies`를 한 번도 거치지 않는다.**

```
qs@6.15.3
└─ body-parser@2.3.0 / express@5.2.1
   └─ @nestjs/platform-express@11.2.1
      └─ @fixer/api (dependencies)
```

**왜 다른가**

express는 **모든 요청의 쿼리스트링을 `qs`로 파싱한다.** 서버가 떠 있는 동안 외부 입력이 매 요청 이 코드를 지나간다. 대장 1~3번이 "개발 PC를 노리는 것"이라면 이건 사용자를 노릴 수 있는 자리다.

- `array-limit bypass via bracket-key comma parsing`
- `Denial of Service via Attacker Controlled isBuffer`

DoS 쪽은 **인증 없이도 때릴 수 있다.**

**그런데도 지금 안 고치는 이유**

- 우리가 직접 올릴 수 없다. `express@5.2.1`이 `body-parser`를 통해 고정한다
- `pnpm overrides`로 강제할 수는 있으나 express 5의 요청 파싱을 건드리는 일이라 회귀 범위가 크다. **의존성 변경은 사람이 판단한다**
- **배포된 환경이 아직 없다.** 지금은 노출 면이 로컬뿐이다

**해소 조건 — 이건 날짜보다 사건이 먼저다**

- **배포하기 전에 반드시 재판정한다.** 배포되는 순간 "노출 면이 없다"는 수용 근거가 사라진다
- `express`가 `qs >= 6.15.4`를 물고 오는 버전을 내면 그 버전으로 올린다
- 그 전에 올려야 하면 `pnpm-workspace.yaml`의 `overrides`로 강제하고, `pnpm test`와 실제 쿼리 파싱(`GET /job-posts?...`, `GET /applications/me?...`)을 확인한다

## 코드 레벨로 수용한 위험

의존성이 아니라 **우리 코드**에서 판단해 남겨둔 것. 같은 기준(도달 경로 × 심각도)을 쓴다.

### 1. `ConsoleMailProvider`의 운영 차단이 fail-open

| 항목       | 내용                                                                       |
| ---------- | -------------------------------------------------------------------------- |
| **위치**   | `apps/api/src/auth/console-mail.provider.ts`                               |
| **발견**   | `/security-review 1` (2026-08-30) · #6에서 재설정 토큰도 해당 (2026-09-03) |
| **판정**   | 🟡 수용 — #37에서 해소                                                     |
| **재검토** | 이슈 #37 (중요 알림 이메일 발송) 착수 시                                   |

**무엇이 문제인가**

개발용 메일러가 인증 코드를 로그에 찍는다. **#6부터는 비밀번호 재설정 링크 토큰도
같은 자리에 찍힌다** — 그 토큰 하나면 비밀번호를 바꿀 수 있으므로 노출 시 피해가 더 크다. 운영 차단이 `NODE_ENV === 'production'`일 때만 걸리므로, **`NODE_ENV`가 비어 있는 채로 배포되면 그냥 통과한다.** 그러면 로그를 읽을 수 있는 사람이 아무 계정이나 인증할 수 있다.

**왜 지금 안 고쳤나**

허용 목록(`['development', 'test']`)으로 바꿔봤더니 **개발 서버가 뜨지 않았다.** `nest start`가 `NODE_ENV`를 설정하지 않아 값이 `undefined`이기 때문이다. 값을 넣으려면 스크립트의 환경변수 주입 방식(Windows에서 접두사가 안 먹음)까지 손대야 하는데, 이슈 #1 범위를 넘는다.

**제대로 된 해결**

한 줄 조건이 아니라 **`AuthModule`이 환경을 보고 메일러를 고르는 것**이다. 운영에서는 `ConsoleMailProvider`가 아예 주입되지 않으면 조건문이 필요 없다. 실제 발송(Resend)을 붙이는 **#37에서 함께 한다.**

**그때까지의 완화**

배포된 환경이 없다. `ConsoleMailProvider`는 로컬에서만 돈다.

## 새 예외를 기록하는 법

`/security-review`가 ⚪로 분류한 항목 중 **반복해서 나올 것**만 여기 적는다. 일회성 오탐은 적지 않는다.

담을 것:

| 필수        | 이유                                                          |
| ----------- | ------------------------------------------------------------- |
| 의존 경로   | 도달 가능성 판단의 근거다. `pnpm why <패키지>` 결과를 붙인다  |
| 수용 이유   | "빌드 전용"만으로는 부족하다. **왜 그렇게 판단했는지**를 쓴다 |
| 재검토 날짜 | 없으면 영구 면제가 된다                                       |
| 해소 조건   | 무엇이 바뀌면 이 예외가 없어지는지                            |
