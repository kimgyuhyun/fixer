# 개발 순서 및 2인 팀 분담

> 전제: `docs/result/spec-fixed.md` 확정 사양
> 팀 구성: **A = 최동훈**, **B = 팀원 1명**
> 분담 원칙: **기능(도메인) 수직 분할** — 각자 DB→API→화면까지 풀스택으로 끝냄

---

## 1. 분담 원칙과 그 이유

2인 팀에서 프론트/백 수평 분할을 쓰면 한쪽이 막힐 때 다른 쪽이 통째로 대기하고, 버스팩터가 1이 된다. 도메인 수직 분할은 각자 자기 기능을 끝까지 책임지므로 대기 시간이 거의 없다.

대신 **수직 분할의 유일한 위험은 공통 기반이 두 갈래로 갈라지는 것**이다. 그래서 Sprint 0에서 공통 자산(Prisma 스키마 전체, 인증 가드, 원장 인터페이스, CSS 토큰, 공통 컴포넌트, 에러 응답 규격)을 **둘이 같이 먼저 못 박고** 나서 갈라진다.

## 2. 담당 영역

### A — 최동훈 : 회원 · 인증 · 문서 

| 영역 | 범위 |
|---|---|
| 인증 | JWT 발급/검증, httpOnly 쿠키, Refresh 토큰 DB, Nest Guard, Next.js middleware 보호 라우팅, 로그아웃 캐시 무효화, 관리자 role 가드 |
| 회원 | 가입 플로우, 이메일 인증 난수, 비밀번호 재설정, 마이페이지, 주소(카카오 우편번호+로컬), 추가 주소 관리 |
| 탈퇴/재활성화 | 소프트 삭제, 탈퇴 보류 조건 3종 판정, 로그인 차단, 재활성화 흐름 |
| 전자서명 | 서명 캔버스, `pdf-lib` PDF 병합, 해시 기록, 스토리지 볼륨 분리, 동의서 조회 |
| 포인트 원장 | `PointTransaction` 코어 서비스(`hold`/`release`/`payout`/`charge`), 잔액 계산, 멱등성 |
| 결제 | 포트원 결제창 연동, 서버 측 금액 재검증, 웹훅 수신·서명 검증, 충전 내역 화면 |
| 환전 | 계좌 등록/암호화, `AccountVerifier`(stub: 형식 검사 → 자동 VERIFIED), 환전 요청(5,000원·10원 단위·7일 경과), `ExchangeProvider` 추상화 |
| 관리자 화면 | 회원 목록/상세, 환전 관리 (요청 목록·승인·이체 완료·반려) |
| 공통 인프라 | 알림 발송 모듈(인앱 + **Resend** 이메일), `MailProvider` 추상화, 에러 응답 규격, 로깅 |

### B — 팀원 : 공고 · 매칭 · 규칙 · 돈

| 영역 | 범위 |
|---|---|
| 카테고리 | `Category` 테이블, seed, 플레이스홀더 문구 연동 |
| 공고 | CRUD, 상태머신(DRAFT/OPEN/CLOSED/COMPLETED/CANCELLED/EXPIRED), 소프트 삭제 |
| **공통 목록 컴포넌트** | `FilterableList` — 검색·필터 칩·정렬·페이징·URL 동기화. **사용자 공고 목록과 관리자 목록이 함께 쓴다** |
| 버전 | 필수항목 변경 감지, `version` 증가, `JobPostVersion` 이력, diff 화면 |
| 신청/수락 | 지원, 구인자 승인제, 정원 초과 방지(행 잠금), 재동의(`PENDING_REACCEPT`) 흐름 |
| 취소/제재 | 무상 취소 창(수락+2h) 판정, `Penalty` 기록, 180일 롤링 5건 → 5일 제재, 제재 중 행위 차단 |
| 평점 | 별점 1~5 양방향, 역할별 평균 집계, 표본 3건 미만 "신규" 표시, **회원 상세용 리뷰 목록 API** |
| 스케줄러 | 모집 미달 3시간 전 알림, 공고 자동 마감, 멱등 처리 + **advisory lock** |
| 관리자 화면 | 블랙리스트(제재 목록·조기 해제), 공고 관리 |

## 3. 개발 순서 (Sprint 단위)

### Sprint 0 — 공통 기반 (약 1주, **둘이 함께**)

이 단계는 나눠서 하지 않는다. 여기서 어긋나면 이후 전부 어긋난다.

- [ ] pnpm 모노레포 골격 (`apps/web`, `apps/api`, `packages/shared`)
- [ ] **Prisma 스키마 전체를 한 번에 설계** — 두 사람의 테이블이 서로 FK로 얽혀 있어 부분 설계 불가
- [ ] `packages/shared`: 공통 타입, Zod 스키마, 에러 코드 enum, 상태 enum
- [ ] API 응답 규격 통일 (`{ status, resultMsg, data }` + try/catch 표준)
- [ ] **인증 가드 인터페이스 + Mock 구현** ← B가 A를 기다리지 않게 하는 핵심
- [ ] **`LedgerService` 인터페이스 + Mock 구현** ← B가 A를 기다리지 않게 하는 핵심
- [ ] `NotificationService` / `MailProvider` / `ExchangeProvider` / `AccountVerifier` 인터페이스 + Mock
- [ ] `RETENTION_*` 상수 파일 (`packages/shared/src/retention.ts`) — 테스트에서 주입 가능하게
- [ ] `User.role`(USER/ADMIN) + `AdminAuditLog` 스키마, 관리자 seed
- [ ] advisory lock 잡 키 상수 정의 (`shared`)
- [ ] CSS: 리셋 1회 적용, 색·간격 CSS 변수 토큰 정의, 공통 컴포넌트(Button/Input/Modal/Table)
- [ ] docker-compose (Postgres), GitHub Actions CI, Vitest + Testcontainers 하네스
- [ ] Resend 계정 생성 + 도메인 인증(SPF/DKIM) — 전파에 시간이 걸리므로 **가장 먼저** 신청

> **인터페이스 우선 원칙:** A와 B가 서로 호출하는 지점은 전부 Sprint 0에서 인터페이스 + Mock으로 먼저 고정한다. 실제 구현이 늦어도 상대는 Mock으로 개발·테스트를 계속한다.

---

### Sprint 1 — 각자 도메인 착수 (약 2주, 병렬)

| A | B |
|---|---|
| 인증 전체 (JWT·쿠키·Guard·미들웨어·로그아웃·관리자 role) | 카테고리 테이블 + seed + 관리 |
| 이메일 인증 난수 + 가입 플로우 (Resend 연동) | 공고 CRUD + 상태머신 |
| 주소 입력 (카카오 우편번호 + 좌표) | **`FilterableList` 공통 컴포넌트** + 공고 목록/상세 |
| **→ Sprint 1 중반에 실제 Guard를 B에게 인계** | **→ Sprint 1 말에 `FilterableList`를 A에게 인계** |

**마일스톤:** 실제로 가입·로그인하고 공고를 등록·조회할 수 있다.

---

### Sprint 2 — 핵심 로직 (약 2주, 병렬)

| A | B |
|---|---|
| 서명 캔버스 + `pdf-lib` PDF 병합 | 신청/수락 (정원 초과 방지 행 잠금) |
| 동의서 저장·해시·스토리지 분리 | **버전 정책 + 재동의 흐름 + diff 화면** |
| 비밀번호 재설정 | 취소 규칙 (무상 취소 창) |
| 탈퇴/재활성화 (보류 조건 3종) | 취소 시 구직자 보상 없음 확정 반영 |
| **포인트 원장 코어 구현 → B에게 실제 서비스 인계** | (그때까지 Mock Ledger 사용) |

**마일스톤:** 서명된 동의서가 나오고, 신청→수락→버전 충돌→재동의가 전부 동작한다.
**이번 스프린트가 가장 위험하다.** 버전 정책과 원장은 둘 다 난이도가 높고 서로 물려 있으므로 중간 점검을 한 번 넣는다.

---

### Sprint 3 — 돈과 규칙 (약 2주, 병렬)

| A | B |
|---|---|
| 포트원 결제창 + 서버 금액 재검증 | HOLD/RELEASE/PAYOUT 도메인 연결 |
| 웹훅 수신·서명 검증·멱등성 | 경고 스택 + 180일 롤링 제재 |
| 충전/포인트 내역 화면 | 평점 (양방향, 역할별 집계) + 리뷰 목록 API |
| 알림 발송 모듈 실제 구현 → B 인계 | 스케줄러 잡 (미달 알림·자동 마감) + **advisory lock** |

**마일스톤:** 포인트를 충전해 공고를 올리고, 완료 시 지급되고, 규칙 위반 시 제재된다.

---

### Sprint 4 — 환전 + 관리자 (약 2주, 병렬)

| A | B |
|---|---|
| 계좌 등록·암호화 + `StubAccountVerifier` (형식 검사) | **블랙리스트 화면** (제재 목록·조기 해제·해제 이력) |
| 환전 요청 (5,000원·10원 단위·7일 경과) | **공고 관리 화면** (검색·필터·강제 취소) |
| `ExchangeProvider` 추상화 + 환경변수 분기 | 목록 성능 튜닝 (인덱스, 필요 시 `pg_trgm`) |
| **관리자 회원 목록/상세** (평점·리뷰 목록은 B의 API 사용) | 개인정보 파기 배치 (비활성화 후 4개월) |
| **관리자 환전 관리** + `AdminAuditLog` | 예외 화면·에러 UX 정리 |

> 환전은 **실송금 없이 요청 목록 + 승인까지만** 만든다. A의 작업량이 당초 예상보다 줄어드는 대신, 인터페이스 분기(`ACCOUNT_VERIFY_MODE` / `EXCHANGE_MODE`)와 전환 시나리오 테스트에 시간을 쓴다.

> Sprint 4 관리자 화면은 B가 Sprint 1에 만든 `FilterableList`를 양쪽 모두 재사용한다. 여기서 검색·필터를 새로 짜기 시작하면 화면마다 동작이 갈린다.

### Sprint 5 — 마감 (약 1주, 공동)

- Playwright E2E 전 구간 (가입→서명→충전→공고→신청→수락→완료→지급→환전 승인)
- k6 부하 테스트 (인기 공고 동시 신청, 목록 조회)
- 배포 체크리스트: 타임존 4곳 일치, DB utf8, 로그 로테이션, 커넥션 풀 총합, 롤백 절차

**마일스톤:** 끝에서 끝까지 통과 + 관리자가 운영 가능한 상태.

## 4. 의존성 관리 — 서로를 막는 지점

| 지점 | 막는 사람 | 막히는 사람 | 해소 방법 |
|---|---|---|---|
| 인증 Guard | A | B (모든 API) | Sprint 0에서 Mock Guard 제공, Sprint 1 중반 실물 인계 |
| 포인트 원장 | A | B (공고 등록·완료) | Sprint 0에서 Mock Ledger 제공, Sprint 2 후반 실물 인계 |
| 알림 모듈 | A | B (재동의·미달 알림) | Sprint 0에서 Mock, Sprint 3 실물 인계 |
| 공고 상태 | B | A (환전 조건 판정) | Sprint 0 Prisma 스키마에 상태 enum 확정 |
| `User` 테이블 | A | B (FK 참조 전부) | Sprint 0에서 전체 스키마 동시 설계 |
| `FilterableList` | B | A (관리자 목록 전부) | Sprint 1 말에 인계. A의 관리자 화면은 Sprint 4라 여유 있음 |
| 리뷰 목록 API | B | A (회원 상세 화면) | Sprint 3에 B가 API 완성, A는 Sprint 4에 사용 |

**규칙:** 인터페이스 변경은 반드시 사전 합의한다. `packages/shared` 수정은 두 사람 모두의 리뷰를 거친다.

## 5. 협업 규칙

- **브랜치:** `feat/{domain}/{작업명}` — 도메인이 갈려 있어 충돌이 거의 나지 않는다
- **리뷰:** 자기 도메인 안은 셀프 머지 허용. `packages/shared`, Prisma 스키마, 인증, 원장 관련 변경은 **반드시 상대 리뷰**
- **마이그레이션:** Prisma 마이그레이션은 하루 1회 합류 시점을 정해 순서 충돌을 막는다
- **동기화:** 주 2회 15분 — 인터페이스 변경 사항과 막힌 지점만 공유
- **테스트 책임:** 각자 자기 도메인의 유닛·통합 테스트를 함께 작성한다. E2E는 Sprint 4에 공동 작성

## 6. 왜 이 순서인가

1. **인증이 먼저다.** 모든 API가 인증에 의존한다. 다만 Mock으로 가려두고 병렬화한다.
2. **돈은 나중이다.** 포인트 원장은 공고 상태머신이 확정돼야 HOLD/RELEASE 시점을 정할 수 있다. 그래서 Sprint 2에 원장 코어, Sprint 3에 도메인 연결.
3. **버전 정책이 가장 어렵다.** 그래서 스택이 가장 안정된 Sprint 2 한가운데에 놓았다. 더 앞이면 기반이 없고, 더 뒤면 수정할 시간이 없다.
4. **제재는 신청·취소 다음이다.** 경고 스택은 취소 이벤트가 있어야 쌓인다.
5. **환전이 마지막이다.** 지급된 포인트가 있어야 환전할 것이 생긴다. 실송금이 없어 자동화 부담도 없다.
6. **관리자 화면은 도메인이 다 굳은 뒤에 만든다.** 관리자 화면은 모든 도메인을 가로질러 읽기 때문에, 스키마가 흔들리는 동안 만들면 두 번 고치게 된다.
