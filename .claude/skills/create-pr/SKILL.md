# PR 생성

```
작업 완료 (Green·Refactor·security-review 통과)
    ↓ /create-pr
변경 요약 → PR 초안 → [GATE] 승인
    ↓
검증 (빌드·타입·린트·단위·E2E)  ← 실패하면 여기서 중단
    ↓
git push → gh pr create
```

**사용법:** `/create-pr` (인자 없음. 현재 브랜치를 대상으로 한다)

---

## 시작 전 확인

### `main`에서는 PR을 만들 수 없다

```bash
git branch --show-current
```

`main`이면 **멈추고 안내한다.** PR은 브랜치에서 `main`으로 보내는 것이라, `main`에 있으면 대상이 없다.

`CLAUDE.md`의 규칙대로 브랜치를 먼저 만든다.

```bash
git switch -c feat/{domain}/issue-{N}
```

이미 `main`에 커밋해버렸다면 그 커밋을 브랜치로 옮겨야 하는데, 이력을 다루는 일이라 **사람이 판단한다.** 방법만 안내하고 실행하지 않는다.

### 커밋되지 않은 변경이 있으면 멈춘다

```bash
git status --porcelain
```

작업 중인 파일이 남아 있으면 PR에 안 들어간다. 커밋할지 물어본다. **묻지 않고 커밋하지 않는다.**

---

## 실행 순서

### 1. 변경사항을 요약해 PR 초안을 만든다

```bash
git log main..HEAD --oneline
git diff main...HEAD --stat
```

**제목** — commitlint 형식을 따른다. 커밋이 하나면 그 제목을 쓰고, 여러 개면 전체를 아우르는 한 줄로 새로 쓴다.

```
feat: 이메일 인증 코드 발급과 검증을 구현
```

**본문 구조**

```markdown
## 무엇을

(이 PR이 무엇을 하는지 2~3줄. 코드를 안 본 사람이 읽는다고 생각하고 쓴다)

## 왜 이렇게

(구조 판단이 있었으면 그 근거. PRD의 ADR을 참조한다)

- `ADR-AUTH-4`(발급 이력 테이블) 결정에 따라 ~

## 확인한 것

- [x] 단위 테스트 28개 통과
- [x] 타입 검사·린트 통과
- [x] E2E 통과
- [x] AC 5개 전부 커버 (`docs/result/scenarios/issue-1.md`)

## 리뷰어가 봐줬으면 하는 것

(판단이 갈렸던 지점, 자신 없는 부분)

closes #1
```

**`closes #N`을 빠뜨리지 않는다.** 이게 있어야 머지될 때 이슈가 자동으로 닫힌다. 이슈 번호는 브랜치 이름(`.../issue-{N}`)이나 커밋 본문에서 가져온다.

**"확인한 것"에 거짓을 쓰지 않는다.** 아직 안 돌린 것은 체크하지 않는다. 4번에서 실제로 돌린 결과로 채운다.

### 2. 초안을 보여주고 승인받는다

```
[GATE] 초안 승인 없이 다음으로 넘어가지 않는다
```

이 게이트가 **push와 PR 생성까지 함께 승인받는 자리**다. 둘 다 저장소 밖으로 나가는 일이라 `CLAUDE.md`가 확인을 요구한다. 승인을 요청할 때 무엇을 할지 명시한다.

```
승인하시면 다음을 실행합니다:
  1. 검증 (빌드·타입·린트·단위·E2E)
  2. git push origin feat/auth-member/issue-1
  3. gh pr create --base main
```

수정 요청이 오면 초안을 고치고 다시 보여준다.

### 3. 검증을 돌린다

**E2E만 돌리지 않는다.** 어차피 CI가 전부 볼 것이고, 여기서 잡으면 훨씬 빠르다.

```bash
pnpm build && pnpm typecheck && pnpm lint && pnpm test
```

> **빌드가 타입 검사보다 먼저다.** Next 16이 `LayoutProps` 같은 전역 타입을 `next build` 때 생성하므로, 순서를 바꾸면 `apps/web`에서 실패한다.

하나라도 실패하면 **PR을 만들지 않고 멈춘다.** 실패 내용을 그대로 보고한다.

### 4. E2E를 돌린다

```bash
pnpm --filter @fixer/web test:e2e
```

**Playwright가 설치돼 있지 않으면** (`apps/web/playwright.config.ts`가 없으면) **멈추지 않는다.** PR 본문의 "확인한 것"에 `E2E 미실행 (Playwright 미설정)`을 적고 진행한다. 조용히 넘어가지 않되, 사람을 기다리지도 않는다.

**설정이 없는 것과 실패한 것은 다르다.** 없는 것은 아직 안 만든 상태고, 실패는 사용자가 그 흐름을 실제로 못 간다는 신호다. 앞은 적어 두고 넘어가지만 뒤는 5번에서 막는다.

여기서 사람에게 물으면 `/tdd-auto-loop`이 답할 사람이 없어 멈춘다. 그러면 이슈마다 브랜치만 쌓이고 PR이 하나도 안 생긴다.

E2E를 먼저 만들고 싶으면 `/e2e-write {도메인}`으로 만든 뒤 다시 온다.

**Docker Desktop이 꺼져 있으면** API가 DB에 붙지 못해 `webServer` 대기에서 멈춘다. 켜라고 안내한다.

### 5. E2E가 실패하면 PR을 만들지 않는다

**여기서 중단한다.** 그리고 아래 절차를 안내한다.

#### ① 실패 지점을 눈으로 확인한다

```bash
pnpm --filter @fixer/web exec playwright show-report
```

Trace Viewer에서 어느 단계에서 멈췄는지, 그 시점의 화면과 네트워크 요청을 본다.

#### ② 어느 계층에서 깨졌는지 판별한다

| 신호                         | 계층       | 다음                                       |
| ---------------------------- | ---------- | ------------------------------------------ |
| API 응답이 4xx·5xx           | **API**    | 해당 서비스의 단위 테스트에 그 조건을 추가 |
| API는 200인데 화면이 안 바뀜 | **렌더링** | 컴포넌트 테스트에 그 상태를 추가           |
| 화면은 바뀌었는데 값이 틀림  | **로직**   | 서비스 단위 테스트에 그 입력을 추가        |
| 요청 자체가 안 나감          | **연결**   | 폼 제출·핸들러 연결 확인                   |

Trace의 **Network 탭**이 이 판별의 핵심이다. 요청이 나갔는지, 응답이 뭐였는지가 계층을 갈라준다.

#### ③ 해당 단위 테스트에 케이스를 추가한다 (Red)

E2E가 잡은 구멍을 **더 빠른 테스트로 내린다.** 같은 버그가 다음에 나면 3초짜리 단위 테스트가 먼저 잡는다.

#### ④ 구현을 고친다 (Green) → 다시 `/create-pr`

---

> ⚠️ **E2E 코드를 고쳐서 통과시키는 것은 금지한다.**
>
> 선택자를 바꾸거나 단언을 느슨하게 하거나 `waitForTimeout`을 넣어 넘기는 것 전부 해당한다. E2E가 빨간불이라는 건 **사용자가 실제로 그 흐름을 못 간다**는 뜻이고, 테스트를 고치면 그 사실만 안 보이게 된다. 근본 원인 회피다.
>
> 예외는 하나뿐이다. **E2E 자체가 잘못 쓰였을 때** — 없는 버튼을 찾고 있거나, 시나리오가 실제 요구와 다를 때. 이 경우에도 고치기 전에 **왜 잘못 쓰였는지 보고하고 승인받는다.**

### 6. push하고 PR을 만든다

```bash
git push -u origin $(git branch --show-current)
```

```bash
gh pr create --base main --title "<제목>" --body-file <본문파일>
```

**base는 `main`이 기본이다.** 다만 선행 이슈가 아직 머지 전이면 그 브랜치를 base로 한다. (`CLAUDE.md` 브랜치 규칙)

라벨을 이슈와 맞춰 단다.

```bash
gh pr edit <번호> --add-label "담당:A-최동훈" --add-label "auth-member"
```

### 7. 결과를 보고한다

- PR URL
- 검증 결과 (무엇을 돌렸고 무엇을 안 돌렸는지)
- 리뷰어가 봐야 할 지점
- **E2E를 건너뛰었다면 그 사실**

---

## 제약

- **`main`에서 실행하지 않는다**
- **초안 승인 전에 push하지 않는다.** push와 PR 생성은 저장소 밖으로 나가는 일이라 `CLAUDE.md`가 확인을 요구한다
- **검증이 실패하면 PR을 만들지 않는다.** "일단 올리고 CI에서 보자"는 리뷰어의 시간을 쓴다
- **E2E를 고쳐서 통과시키지 않는다**
- 커밋되지 않은 변경이 있으면 묻는다. 자동으로 커밋하지 않는다
- `--force` push를 쓰지 않는다
- PR 본문에 비밀값·토큰을 넣지 않는다

---

## 이 저장소의 흐름에서 어디쯤인가

`CLAUDE.md`의 TDD 이슈 사이클 **7번**이다.

```
1 /test-scenarios → 2 /tdd-red → 3 /tdd-green → 4 @ac-verifier
→ 5 /tdd-refactor → 6 /security-review → 7 /create-pr → squash merge → 이슈 클로즈
```

**앞 단계를 건너뛰고 오지 않았는지 확인한다.** 특히 4번(`@ac-verifier`)은 "테스트는 통과하는데 AC가 안 채워진" 상태를 잡는 단계라, 빠뜨리면 이슈를 닫을 근거 없이 PR이 올라간다.

`docs/result/scenarios/issue-{N}.md`의 체크박스가 전부 `[x]`인지 보면 진도를 알 수 있다.

---

## 흔한 실수

- **`main`에서 PR을 만들려 하기.** 대상이 없다
- **검증 실패를 무시하고 올리기.** CI가 어차피 잡고, 리뷰어는 그때까지 기다린다
- **E2E를 고쳐서 통과시키기.** 이 스킬이 가장 강하게 막는 것이다
- **`closes #N` 누락.** 머지해도 이슈가 안 닫혀 수동으로 정리하게 된다
- **"확인한 것"에 안 돌린 항목 체크.** 리뷰어가 그걸 믿고 안 본다
- **초안 없이 바로 push.** 승인 게이트가 push까지 포함한다는 점을 잊지 않는다
- **PR 본문이 커밋 목록 나열.** 커밋은 `git log`로 보면 된다. 본문에는 **왜**를 쓴다
