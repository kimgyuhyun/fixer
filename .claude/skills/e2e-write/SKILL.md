# E2E 테스트 작성

PRD의 **사용자 스토리**를 브라우저에서 도는 시나리오로 옮긴다.

```
docs/result/prd/{도메인}.md  §2 사용자 스토리
    ↓ /e2e-write {도메인}
apps/web/e2e/{도메인}.spec.ts   →  브라우저로 실행 확인
```

**사용법:** `/e2e-write auth-member` (도메인 이름)

도메인 이름이 없으면 물어본다. `docs/result/prd/`에 있는 것 중에서 고른다.

---

## E2E는 무엇을 검증하는가

**"규칙이 맞는가"가 아니라 "사용자가 끝까지 갈 수 있는가"를 본다.**

E2E는 느리고, 잘 깨지고, 실패했을 때 원인을 찾기 어렵다. 그 비용을 치를 값어치가 있는 것만 담는다.

| 검증 대상                                 | 단위·통합 | E2E | 왜                                               |
| ----------------------------------------- | --------- | --- | ------------------------------------------------ |
| 59초 vs 60초 쿨다운 경계                  | ✅        | ❌  | 브라우저 없이 훨씬 빠르고 정확하게 검증된다      |
| 에러 코드 매핑 (`MEMBER_RESEND_COOLDOWN`) | ✅        | ❌  | 서비스 계층의 일이다                             |
| 코드가 해시로 저장되는가                  | ✅        | ❌  | 화면에서 보이지 않는다                           |
| 이메일 입력 → 코드 입력 → 다음 화면       | ❌        | ✅  | **화면이 실제로 이어지는가**는 브라우저로만 안다 |
| 로그아웃 후 뒤로가기 차단                 | ❌        | ✅  | bfcache는 진짜 브라우저에서만 재현된다           |
| 필터 걸고 새로고침·뒤로가기               | ❌        | ✅  | URL·히스토리 동작                                |
| 서명 캔버스 → PDF에 서명이 박히는가       | ❌        | ✅  | 터치 좌표와 렌더링                               |

**같은 것을 두 곳에서 검증하지 않는다.** 단위 테스트가 잡는 것을 E2E에 또 넣으면, 규칙이 바뀔 때 두 곳을 고쳐야 하고 E2E 실행 시간만 길어진다.

의심스러우면 이렇게 묻는다. **"브라우저 없이 검증할 수 있는가?"** 있으면 단위 테스트의 몫이다.

### 개수

**도메인당 3~5개.** 사용자 스토리가 8개라도 E2E가 8개가 되지 않는다.

- 가장 중요한 **정상 흐름 하나**를 끝에서 끝까지
- 브라우저 없이 확인 불가능한 것 2~3개
- 나머지는 단위·통합에 맡긴다

---

## 실행 순서

### 1. 사용자 스토리를 읽는다

`docs/result/prd/{도메인}.md` §2

우리 스토리는 이 형식이다.

```
**구직자로서** 이메일 인증을 거쳐 가입하고 싶다. 실제로 받을 수 있는 주소여야 ~ 때문이다.
```

- **앞부분(누가·무엇을)** → 시나리오의 행동이 된다
- **뒷부분(왜)** → 무엇을 단언해야 하는지 알려준다. "재동의 요청이 도달하기 때문"이면 **인증된 상태가 실제로 남는지**가 확인 대상이다

`docs/result/prd/{도메인}.md`의 **Out of Scope**도 함께 읽는다. 거기 있는 것은 E2E로도 쓰지 않는다.

### 2. 어떤 스토리를 E2E로 올릴지 고른다

위 "무엇을 검증하는가" 기준으로 거른다. 고른 것과 **뺀 것과 그 이유**를 함께 보고한다.

```
[GATE] 어떤 시나리오를 쓸지 승인받은 뒤 코드를 쓴다
```

E2E는 한번 쓰면 계속 돌아가는 비용이라, 무엇을 담을지가 어떻게 쓸지보다 중요하다.

### 3. Playwright 설정이 없으면 만든다

이 저장소에는 **아직 Playwright가 설치돼 있지 않다.** 첫 실행이면 설치와 설정이 이 스킬의 범위 안이다 — 돌릴 수 없으면 작성해도 의미가 없다.

```bash
pnpm --filter @fixer/web add -D @playwright/test
pnpm --filter @fixer/web exec playwright install chromium
```

`apps/web/playwright.config.ts`

```typescript
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './e2e',
  // 같은 DB를 공유하므로 병렬로 돌리면 서로의 데이터를 밟는다.
  fullyParallel: false,
  workers: 1,
  retries: process.env.CI ? 2 : 0,

  use: {
    baseURL: 'http://localhost:3000',
    // 실패했을 때 원인을 찾을 증거를 남긴다. E2E는 재현이 어렵다.
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
  },

  projects: [{ name: 'chromium', use: { ...devices['Desktop Chrome'] } }],

  // web과 api를 함께 띄운다. Next가 /api/*를 3001로 프록시하므로
  // 브라우저에서는 같은 출처가 되어 쿠키가 그대로 붙는다.
  webServer: [
    {
      command: 'pnpm --filter @fixer/api dev',
      url: 'http://localhost:3001/api/health',
      reuseExistingServer: !process.env.CI,
      timeout: 120_000,
    },
    {
      command: 'pnpm --filter @fixer/web dev',
      url: 'http://localhost:3000',
      reuseExistingServer: !process.env.CI,
      timeout: 120_000,
    },
  ],
});
```

`api/health`를 준비 신호로 쓴다. DB 연결까지 확인해주므로 "서버는 떴는데 DB가 아직"인 상태에서 테스트가 시작되는 것을 막는다.

`package.json`에 스크립트를 더한다.

```json
"test:e2e": "playwright test",
"test:e2e:ui": "playwright test --ui"
```

### 4. 시나리오를 작성한다

파일 위치와 이름:

```
apps/web/
├── playwright.config.ts
└── e2e/
    ├── fixtures/          로그인 등 공통 준비
    └── {도메인}.spec.ts
```

**확장자를 `.spec.ts`로 쓴다.** 단위 테스트는 `.test.ts`다. 둘을 구분해야 Vitest가 E2E를 잘못 수집하지 않고, 파일명만 보고도 어느 쪽인지 안다.

`describe`는 사용자 스토리 단위로, `test`는 그 스토리의 구체적 흐름으로 묶는다.

### 5. 실행해서 실제로 통과하는지 본다

```bash
pnpm --filter @fixer/web test:e2e
```

**Docker Desktop이 켜져 있어야 한다.** API가 DB에 붙지 못하면 `webServer`의 health 체크에서 멈춘다.

디버깅이 필요하면 UI 모드를 쓴다.

```bash
pnpm --filter @fixer/web test:e2e:ui
```

### 6. 결과를 보고한다

- 쓴 시나리오와 각각이 어느 사용자 스토리에서 왔는지
- **E2E로 올리지 않은 스토리와 그 이유**
- 실행 결과
- 막힌 것 — 화면이 아직 없어서 못 쓴 시나리오가 있으면 명시

## 지킬 원칙

### 사용자가 하는 행동만 쓴다

DB를 직접 열거나 내부 상태를 확인하지 않는다. **화면에 보이는 것과 사용자가 누르는 것**만으로 시나리오가 성립해야 한다.

내부를 봐야만 검증되는 것은 애초에 단위·통합 테스트의 몫이다.

### 선택자는 역할과 이름으로 잡는다

```typescript
// 좋다 — 사용자가 화면을 인식하는 방식 그대로
await page.getByRole('button', { name: '인증 코드 받기' }).click();
await page.getByLabel('이메일').fill(email);
await expect(page.getByText('인증되었습니다')).toBeVisible();

// 나쁘다 — 스타일을 고치면 깨진다
await page.locator('.btn-primary').click();
await page.locator('div > form > input:nth-child(2)').fill(email);
```

CSS 클래스와 DOM 구조는 리팩토링에서 바뀐다. **역할과 이름은 잘 안 바뀐다.** 우리 `Input` 컴포넌트는 `label`과 `htmlFor`를 붙이므로 `getByLabel`이 그대로 동작한다.

`data-testid`는 마지막 수단이다. 역할·이름으로 잡을 수 없을 때만 쓰고, 왜 필요했는지 주석을 남긴다.

### 기다림을 직접 만들지 않는다

```typescript
// 나쁘다 — 느린 기계에서 깨지고, 빠른 기계에서 시간을 버린다
await page.waitForTimeout(2000);

// 좋다 — 조건이 만족될 때까지 자동으로 기다린다
await expect(page.getByText('발송되었습니다')).toBeVisible();
```

Playwright의 단언은 조건이 참이 될 때까지 재시도한다. `waitForTimeout`은 **디버깅할 때 말고는 쓰지 않는다.**

### 테스트끼리 독립적이어야 한다

각 테스트가 자기 데이터를 만들고, 실행 순서에 기대지 않는다.

```typescript
// 테스트마다 다른 이메일. 앞 테스트가 남긴 계정과 부딪히지 않는다
const email = `e2e-${Date.now()}-${Math.random().toString(36).slice(2, 8)}@example.com`;
```

"1번 테스트가 만든 계정을 2번이 쓴다"는 구조를 만들지 않는다. 1번이 깨지면 2번도 같이 죽어서 원인이 흐려진다.

### 외부로 실제 요청을 보내지 않는다

메일 발송·결제·주소 API가 진짜로 나가면 안 된다. `spec-fixed.md`가 정한 대로 테스트 모드나 스텁을 쓴다.

**인증 코드를 E2E가 어떻게 읽을 것인가는 아직 정해지지 않았다.** 화면에는 안 보이고 메일은 안 나가기 때문이다. 이 도메인을 처음 쓸 때 셋 중 하나를 정하고 그 결정을 보고한다.

| 방법                                    | 장점                  | 단점                                |
| --------------------------------------- | --------------------- | ----------------------------------- |
| 테스트 모드에서 고정 코드 발급          | 가장 단순             | 실제 발급 경로를 안 탄다            |
| 발송 내역을 읽는 테스트 전용 엔드포인트 | 실제 경로를 탄다      | 운영에 나가면 안 되는 경로가 생긴다 |
| 스텁 메일러가 파일·로그에 기록          | 운영 경로에 영향 없음 | 테스트가 파일을 읽어야 한다         |

### 로그인은 재사용한다

모든 테스트가 가입·로그인을 반복하면 E2E가 몇 배로 느려진다. 로그인 상태를 `storageState`로 저장해 재사용하고, **가입 흐름 자체를 검증하는 시나리오에서만** 처음부터 밟는다.

---

## 제약

- **단위·통합 테스트가 검증하는 것을 다시 쓰지 않는다**
- 도메인당 3~5개를 넘기지 않는다. 넘겨야 한다고 판단되면 이유와 함께 보고한다
- **구현 코드를 고치지 않는다.** 화면에 필요한 것이 없으면 그 사실을 보고한다 — E2E를 통과시키려고 `src`를 손대는 것은 이 스킬의 일이 아니다
- `data-testid`를 붙이려고 컴포넌트를 고치는 것도 보고 대상이다
- PRD의 Out of Scope에 있는 것은 쓰지 않는다
- 실제 계정·실제 결제·실제 메일을 쓰지 않는다

## 이 저장소에서 E2E가 꼭 필요한 것들

`docs/result/issues.md`에서 **브라우저 없이는 검증이 불가능한** 것들이다. E2E를 쓸 때 우선순위로 둔다.

| 이슈                              | 왜 E2E여야 하나                                            |
| --------------------------------- | ---------------------------------------------------------- |
| #5 로그아웃 후 뒤로가기 차단      | bfcache는 진짜 브라우저에서만 재현된다                     |
| #7 서명 캔버스 → PDF 병합         | 터치 좌표가 PDF에 정확히 옮겨지는지                        |
| #13 필터 유지 (새로고침·뒤로가기) | URL과 히스토리 동작                                        |
| #12 공고 등록 전체 흐름           | 충전 → 등록 → 목록까지 이어지는가                          |
| 전 구간                           | 가입 → 서명 → 충전 → 공고 → 신청 → 수락 → 완료 → 환전 승인 |

마지막 전 구간 시나리오는 **하나만** 둔다. 이게 깨지면 어딘가 끊어졌다는 뜻이고, 어디서 끊어졌는지는 단위 테스트가 알려준다.

## 흔한 실수

- **단위 테스트를 E2E로 옮겨 쓰기.** 경계값 20개를 브라우저로 돌리면 5분이 걸리고 자주 깨진다
- **`waitForTimeout`으로 때우기.** 느린 기계에서 깨지고 빠른 기계에서 시간을 버린다
- **CSS 클래스·DOM 경로 선택자.** 스타일 리팩토링 한 번에 전부 깨진다
- **테스트끼리 데이터를 물려주기.** 앞이 깨지면 뒤도 같이 죽어 원인이 흐려진다
- **사용자 스토리 수만큼 E2E 만들기.** 8개 스토리가 8개 E2E가 되면 아무도 안 돌리게 된다
- **실패해도 증거가 안 남게 두기.** `trace`와 `screenshot`을 켜둔다. E2E 실패는 재현이 어렵다
- **E2E를 통과시키려고 구현을 고치기.** 화면이 없으면 없다고 보고하는 게 맞다
