# TDD Green — 최소 구현

실패 중인 테스트를 **하나씩** 통과시킨다.

```
테스트 28개 전부 실패 🔴  (tdd-red 산출물)
    ↓ /tdd-green {N}
테스트 하나 → 구현 → 전체 실행 → 체크박스 [x]  ← 반복
    ↓
전부 통과 🟢 + 커버리지 보고
    ↓ @ac-verifier {N} → /tdd-refactor {N}
```

**사용법:** `/tdd-green 12` (GitHub 이슈 번호)

번호가 없으면 물어본다. 실패 테스트가 없으면 `/tdd-red {N}`을 먼저 하자고 안내한다.

---

## "최소"가 무슨 뜻인가

**테스트가 요구하지 않는 것을 만들지 않는다는 뜻이다.** 코드를 못나게 쓰라는 뜻이 아니다.

구분이 중요하다.

|         | 예                                    | 판정                                                        |
| ------- | ------------------------------------- | ----------------------------------------------------------- |
| ✅ 최소 | 테스트가 요구하는 분기만 구현         | Green                                                       |
| ✅ 최소 | 읽기 좋은 이름, 적절한 함수 분리      | Green (구조 개선은 Refactor지만 처음부터 못 쓸 필요는 없다) |
| ❌ 초과 | 테스트에 없는 옵션 파라미터 추가      | 검증되지 않는 코드가 생긴다                                 |
| ❌ 초과 | "나중에 필요할 것 같아서" 만든 추상화 | 요구가 오면 그때 만든다                                     |
| ❌ 초과 | 로깅·캐싱·재시도를 스스로 판단해 추가 | 이슈에 없으면 다음 이슈다                                   |

**테스트에 없는 코드는 아무도 검증하지 않는다.** 그게 나중에 조용히 틀린 채로 남는다.

반대로 **테스트를 속여서 통과시키는 것도 금지다.** 특정 입력에만 맞는 값을 하드코딩해 넘어가면, 그 테스트는 다음 이슈에서 무의미해진다. 우리 시나리오는 정상·경계·예외를 함께 잡으므로 하드코딩으로는 대개 통과하지 않는다 — 통과했다면 시나리오가 부족한 것이니 보고한다.

## 실행 순서

### 1. 실패 테스트 목록을 확인한다

```bash
pnpm test
```

어떤 테스트가 몇 개 실패 중인지 적어둔다. 이 숫자가 진도의 기준이 된다.

### 2. collect 실패를 먼저 잡는다

**시나리오 문서의 체크박스 수와 테스트 러너가 보고하는 테스트 수를 비교한다.**

```bash
grep -c '^- \[[ x]\] \[' docs/result/scenarios/issue-{N}.md
```

두 숫자가 다르면 **테스트가 수집(collect)되지 않은 것**이다. 대개 import 대상 모듈이 없어서 파일 전체가 로드에 실패한 경우다. 이때는 시그니처만 있는 stub 파일을 만들어 전체 테스트가 인식되게 한다.

```typescript
export class XxxService {
  async method(param: Type): Promise<Result> {
    throw new Error('not implemented');
  }
}
```

**이 단계를 건너뛰면 "28개 중 5개 통과"라고 보고하는데 실제로는 23개가 실행조차 안 된 상태**가 된다. 숫자가 맞는지 먼저 확인한다.

### 3. 디자인 컨텍스트를 읽는다 (화면이 있는 이슈만)

이 저장소는 **일반 CSS**를 쓴다. Tailwind가 아니다.

| 볼 것                                | 무엇이 있나                                                      |
| ------------------------------------ | ---------------------------------------------------------------- |
| `apps/web/src/app/globals.css`       | 색·간격·radius·폰트 **토큰**. 새 색을 만들지 말고 여기 값을 쓴다 |
| `docs/result/scenarios/issue-{N}.md` | "디자인 참고" 섹션이 있으면 함께 확인                            |
| `CLAUDE.md`                          | 스타일링 컨벤션                                                  |
| `docs/result/spec-fixed.md` §10      | CSS 규약과 **예외가 허용된 화면 목록**                           |

지켜야 할 것:

- 색·간격은 **`var(--color-*)`, `var(--space-*)`** 토큰만 쓴다. 하드코딩한 hex나 px를 넣지 않는다
- 화면별 스타일은 `*.module.css`에, 토큰은 `globals.css`에만
- 모바일 우선(`min-width` 미디어쿼리), 터치 목표 최소 44px
- 표는 정렬 규약을 따른다 — 가변 텍스트=좌, 형식 자료=중앙, 숫자=우
- **문서에 없는 시각적 요소를 임의로 추가하지 않는다.** 그림자·애니메이션·아이콘을 스스로 판단해 넣지 않는다

디자인 문서가 없으면 이 단계를 건너뛰고 토큰과 컨벤션만 따른다.

### 4. 첫 번째 실패 테스트를 통과시키는 코드만 쓴다

**하나만 고른다.** 여러 개를 한 번에 통과시키려 하면 어느 코드가 어느 테스트를 위한 것인지 흐려진다.

실패 메시지를 먼저 읽는다. `expected 1 to be 2`가 말해주는 것이 요구사항이다.

### 5. 전체 테스트를 돌려 통과와 회귀를 확인한다 — 피드백 루프

```bash
pnpm test
```

**해당 테스트 하나가 아니라 전체를 돌린다.** 방금 쓴 코드가 다른 테스트를 깨뜨렸는지(회귀) 여기서 잡는다.

- **통과 + 회귀 없음** → 6번으로
- **아직 실패** → 에러 메시지를 읽고 원인을 분석해 코드를 고친 뒤 5번을 다시 실행한다
- **다른 테스트가 깨졌다** → 방금 쓴 코드가 원인이다. 되돌리고 다시 접근한다

**같은 테스트에 5회까지만 시도한다.** 5회를 넘기면 멈추고 개발자에게 보고한다. 다섯 번을 고쳐도 안 되면 대개 코드가 아니라 **시그니처나 시나리오가 틀린 것**이므로, 혼자 더 시도해봐야 엉뚱한 방향으로 간다.

보고할 때 담을 것: 실패 메시지, 시도한 접근 5가지, 어디서 막혔다고 보는지.

### 6. 시나리오 문서의 해당 항목을 체크한다

`docs/result/scenarios/issue-{N}.md`에서 통과시킨 시나리오를 `- [ ]` → `- [x]`로 바꾼다.

진도가 문서에 남아 세션이 끊겨도 이어서 할 수 있다.

### 7. 다음 실패 테스트로 이동해 4번부터 반복한다

### 8. 전부 통과하면 커버리지를 측정한다

```bash
pnpm --filter @fixer/api exec vitest run --coverage
```

미커버 라인을 확인하고 **개발자에게 보고한다.** 판단할 것은 둘 중 하나다.

- **시나리오에서 빠진 케이스** → 시나리오를 보강하자고 제안한다
- **테스트가 요구하지 않는데 만든 코드** → 지우는 게 맞다. 4번의 "최소" 원칙을 어긴 것이다

**커버리지를 올리려고 테스트를 추가하지 않는다.** 숫자를 채우려고 쓴 테스트는 아무 의미가 없다. 커버리지는 참고용 지표지 목표가 아니다.

### 9. 결과를 요약한다

- 통과시킨 테스트 수 / 전체
- 만든·고친 파일 목록
- 커버리지와 미커버 구간에 대한 판단
- **막혀서 5회 루프를 돈 것이 있으면** 무엇을 어떻게 풀었는지
- 구현하면서 발견한 시나리오·시그니처의 문제

## 제약

- **테스트에 없는 기능을 구현하지 않는다**
- **테스트 파일을 고치지 않는다.** 테스트가 틀렸다고 판단되면 멈추고 말한다 — 테스트를 고쳐서 통과시키는 순간 TDD가 무너진다
- 시그니처를 바꾸지 않는다. 바꿔야 하면 `issue-{N}.md`부터 고치는 게 순서다
- 불필요한 추상화를 만들지 않는다. 인터페이스가 하나뿐이면 인터페이스로 뽑지 않는다
- 디자인 문서에 없는 시각적 요소를 임의로 추가하지 않는다
- **`.env`나 비밀값을 코드에 넣지 않는다.** 환경변수로 읽고 `.env.example`에 이름만 추가한다

## 이 저장소에서 구현할 때

| 계층         | 따를 패턴                                                                              |
| ------------ | -------------------------------------------------------------------------------------- |
| 공유 타입    | `packages/shared/src/health.ts` — zod 스키마 하나가 API 검증과 웹 타입을 함께 책임진다 |
| API 컨트롤러 | `apps/api/src/health/health.controller.ts` — 응답을 zod로 `parse`해서 반환             |
| DB 접근      | `apps/api/src/prisma/prisma.service.ts` — Prisma 7 드라이버 어댑터                     |
| CSS          | `apps/web/src/app/globals.css` 토큰 + `*.module.css`                                   |

**PRD의 ADR을 먼저 읽는다.** 구조 결정이 이미 내려져 있으면 그대로 따른다. 어긋나게 구현하면 나중에 뜯는다.

**Prisma 모델을 추가하면 마이그레이션을 만든다.** 운영 DB에 직접 DDL을 실행하지 않는다.

```bash
pnpm db:migrate
```

**DB가 필요한 테스트는 Docker Desktop이 켜져 있어야 한다.** 꺼져 있으면 `Could not find a working container runtime strategy`로 실패한다.

## 흔한 실수

- **여러 테스트를 한 번에 통과시키기.** 어느 코드가 어느 요구를 위한 것인지 흐려진다
- **해당 테스트만 돌리기.** 회귀를 못 잡는다. 매번 전체를 돌린다
- **테스트를 고쳐서 통과시키기.** 가장 하기 쉬운 실수이자 가장 나쁜 실수다
- **하드코딩으로 넘기기.** 통과했다면 오히려 시나리오가 부족하다는 신호다
- **5회 루프를 무시하고 계속 시도.** 대개 시그니처가 틀린 것이니 사람에게 물어본다
- **커버리지 숫자를 채우려고 테스트 추가.** 지표를 목표로 삼는 순간 지표가 망가진다
- **체크박스를 안 채우기.** 세션이 끊기면 어디까지 했는지 모른다
