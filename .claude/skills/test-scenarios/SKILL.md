# 테스트 시나리오 도출

GitHub 이슈 하나를 **TDD를 시작할 수 있는 상태**로 만든다.

```
GitHub 이슈 (AC 포함)
    ↓ 1~3단계 — 시그니처 확정          [GATE]
issue-{N}.md 상단
    ↓ 4~7단계 — 시나리오 도출 + AC 대조 [GATE]
issue-{N}.md 하단
    ↓
/tdd-red — 실패하는 테스트 작성
```

**사용법:** `/test-scenarios 12` (GitHub 이슈 번호)

번호가 없으면 물어본다. 추측해서 진행하지 않는다.

---

## 여기서 코드는 쓰지 않는다

이 스킬은 **구현 코드도, 테스트 코드도 쓰지 않는다.** 시그니처와 시나리오라는 두 가지 문서만 만든다.

이유가 있다. 시그니처가 흔들린 채로 Red(실패하는 테스트)를 쓰면, Green(구현) 단계에서 "아 이 함수는 이 인자를 받아야 하네" 하면서 **테스트를 다시 쓰게 된다.** 그러면 테스트가 구현을 검증하는 게 아니라 구현을 따라가게 되고, TDD의 이점이 사라진다.

시그니처를 먼저 못 박는 것이 이 스킬의 존재 이유다.

예외: 문서에 넣는 **타입 선언과 시그니처 예시**는 당연히 쓴다. 파일로 저장하는 건 `issue-{N}.md` 하나뿐이다.

---

## 용어 표기 규칙

이 저장소의 다른 문서와 같은 규칙을 따른다. 기술 용어가 처음 등장할 때는 **`용어(한 줄 설명)`** 형태로 쓴다.

```
zod(런타임에 데이터 모양을 검사하고 TypeScript 타입까지 만들어주는 라이브러리)
DTO(계층 사이로 데이터를 옮길 때 쓰는 형태 정의)
```

같은 문서에서 두 번째부터는 그냥 쓴다. 용어 사전은 `.claude/skills/feature-planner/references/project-conventions.md`에 있으니 거기서 설명을 가져다 쓰고, 없으면 새로 쓴 뒤 거기에 추가한다.

읽는 사람이 문서를 읽다 말고 검색하러 나가지 않게 하는 것이 목적이다.

## 실행 순서

### 1. 시그니처를 확정한다

**읽을 것 세 가지:**

```bash
gh issue view {N}
```

- **GitHub 이슈** — 제목, 설명, AC, 담당, 선행 이슈
- **해당 도메인 PRD** — `docs/result/prd/{도메인}.md`. 이슈 본문 마지막 줄에 경로가 적혀 있다. 여기의 **기술 결정(ADR)** 섹션이 구조를 정해두었으므로 시그니처가 그 결정과 어긋나면 안 된다
- **코드베이스** — 기존 패턴을 따르기 위해

**확정할 것:**

| 항목           | 내용                           |
| -------------- | ------------------------------ |
| 함수 시그니처  | 이름, 파라미터 타입, 반환 타입 |
| 에러 케이스    | 어떤 상황에서 무엇을 던지는지  |
| 컴포넌트 Props | 화면이 있는 이슈만             |
| zod 스키마     | 요청·응답 검증이 필요한 경우   |

**기존 패턴을 따른다.** 이 저장소의 현재 관습:

| 계층         | 참조 파일                                       | 패턴                                                      |
| ------------ | ----------------------------------------------- | --------------------------------------------------------- |
| API 컨트롤러 | `apps/api/src/health/health.controller.ts`      | Nest 컨트롤러가 응답을 zod 스키마로 `parse`해서 반환      |
| 공유 타입    | `packages/shared/src/health.ts`                 | zod 스키마 **하나가** API 검증과 웹 타입을 동시에 책임짐  |
| DB 접근      | `apps/api/src/prisma/prisma.service.ts`         | Prisma 7 드라이버 어댑터. 생성물은 `src/generated/prisma` |
| 화면 스타일  | `apps/web/src/app/globals.css` + `*.module.css` | 토큰은 `globals.css`에만                                  |

저장소가 자라면 이 표보다 **최근에 자리잡은 패턴**이 우선이다. 같은 계층의 최신 파일을 먼저 본다.

**에러 케이스는 이슈의 AC에서 가져온다.** AC에 `MEMBER_VERIFICATION_CODE_EXPIRED` 같은 코드가 이미 적혀 있으면 그대로 쓴다. AC에 없는 에러를 새로 만들면 그 에러는 테스트로 검증되지 않는다.

**시그니처를 쓸 때 지킬 것:**

- 반환 타입에 `any`를 쓰지 않는다. 모양이 안 정해졌다는 뜻이므로 정하고 넘어간다
- 파라미터가 3개를 넘으면 객체 하나로 묶는 것을 검토한다
- 비동기면 `Promise<T>`를 명시한다
- **이슈 범위 밖의 시그니처는 만들지 않는다.** PRD의 Out of Scope를 확인한다

### 2. 시그니처를 개발자에게 보여주고 승인받는다

```
[GATE] 시그니처를 확정할 때까지 다음 단계로 넘어가지 않는다
```

보여줄 때 함께 밝힐 것:

- **이 시그니처가 따르는 ADR** — "PRD의 ADR-JOB-1(스냅샷 저장) 결정에 따라 `getVersion(id, version)`이 전문을 반환합니다"
- **판단이 갈렸던 지점** — 대안이 있었으면 왜 이걸 골랐는지 한 줄
- **이슈 범위 밖으로 미룬 것** — 있으면 명시

승인 없이 4단계로 넘어가면, 잘못된 시그니처에서 시나리오를 뽑고 그 시나리오로 테스트를 써서 **세 겹으로 잘못된 것**을 만들게 된다.

### 3. 승인된 시그니처를 기록한다

`docs/result/scenarios/issue-{N}.md` **상단**에 쓴다. 폴더가 없으면 만든다.

파일 형식은 아래 "산출물 형식"을 그대로 따른다.

### 4. 시그니처를 기반으로 테스트 시나리오를 도출한다

**형식:**

```
[정상] 함수명 — should [기대동작] when [조건]
[경계] 함수명 — should [기대동작] when [조건]
[예외] 함수명 — should [기대동작] when [조건]
```

**분류 기준:**

| 분류     | 무엇을 잡는가                 | 예                                                      |
| -------- | ----------------------------- | ------------------------------------------------------- |
| **정상** | 의도한 대로 흘러가는 경우     | 유효한 코드를 입력하면 인증된다                         |
| **경계** | 값의 끝, 개수의 끝, 시간의 끝 | 정확히 10분 지난 코드, 정원이 1자리 남은 공고, 0건일 때 |
| **예외** | 실패해야 하는 경우            | 만료된 코드, 잔액 부족, 권한 없음                       |

**경계를 빠뜨리기 쉽다.** 시그니처의 각 파라미터마다 "이 값의 끝은 어디인가"를 한 번씩 물어본다. 숫자면 0과 최대값, 배열이면 빈 배열, 시간이면 정확히 그 시각, 문자열이면 빈 문자열과 최대 길이.

**동시성이 걸린 이슈는 경계에 반드시 넣는다.** "두 요청이 동시에 왔을 때 하나만 성공한다"는 나중에 테스트로 옮기기 어려우므로 여기서 미리 문장으로 못 박는다.

**시나리오는 구현 방법을 말하지 않는다.** "트랜잭션으로 감싼다"가 아니라 "동시에 두 번 호출해도 한 번만 기록된다"라고 쓴다. 구현은 Green 단계에서 정한다.

**테스트 코드는 쓰지 않는다.** 문장까지다.

**시나리오는 체크박스(`- [ ]`)로 쓴다.** `/tdd-green`이 하나씩 통과시킬 때마다 `[x]`로 바꾸며 진도를 표시하고, 체크박스 총 개수와 테스트 러너가 보고하는 테스트 수를 대조해 누락을 잡는다.

### 5. 시나리오를 기록한다

같은 파일 `issue-{N}.md` **하단**에 추가한다.

### 6. GitHub 이슈의 AC와 대조한다

```bash
gh issue view {N}
```

AC 목록을 읽고 **모든 AC가 최소 1개 이상의 시나리오로 커버되는지** 확인한다.

**대조표를 만든다.** 이게 이 단계의 산출물이다.

| AC                                                 | 커버하는 시나리오                                                                                                                              |
| -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Given 유효한 코드, When 입력하면, Then 인증된다    | `[정상] verifyCode — should mark email verified when code matches`                                                                             |
| Given 10분 지난 코드, When 입력하면, Then 거절된다 | `[경계] verifyCode — should reject when code is exactly 10 minutes old`<br>`[예외] verifyCode — should throw EXPIRED when code is past expiry` |

**빠진 AC가 있으면 시나리오를 추가한다.** 반대로 **AC에 없는데 시나리오만 있는 것**도 표시한다. 둘 중 하나다.

- 이슈에 빠진 요구사항이다 → 이슈의 AC를 보강하자고 제안한다
- 범위를 넘은 것이다 → 시나리오에서 뺀다

이 대조가 없으면 "테스트는 다 통과하는데 이슈는 안 끝난" 상태가 생긴다.

### 7. 시나리오를 개발자에게 보여주고 승인받는다

```
[GATE] 시나리오를 승인할 때까지 다음 단계로 넘어가지 않는다
```

보여줄 때 함께 밝힐 것:

- **AC 커버리지** — "AC 5개 전부 커버, 시나리오 12개"
- **AC에 없는데 추가한 시나리오** — 있으면 이유와 함께
- **판단이 필요한 지점** — "이 경계값이 맞는지 확인 필요"

## 다음 단계로 넘길 때

시나리오가 승인되면 `/tdd-red {N}`으로 넘어간다. Red 단계는 이 파일의 시나리오를 **그대로** 테스트 이름으로 옮긴다.

그래서 시나리오 문장이 애매하면 Red에서 막힌다. "should work correctly"는 테스트 이름이 될 수 없다. **"should ... when ..."의 양쪽이 모두 구체적인지** 승인 전에 확인한다.

## 흔한 실수

- **시그니처 승인 없이 시나리오로 넘어가기.** 두 게이트는 각각 멈추라고 있는 것이다
- **PRD의 ADR을 안 읽고 시그니처 만들기.** 구조 결정이 이미 나 있는데 어긋나는 모양을 만들면 Green에서 충돌한다
- **경계 시나리오 누락.** 정상과 예외는 잘 나오는데 경계가 빈다. 파라미터마다 끝값을 물어보는 습관으로 막는다
- **시나리오에 구현 방법 쓰기.** "이렇게 구현한다"가 아니라 "이렇게 동작한다"를 쓴다
- **AC 대조 건너뛰기.** 이걸 빠뜨리면 이슈를 닫을 근거가 없어진다
