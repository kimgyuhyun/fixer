# TDD Red — 실패하는 테스트

승인된 시나리오를 테스트 코드로 옮기고, **실패를 눈으로 확인한다.**

```
docs/result/scenarios/issue-{N}.md  (시그니처 + 시나리오, 승인됨)
    ↓ /tdd-red {N}
테스트 파일 + 최소 stub  →  전부 실패 확인 🔴
    ↓ /tdd-green {N}
```

**사용법:** `/tdd-red 12` (GitHub 이슈 번호)

번호가 없으면 물어본다. 시나리오 파일이 없으면 `/test-scenarios {N}`을 먼저 하자고 안내한다.

---

## 왜 일부러 실패시키는가

**그 테스트가 진짜로 무언가를 검증하는지 확인하려고.**

구현이 없는데도 통과하는 테스트는 아무것도 보고 있지 않은 가짜다. 단언(assertion)을 잘못 썼거나, 비동기를 기다리지 않았거나, 아예 실행되지 않는 경우가 실제로 흔하다. 이런 테스트는 나중에 코드가 망가져도 초록불을 켠다.

**실패를 눈으로 봐야 그 테스트를 믿을 수 있다.** 이 단계의 산출물은 코드가 아니라 "빨간불을 확인했다"는 사실이다.

---

## 좋은 실패와 나쁜 실패

이 구분이 Red 단계의 핵심이다.

|              | 실패 메시지                              | 판정                                              |
| ------------ | ---------------------------------------- | ------------------------------------------------- |
| 🟢 좋은 실패 | `expected 1 to be 2` — **단언에서 실패** | 테스트가 실제로 동작을 검사하고 있다              |
| 🟢 좋은 실패 | `Error: not implemented` — stub이 던짐   | 함수까지 도달했다. 정상                           |
| 🔴 나쁜 실패 | `Cannot find module './auth.service'`    | 컴파일 단계에서 죽었다. 테스트가 실행조차 안 됐다 |
| 🔴 나쁜 실패 | `xxx is not a function`                  | import는 됐는데 대상이 없다                       |

**나쁜 실패는 Red가 아니다.** 파일이 없어서 나는 오류는 "테스트가 검증에 실패했다"가 아니라 "테스트를 시작도 못 했다"는 뜻이다.

그래서 stub이 필요하다.

---

## stub 규칙

**stub = 시그니처만 있고 본문이 없는 껍데기.** Red 단계에서 만드는 유일한 구현 파일이다.

```typescript
// apps/api/src/auth/auth.service.ts
export class AuthService {
  async verifyCode(email: string, code: string): Promise<VerifyResult> {
    throw new Error('not implemented');
  }
}
```

지킬 것:

- **시그니처는 `issue-{N}.md`에 승인된 것을 그대로** 옮긴다. 여기서 바꾸지 않는다
- 본문은 `throw new Error('not implemented')` 하나뿐이다
- 조건문·계산·DB 호출을 **한 줄도 쓰지 않는다.** 한 줄이라도 쓰면 그건 Green 단계다
- 타입·zod 스키마·enum은 stub에 포함해도 된다. 이것들이 없으면 테스트가 컴파일되지 않는다

`throw`를 쓰는 이유: 아무것도 안 하고 `undefined`를 반환하면 어떤 테스트는 우연히 통과할 수 있다. 던지면 반드시 실패한다.

---

## 실행 순서

### 1. 시나리오와 시그니처를 읽는다

`docs/result/scenarios/issue-{N}.md`

- **상단 시그니처** → stub과 테스트의 import를 여기서 가져온다
- **하단 시나리오** → 테스트 이름이 된다
- **AC 대조표** → 빠뜨린 시나리오가 없는지 마지막에 대조한다

파일이 없거나 승인 표시가 없으면 멈추고 `/test-scenarios {N}`을 먼저 하자고 안내한다.

### 2. 시나리오를 하나씩 테스트로 옮긴다

**시나리오 문장이 그대로 테스트 이름이 된다.**

```
시나리오: [경계] verifyCode — should reject when code is exactly 10 minutes old
```

```typescript
describe('verifyCode', () => {
  it('should reject when code is exactly 10 minutes old', async () => {
    // ...
  });
});
```

- `describe`는 **함수·컴포넌트 단위**로 묶는다
- 분류([정상]/[경계]/[예외])는 테스트 이름에 넣지 않는다. 파일 안에서의 순서로 드러난다
- 시나리오 문장을 임의로 고치지 않는다. 고쳐야 할 만큼 애매하면 시나리오를 먼저 고치자고 말한다

**한 테스트는 한 가지만 검사한다.** 단언이 여러 개면 실패했을 때 어느 줄에서 멈췄는지에 따라 뒤쪽 단언은 확인조차 안 된다.

### 3. 하나 쓸 때마다 즉시 실행해 실패를 확인한다

```bash
pnpm --filter @fixer/api test -- --run auth.service.test.ts
```

전부 쓰고 한 번에 돌리지 않는다. **하나씩 확인해야 어떤 테스트가 왜 실패하는지 알 수 있다.**

실패 메시지를 보고 위의 "좋은 실패 / 나쁜 실패" 표로 판정한다. 나쁜 실패면 stub을 손봐서 좋은 실패로 만든 뒤 다음으로 넘어간다.

### 4. 전체를 돌려 모두 실패하는 것을 확인한다

```bash
pnpm test
```

**하나라도 통과하면 그 테스트를 의심한다.** 구현이 없는데 통과했다는 뜻이므로 셋 중 하나다.

- 단언이 실제로는 아무것도 검사하지 않는다
- 비동기 함수를 `await` 없이 호출해서 단언이 실행되기 전에 테스트가 끝났다
- stub이 `throw` 대신 값을 반환하고 있다

### 5. 결과를 보고한다

- 작성한 테스트 수, 전부 실패 확인
- 만든 stub 파일 목록
- 시나리오 대비 누락 여부
- **나쁜 실패였다가 고친 것이 있으면** 무엇을 왜 고쳤는지

## 테스트 파일 컨벤션

**테스트는 대상 파일과 같은 디렉토리에 둔다.** 별도 `__tests__` 폴더를 만들지 않는다. 파일을 옮길 때 테스트가 따라오지 않는 일을 막기 위함이다.

| 대상                                   | 테스트 파일                                 |
| -------------------------------------- | ------------------------------------------- |
| `packages/shared/src/retention.ts`     | `packages/shared/src/retention.test.ts`     |
| `apps/api/src/auth/auth.service.ts`    | `apps/api/src/auth/auth.service.test.ts`    |
| `apps/web/src/components/TagInput.tsx` | `apps/web/src/components/TagInput.test.tsx` |

- 확장자: `.test.ts` / `.test.tsx`
- **Nest 기본값은 `.spec.ts`지만 이 저장소는 `.test.ts`로 통일한다.** 세 패키지에서 같은 규칙을 쓰는 편이 낫다

### 계층별 도구

| 계층                        | 도구                           | 비고                                |
| --------------------------- | ------------------------------ | ----------------------------------- |
| `packages/shared` 순수 함수 | Vitest                         | DB도 브라우저도 불필요. 가장 빠르다 |
| `apps/api` 서비스 로직      | Vitest                         | 의존성은 목(mock)으로               |
| `apps/api` DB가 필요한 것   | Vitest + Testcontainers        | 진짜 Postgres를 컨테이너로 띄운다   |
| `apps/web` 컴포넌트         | Vitest + React Testing Library | `jsdom` 환경 필요                   |

**도구가 아직 설치돼 있지 않으면 설치부터 하고 그 사실을 보고한다.** 첫 Red에서는 Vitest 설정 자체가 없을 수 있다. 설치와 설정 파일 추가는 Red 범위 안이다 — 테스트를 돌릴 수 없으면 실패를 확인할 방법이 없기 때문이다.

**DB가 필요한 시나리오는 Testcontainers를 쓴다.** `spec-fixed.md`에서 확정된 사항이며, H2 같은 경량 DB로 대체하지 않는다. 잠금·트랜잭션 동작이 DB마다 달라 진짜 Postgres에서 검증해야 의미가 있다.

---

## 제약

- **테스트 파일과 stub만 만든다.** 그 외 구현 파일을 수정하지 않는다
- 이미 있는 구현 코드는 **한 줄도 고치지 않는다.** 테스트를 통과시키려고 구현을 손대는 순간 Red가 아니다
- 시그니처를 바꾸지 않는다. 바꿔야 한다고 판단되면 **멈추고 말한다** — `issue-{N}.md`를 고치는 게 먼저다
- 테스트를 통과시키려 하지 않는다. **이 단계의 목표는 빨간불이다**

기존 테스트가 이 작업 때문에 깨지면 그것도 보고한다. 새 stub이 기존 코드와 충돌했다는 뜻이므로 시그니처 단계로 돌아가야 할 수 있다.

---

## 흔한 실수

- **stub 없이 테스트만 쓰기.** `Cannot find module`은 Red가 아니다
- **stub에 로직 넣기.** "이 정도는 자명하니까"가 Green의 시작이다. 참으면 Green에서 그 자명함이 틀렸다는 걸 발견할 때가 있다
- **전부 쓰고 한 번에 돌리기.** 어느 테스트가 왜 실패하는지 뒤엉킨다
- **통과한 테스트를 그냥 넘기기.** 구현이 없는데 통과했으면 그 테스트가 고장난 것이다
- **비동기를 `await` 없이 호출.** 단언이 실행되기 전에 테스트가 끝나 초록불이 켜진다
- **시나리오 문장을 임의로 다듬기.** 승인된 문장이므로 바꾸려면 되돌아가서 합의한다
