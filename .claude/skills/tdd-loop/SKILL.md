# TDD 루프 — 이슈 하나를 끝까지

```
/tdd-loop {N}
  0. 사전 점검 (브랜치·선행 이슈·환경)
  1. /test-scenarios {N}   시그니처 + 시나리오        [게이트 2개]
  2. /tdd-red {N}          실패 테스트 + stub
  3. /tdd-green {N}        최소 구현, 전체 통과
  4. @ac-verifier {N}      AC 충족 독립 검증
  5. /tdd-refactor {N}     구조 개선
  6. /security-review {N}  타입·보안 3분류          [게이트]
  7. /create-pr            검증 → push → PR          [게이트]
```

**사용법:** `/tdd-loop 12` (GitHub 이슈 번호)

번호가 없으면 물어본다.

---

## 이 스킬은 게이트를 만들지 않는다

**컨테이너는 순서만 보장한다.** 각 단계의 승인은 그 스킬 안에 이미 있고, 그것들이 그대로 동작한다. 컨테이너가 단계 사이에 "다음으로 갈까요?"를 **추가로 묻지 않는다.**

이유가 있다. 게이트가 두 겹이면 사용자는 같은 것을 두 번 승인하게 되고, **두 번째 승인은 반사적으로 누르게 된다.** 그러면 첫 번째 게이트의 무게까지 같이 가벼워진다. 게이트는 실제로 판단이 필요한 곳에만 있어야 값을 한다.

컨테이너가 하는 일은 셋뿐이다.

1. 시작 전 **환경이 준비됐는지** 확인
2. 단계 사이에 **진행 상황을 한 줄로** 출력
3. 실패하면 **어디서 멈췄는지** 명확히 알리고 중단

---

## 0. 사전 점검

**하나라도 걸리면 시작하지 않는다.** 3단계쯤에서 환경 문제로 막히면 그때까지 한 것을 되돌려야 한다.

### 이슈를 읽는다

```bash
gh issue view {N}
```

여기서 셋을 얻는다.

| 얻는 것       | 어디서                             | 쓰이는 곳             |
| ------------- | ---------------------------------- | --------------------- |
| **도메인**    | 라벨 (`auth-member`, `job-post` …) | 브랜치 이름, PRD 경로 |
| **선행 이슈** | 본문의 `**선행**` 필드             | 아래 선행 확인        |
| AC            | 본문 체크박스                      | 1단계와 4단계         |

`gh`가 PATH에 없으면 전체 경로로 부른다. 없으면 설치를 안내하고 중단한다.

### 선행 이슈가 끝났는지 본다

```bash
gh issue view {선행번호} --json state,number
```

**선행 이슈가 열려 있으면 알리고 판단을 받는다.** 예를 들어 #12는 #11·#28을 선행으로 두므로, 둘이 아직 안 끝났으면 작업이 중간에 막힌다.

두 가지 선택지를 준다.

- 선행 이슈를 먼저 끝낸다
- 선행 이슈 브랜치 위에서 이 이슈를 시작한다 (`CLAUDE.md` 브랜치 규칙)

### 커밋되지 않은 변경이 있으면 중단한다

```bash
git status --porcelain
```

작업 중인 파일이 남은 채로 브랜치를 만들면 그 변경이 딸려간다. **커밋하거나 정리한 뒤 다시 부르라고 안내한다.** 자동으로 커밋하거나 버리지 않는다.

### 브랜치를 준비한다

`CLAUDE.md`의 규칙을 따른다.

```
feat/{domain}/issue-{N}
예) feat/auth-member/issue-1
```

| 현재 상태                   | 처리                                                                        |
| --------------------------- | --------------------------------------------------------------------------- |
| 대상 브랜치가 **이미 있다** | **같은 이슈를 다시 도는 것**으로 본다. 이어서 할지 새로 시작할지 확인받는다 |
| `main`에 있다               | `main`에서 분기 (선행 이슈가 미머지면 그 브랜치에서)                        |
| 다른 이슈 브랜치에 있다     | 알리고 중단. 실수로 남의 작업 위에 쌓는 것을 막는다                         |

**"이어서 한다"를 고르면 재개 지점을 판단한다.** 아래 "중단된 곳부터 다시" 참고.

### 환경을 확인한다

| 확인                             | 왜                                                                                                                             |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **Docker Desktop이 켜져 있는가** | DB 통합 테스트가 Testcontainers를 쓴다. 꺼져 있으면 3·5단계에서 `Could not find a working container runtime strategy`로 멈춘다 |
| `pnpm`이 PATH에 있는가           | 없으면 `corepack pnpm`으로 대체                                                                                                |
| Playwright 설정이 있는가         | 없으면 7단계에서 E2E를 건너뛰게 된다. **미리 알린다**                                                                          |

```bash
docker info > /dev/null 2>&1 && echo "Docker OK" || echo "Docker 꺼짐"
```

Docker가 꺼져 있으면 켜라고 안내하고 중단한다. **켜지는 데 90초쯤 걸리므로** 3단계에서 발견하는 것보다 지금 발견하는 게 훨씬 싸다.

## 1~7. 단계 실행

각 단계를 **그 스킬을 그대로 호출해서** 진행한다. 컨테이너가 그 안의 절차를 흉내 내지 않는다 — 스킬이 바뀌면 컨테이너도 자동으로 따라가야 하기 때문이다.

단계 사이에는 한 줄만 출력한다.

```
[1/7] 시그니처 + 시나리오 도출  →  /test-scenarios 12
```

| #   | 호출                   | 산출물                               | 내부 게이트                   |
| --- | ---------------------- | ------------------------------------ | ----------------------------- |
| 1   | `/test-scenarios {N}`  | `docs/result/scenarios/issue-{N}.md` | 시그니처 승인, 시나리오 승인  |
| 2   | `/tdd-red {N}`         | 테스트 파일 + stub, 전부 빨간불      | —                             |
| 3   | `/tdd-green {N}`       | 구현, 전체 통과 + 커버리지           | — (5회 루프 실패 시 중단)     |
| 4   | `@ac-verifier {N}`     | AC별 ✅/⚠️/❌ 판정                   | — (갭이 있으면 보고)          |
| 5   | `/tdd-refactor {N}`    | 구조 개선                            | 대상 목록 승인                |
| 6   | `/security-review {N}` | 3분류 보고                           | 수정 항목 승인                |
| 7   | `/create-pr`           | PR                                   | 초안 승인 (push·PR 생성 포함) |

### 단계마다 커밋한다 — 끊겨도 안 날아가게

**마지막에 한 번만 커밋하지 마라.** 세 번이다.

| 단계 끝 | 커밋                                       |
| ------- | ------------------------------------------ |
| 1       | `docs: {제목}의 테스트 시나리오를 도출`    |
| 2       | `test: {제목}의 실패 테스트와 stub를 추가` |
| 3       | `feat: {제목}` (본문에 `closes #{N}`)      |

세션은 끊긴다. 사용량 초기화, 컨텍스트 한도, 창을 닫는 것 전부다. 마지막에 한 번만 커밋하면 50분째에 끊길 때 50분이 통째로 날아간다.

**Red를 이력에 남기는 값도 있다.** 테스트와 구현이 한 커밋에 섞이면 "구현 없이 정말 실패했는지"를 나중에 확인할 방법이 없다. 2단계 커밋이 그 증거다.

5·6단계의 수정은 각각 `refactor:`·`fix:`로 따로 커밋한다.

### 4단계에서 갭이 나오면

`@ac-verifier`가 ⚠️나 ❌를 내면 **5단계로 그냥 넘어가지 않는다.** AC가 안 채워진 채로 리팩토링·PR까지 가면 이슈를 닫을 근거가 없다.

사용자에게 보고하고 판단을 받는다.

- **갭을 메운다** → 2단계(`/tdd-red`)로 돌아가 빠진 시나리오를 테스트로 추가하고 3단계를 다시 돈다
- **범위 밖으로 인정한다** → 이유를 `issue-{N}.md`에 적고 진행한다

### 7단계에서 E2E가 없으면

`/create-pr`이 알아서 처리한다 — 설정이 없으면 PR 본문에 `E2E 미실행 (Playwright 미설정)`을 적고 진행한다. 컨테이너는 그 결정을 대신하지 않는다.

## 실패하면

**어디서 멈췄는지 명확히 출력하고 중단한다.** 다음 단계로 넘어가지 않는다.

```
❌ [3/7] /tdd-green 에서 중단

  실패: should invalidate the previous unconsumed code when a new one is issued
  원인: 5회 피드백 루프를 돌았으나 통과하지 못함
  판단: 시그니처의 "최신 행 하나만 유효" 규칙과 구현이 어긋남

  다음 중 하나가 필요합니다:
    - issue-1.md의 시그니처를 고친 뒤 2단계부터 다시
    - 시나리오 문장 자체를 재검토

  지금까지 완료: 1/7, 2/7
  브랜치: feat/auth-member/issue-1 (커밋 없음)
```

담을 것: **어느 단계**, **무엇이 실패**, **왜 그렇다고 보는지**, **무엇이 필요한지**, **어디까지 됐는지**.

마지막 줄이 중요하다. 다시 부를 때 **어디서부터 시작할지** 알려주기 때문이다.

---

## 중단된 곳부터 다시

세션이 끊기거나 실패로 멈춘 뒤 다시 부르면, 컨테이너가 **어디까지 됐는지 스스로 판단한다.**

| 신호                                        | 어디까지 됐나               |
| ------------------------------------------- | --------------------------- |
| `docs/result/scenarios/issue-{N}.md`가 없다 | 1단계 전                    |
| 있고 체크박스가 전부 `[ ]`                  | 1단계 완료, 2~3단계 중      |
| 체크박스가 일부 `[x]`                       | 3단계 진행 중 — 그 지점부터 |
| 전부 `[x]`이고 `pnpm test` 통과             | 3단계 완료, 4단계부터       |
| 커밋이 있고 PR이 없다                       | 7단계 전                    |

```bash
grep -c '^- \[x\] \[' docs/result/scenarios/issue-{N}.md
grep -c '^- \[ \] \[' docs/result/scenarios/issue-{N}.md
```

**판단한 재개 지점을 먼저 알리고 시작한다.** 틀렸으면 사용자가 바로잡을 수 있어야 한다.

---

## 제약

- **컨테이너가 게이트를 추가하지 않는다.** 각 스킬의 승인만으로 충분하다
- **각 스킬의 절차를 컨테이너가 흉내 내지 않는다.** 그 스킬을 호출한다
- 단계를 건너뛰지 않는다. 특히 **4단계(`@ac-verifier`)** — Green은 있는 테스트만 통과시키므로, 이걸 빼면 AC가 빈 채로 초록불이 된다
- 실패하면 **다음 단계로 넘어가지 않는다**
- 사전 점검에서 걸리면 **아무것도 만들지 않고** 중단한다
- 커밋되지 않은 변경을 자동으로 커밋하거나 버리지 않는다

---

## 언제 이걸 쓰고 언제 안 쓰나

| 상황                           | 권장                                             |
| ------------------------------ | ------------------------------------------------ |
| 이슈 하나를 처음부터 끝까지    | ✅ `/tdd-loop {N}`                               |
| 이미 Green까지 했고 리팩토링만 | ❌ `/tdd-refactor {N}`을 직접                    |
| 시나리오만 뽑아두고 싶다       | ❌ `/test-scenarios {N}`을 직접                  |
| 여러 이슈를 연달아             | ❌ 하나씩 돈다. 묶어 돌리면 실패 지점이 흐려진다 |

**루프는 편의지 필수가 아니다.** 단계를 따로 부르는 것이 더 나은 경우가 많다.

---

## 흔한 실수

- **컨테이너가 게이트를 추가하기.** 승인이 두 겹이 되면 둘 다 형식이 된다
- **사전 점검을 건너뛰고 시작.** Docker가 꺼진 채로 3단계까지 가면 그때까지 한 것이 애매해진다
- **선행 이슈 확인 누락.** 중간에 "선행 이슈의 코드가 없어서" 막힌다
- **4단계 갭을 무시하고 진행.** 이슈를 닫을 근거 없이 PR이 올라간다
- **실패했는데 다음 단계 시도.** 잘못된 것 위에 계속 쌓인다
- **`main`에서 시작.** 7단계에서 PR을 만들 수 없어 헛수고가 된다
