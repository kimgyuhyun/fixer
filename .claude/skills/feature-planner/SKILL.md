# Feature 기획 워크플로우

하나의 기능을 **아이디어 → 개발 가능한 이슈 단위**로 변환한다.

```
spec-original.md (초기 아이디어)
    ↓ 단계 1 — 요구사항 인터뷰
spec-fixed.md (확정된 요구사항)
    ↓ 단계 2 — PRD 작성 + 기술 결정(ADR)
prd.md (단일 기준 문서)
    ↓ 단계 3 — 이슈 분해
issues.md + GitHub Issues (실행 가능한 작업 단위)
```

---

## 이 워크플로우에서 코드는 나오지 않는다

**3단계까지는 전부 문서 작업이다.** 실제 구현은 이후 TDD 사이클(Red → Green → Refactor)에서 시작된다.

이걸 먼저 못 박는 이유가 있다. 기획 중에 "이 구조가 코드로는 이렇게 생겼겠네"라는 생각이 들면 손이 근질거려서 스캐폴딩을 만들고 싶어진다. 그러면 사용자는 자기가 시키지도 않은 코드를 리뷰해야 하고, 아직 확정되지 않은 ADR 때문에 그 코드를 다시 버리게 된다.

**코드를 쓰기 전에는 반드시 사용자에게 별도로 물어본다.** "구조를 정하려면 코드가 있어야 한다"는 판단이 들더라도, 그건 제안이지 실행 허가가 아니다.

예외: 문서에 넣는 **예시 스키마·코드 조각**은 괜찮다. 파일로 저장하지만 않으면 된다.

---

## 용어 표기 규칙

이 워크플로우의 산출물은 **기술 배경이 서로 다른 사람들이 함께 읽는다.** 팀에 백엔드 경험이 적은 사람이 있을 수 있고, 3개월 뒤의 본인도 그 라이브러리를 잊었을 수 있다.

**기술 용어가 문서에 처음 등장할 때는 `용어(한 줄 설명)` 형태로 쓴다.**

```
zod(런타임에 데이터 모양을 검사하고 TypeScript 타입까지 만들어주는 라이브러리)
Prisma(TypeScript에서 DB를 다루는 도구. 스키마 파일 하나로 테이블과 타입을 함께 만든다)
advisory lock(PostgreSQL이 제공하는 잠금. 여러 서버가 같은 작업을 동시에 하지 않게 막는다)
멱등성(같은 요청을 두 번 보내도 결과가 한 번 보낸 것과 같은 성질)
수직 슬라이싱(기능을 레이어가 아니라 "사용자가 볼 수 있는 동작" 단위로 자르는 것)
```

- 같은 문서 안에서 **두 번째부터는 그냥** 쓴다. 매번 붙이면 읽기 힘들다.
- 설명은 **한 줄**이다. 정확한 정의보다 "이게 대충 뭐 하는 물건인지" 감을 주는 게 목적이다.
- 팀이 이미 매일 쓰는 말(예: 로그인, 페이징)에는 붙이지 않는다. 판단이 서지 않으면 붙인다.
- 문서가 길면 하단에 **"이 문서에 나온 기술 용어"** 표를 두고 한 번에 모아준다.

이 규칙을 지키면 사용자가 문서를 읽다 말고 검색하러 나가지 않는다. 그게 목적이다.

## 단계 1: 요구사항 인터뷰

### 목적
초기 기능 정의서의 모호성을 제거하고, 엣지 케이스와 결정 사항을 확정한다.

### 입력
- 초기 기능 정의서 (`spec-original.md` 또는 그에 준하는 메모)
- 코드베이스 (기존 구조·패턴 참조)

### 하는 일

**AI가 인터뷰어가 된다.** 사용자에게 답을 요구하되, **추천안과 그 이유를 항상 함께** 제시한다. 사용자는 자기 도메인 전문가지 기술 선택 전문가가 아니다. "어떻게 할까요?"만 던지면 답할 수 없다.

다뤄야 할 영역:

1. 이 기능의 primary user는 누구인가?
2. 최소 동작 시나리오 3개는? (가장 기본적인 사용 흐름)
3. 데이터 저장 방식 — 기존 구조와의 관계는?
4. 경계 조건 — 최대값, 빈 값, 중복, 동시성은?
5. 에러 처리 — 실패 시 사용자에게 어떻게 표시하는가?
6. 기존 UI 패턴과의 일관성 — 어떤 컴포넌트를 재사용할 수 있는가?
7. 성능 제약 — 허용 응답 시간, 데이터 크기 제한은? 데이터 소멸 경계는?
8. 향후 확장 가능성 — 이 결정이 다음 기능에 영향을 주는가?
9. 유지보수성 — 이 결정을 나중에 되돌리려면 무엇을 뜯어야 하는가?

### 질문 묶는 법

원문은 "한 번에 하나씩"이지만, 서로 물려 있는 결정(예: DB 선택 ↔ ORM 선택)은 따로 물으면 답이 어긋난다. **주제별로 3~4문항씩 묶어** 라운드로 진행하고, 묶은 이유를 사용자에게 밝힌다.

### 원본 정의서와 어긋나는 것을 발견하면

그냥 따르지 말고 **표로 정리해 알린다.** 원문 그대로 구현하면 사고가 나는 경우가 실제로 있다.

| 원문 | 문제 | 대안 |
|---|---|---|
| "테스트는 H2로" | H2는 자바 전용 DB라 이 스택에서 연결 불가 | 실제 DB를 컨테이너로 띄우는 방식 |
| "비밀번호 수정 차단" | 그대로면 비번 분실 시 계정이 영구히 잠김 | 변경만 차단, 재설정은 허용 |

사용자가 원문을 고수하면 그 결정을 따르고, 그렇게 정해진 이유를 문서에 남긴다.

### Ubiquitous Language(용어 통일) 확정

- 인터뷰 과정에서 나온 용어를 고정한다
- 코드·문서·대화에서 같은 단어로 같은 것을 가리킨다
- **금지어 목록도 함께 만든다** — "이 단어 대신 저 단어를 쓴다"가 명시돼야 실제로 통일된다
- `spec-fixed.md`에 "용어 정의" 섹션으로 넣는다

### 산출물
`spec-fixed.md` — 확정 사양 + 용어 정의 + 원본 대비 변경 사항 + 미해결 항목

```
[GATE] 사용자가 spec-fixed.md를 읽고 확정할 때까지 대기
```

## 단계 2: PRD 작성 + 기술 결정(ADR)

ADR = Architecture Decision Record. **어떤 구조를 골랐고 왜 그랬는지, 그리고 무엇을 버렸는지**를 남기는 기록이다.

### 목적
"이 기능에 대해 궁금하면 여기만 보면 된다"는 단일 기준점을 만든다.

### spec-fixed와 PRD의 차이

헷갈리기 쉬우므로 분명히 한다.

| 문서 | 답하는 질문 | 예 |
|---|---|---|
| `spec-fixed.md` | **무엇을** 만드는가 (제품 규칙) | "필수항목이 바뀌면 버전이 오르고, 신청자는 재동의 대기가 된다" |
| `prd.md` | **어떤 구조**로, **왜** 그렇게 골랐는가 | "버전 이력을 스냅샷 테이블에 저장. diff 방식과 이벤트 소싱은 각각 이런 이유로 기각" |

### 2-1. PRD 뼈대 생성 (기술 결정은 TODO로 비워둠)

- **개요** — 기능의 목적과 범위
- **사용자 스토리** — "~로서, ~하고 싶다. 왜냐하면 ~"
- **기술 결정** — 여기서 ADR 작성 (지금은 TODO)
- **Out of Scope** — 이번에 하지 않을 것
- **용어 정의** — spec-fixed.md에서 동기화

기술 결정 칸에는 **결정할 항목과 "왜 3안 비교가 필요한가"를 함께** 적는다. 이걸 못 쓰는 항목은 애초에 3안이 필요 없는 항목이니 목록에서 뺀다. 형식적인 비교를 만들어내지 않기 위한 장치다.

### 2-2. 아키텍처 3안 제안 & 비교

최소 3가지 안을 제안하고 **아래 7가지 고정 기준**으로 비교한다.

| # | 기준 | 설명 |
|---|---|---|
| 1 | 데이터 구조 | 어떤 형태로 데이터를 저장/표현하는가 |
| 2 | API 레이어 변경지점 | 기존 API에서 무엇이 바뀌는가 |
| 3 | 상태관리 변경지점 | 프론트엔드에서 무엇을 들고 있어야 하는가 |
| 4 | 핵심 동작 | 이 결정이 좌우하는 가장 중요한 동작이 어떻게 구현되는가 |
| 5 | 컴포넌트 구조 | 어떤 컴포넌트가 추가/수정되는가 |
| 6 | 기존 패턴과의 일관성 | 코드베이스의 기존 관습과 얼마나 맞는가 |
| 7 | 테스트 용이성 | 단위 테스트, E2E 테스트 작성이 쉬운가 |

**기준 6은 실제 파일을 가리켜야 한다.** 추상적인 "일관성"은 판단에 도움이 안 된다. 비교표 앞에 "이 프로젝트의 기존 패턴" 표를 두고 파일 경로와 함께 명시한다.

**해당 없는 기준은 억지로 채우지 않는다.** 서버 전용 결정에서 3·5번은 "해당 없음"이 정직하다. 채워 넣으면 문서만 길어지고 판단이 흐려진다.

**추천안에는 반드시 "이 안을 골랐을 때 감수하는 것"을 붙인다.** 단점 없는 추천은 ADR이 아니라 광고다.

비교 결과를 표로 정리한 뒤 **사용자가 선택한다.**

```
[GATE] 사용자가 3안 중 하나를 선택할 때까지 대기
```

### 2-3. 선택한 안을 ADR 4요소로 작성

```markdown
### 기술 결정 제목

**Context** — 이 결정이 필요한 맥락. 무엇을 풀고 있는가.

**Decision** — 무엇을 선택했는가.

**Alternatives** — 거부한 안과 각각의 거부 이유. 이유 없는 거부 금지.

**Consequences** — 트레이드오프. 장점뿐 아니라 단점도 반드시 명시.
```

**Consequences에 "이 결정을 다시 여는 조건"을 함께 적는다.** 예: "공고 하나가 수십 번 수정되는 패턴이 관측되면 재검토한다." 이게 있어야 나중에 "그때는 맞았는데 지금은 틀렸다"를 판단할 수 있다.

**3안 비교 원본은 지우지 않고 별도 파일로 남긴다.** 3개월 뒤 "왜 저 안을 안 썼지?"를 물으면 비교표가 그대로 답한다.

### 2-4. Out of Scope 작성

"하지 않을 것"을 **구체적으로** 나열한다. 이게 AI에게 특히 중요한 이유: 명시하지 않으면 맥락을 확장 해석해 범위 초과 구현을 한다.

각 항목에 **이유를 붙인다.** "안 함"만 있으면 나중에 누군가 다시 제안한다.

### 산출물
`prd.md` (도메인이 여러 개면 도메인별로) + 3안 비교 원본

```
[GATE] 사용자가 Out of Scope을 읽고 확정할 때까지 대기
```

## 단계 3: 이슈 분해

### 목적
PRD를 실행 가능한 작업 단위로 변환한다. 각 이슈는 독립적으로 TDD 사이클을 돌릴 수 있어야 한다.

### 수직 슬라이싱 원칙

> **"이 이슈만 완료하면 사용자에게 보여줄 수 있는 동작이 있는가?"**

- **Yes** → 수직 슬라이스. TDD 사이클을 돌릴 수 있다.
- **No** → 다른 이슈와 합치거나 다시 나눈다.

**수평 슬라이싱(레이어별: API → 상태관리 → UI)은 금지.** 마지막 이슈까지 완료해야 동작이 나오므로 TDD 사이클을 이슈 단위로 돌릴 수 없다.

| 나쁨 (수평) | 좋음 (수직) |
|---|---|
| "User 테이블 스키마 작성" | "이메일 인증을 거쳐 가입한다" |
| "공고 API 엔드포인트 5개" | "공고를 등록하면 목록에 뜬다" |
| "목록 UI 컴포넌트" | "카테고리로 공고를 걸러 본다" |

스키마·API·화면은 **각 이슈 안에서 세로로 함께** 만든다.

**이 원칙의 이득이 나중에 나온다.** ADR이 바뀌어도 이슈 제목은 그대로다. 동작은 구조가 바뀌어도 같기 때문이다. 수평으로 잘랐다면 ADR 하나 바뀔 때마다 이슈를 다시 써야 한다.

### 예외를 허용하는 경우

화면이 없는 핵심 모듈(예: 금전 원장, 인증 코어)은 수직 슬라이스가 성립하지 않는다. 이때는 **"통합 테스트 결과가 데모다"**라고 명시하고 예외로 둔다. 예외는 드물어야 하고 이유를 적어야 한다.

셋업 작업(모노레포 구성, CI, 공통 컴포넌트)은 아예 **이슈가 아니다.** 별도 체크리스트로 처리한다.

### 이슈 크기
반나절~하루 안에 TDD 사이클 완료 가능한 것. 너무 크면 피드백 루프가 느려지고, 너무 작으면 PR 오버헤드가 초과한다. 하루를 넘는 것은 **왜 쪼갤 수 없는지** 적는다.

### 의존성 순서
앞 이슈의 결과가 다음 이슈의 입력이 되도록 배치한다. 역방향 개발 금지.

### Acceptance Criteria — Given-When-Then

```markdown
## Acceptance Criteria
- [ ] Given [사전 조건], When [행동], Then [기대 결과]
```

각 이슈에 반드시 AC를 포함한다. **AC는 다음 단계에서 테스트 시나리오의 씨앗이 된다.** 대충 쓰면 테스트를 못 쓴다.

AC가 그대로 테스트 코드로 옮겨질 만큼 구체적인지 확인한다. "잘 동작한다"가 아니라 "21건 중 2페이지에 1건이 보인다" 수준이어야 한다.

**ADR이 새로 보장해주는 것은 AC로 박아둔다.** 예를 들어 스냅샷 저장을 골랐다면 "과거 버전의 전문을 조회할 수 있다"가 AC로 들어간다. 다른 안이었으면 못 쓰는 AC다.

```
[GATE] 사용자가 이슈 목록을 읽고 수직 슬라이스 기준 충족을 확인할 때까지 대기
```

### GitHub 등록

**등록은 git push가 아니다.** 저장소에는 공간이 둘 있다.

- **Code 탭** — 파일. `git push`로 올라간다. `issues.md`는 여기 들어간다.
- **Issues 탭** — 할 일 카드. `gh issue create`로 만든다. 파일이 아니다.

md 파일을 push해도 Issues 탭은 비어 있다. 둘 다 하는 이유: md는 전체를 한 화면에서 훑는 계획서, Issues는 진행 상태 추적과 커밋 연결용이다.

**등록 전에 번호를 맞춘다.** GitHub은 이슈와 PR에 번호를 이어서 매긴다. 기존 이슈·PR이 0개면 `#1`부터 순서대로 붙는다. md 번호에 구멍이 있으면 어긋나므로 **md를 1..N 연속으로 먼저 정리한다.** 안 그러면 "선행 #12" 같은 참조가 전부 틀어진다.

```bash
gh issue create --title "이슈 제목" --body-file body.md --label "담당:이름,도메인"
```

라벨은 **담당자 + 도메인** 두 축이면 충분하다. 크기는 본문에 있으므로 라벨로 만들지 않는다.

39개를 한 번에 만들기 전에 **1개만 먼저 만들어 GitHub에서 어떻게 보이는지 확인**하는 것을 권한다. 마음에 안 들면 1개만 지우면 된다.

```
[GATE] 이슈 생성은 되돌리기 번거로운 외부 작업이다. 실행 전에 목록을 보여주고 확인받는다
```

## 규모가 클 때

도메인이 여러 개면 **한 번에 다 하지 말고 하나씩 게이트를 걸며** 진행한다. ADR 30건을 한 번에 주면 사용자가 읽고 결정할 수가 없다.

순서는 **의존 관계**를 따른다. 다른 도메인의 선택지를 좁히는 결정(보통 핵심 데이터 구조)을 먼저 한다.
