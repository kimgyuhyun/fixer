# TDD Refactor — 동작을 그대로 두고 구조만 고친다

```
테스트 전부 통과 🟢  (tdd-green 산출물)
    ↓ /tdd-refactor {N}
대상 식별 → [GATE] 승인 → 하나씩 고치고 매번 전체 테스트 🟢
    ↓
/security-review {N} → commit
```

**사용법:** `/tdd-refactor 12` (GitHub 이슈 번호)

번호가 없으면 물어본다.

---

## 시작 조건: 초록불

**테스트가 하나라도 실패 중이면 리팩토링을 시작하지 않는다.**

리팩토링은 "동작을 바꾸지 않는다"가 전제인데, 그걸 보장해주는 건 테스트뿐이다. 빨간불 상태에서 구조를 고치면 **원래 깨져 있던 것인지 방금 내가 깨뜨린 것인지 구분할 수 없다.**

실패가 있으면 멈추고 `/tdd-green {N}`을 먼저 끝내자고 안내한다.

---

## 테스트가 없는 코드는 건드리지 않는다

같은 이유다. 안전망이 없는 곳을 고치면 잘못돼도 아무도 알려주지 않는다.

리팩토링 대상 중에 테스트가 없는 파일이 있으면 **고치지 말고 보고한다.** "이 파일은 테스트가 없어 손대지 않았습니다"가 정직한 결과다.

---

## 실행 순서

### 1. `CLAUDE.md`를 읽는다

프로젝트 컨벤션(네이밍, 패턴, 스타일링, 기존 참조 파일)을 파악한다. 리팩토링의 기준이 개인 취향이 아니라 **이 저장소의 약속**이어야 한다.

`docs/result/prd/{도메인}.md`의 기술 결정(ADR)도 함께 본다. **ADR에 어긋나게 "개선"하면 그건 개악이다.**

### 2. 전체 통과를 먼저 확인한다

```bash
pnpm test
```

이 초록불이 리팩토링 내내 유지해야 할 기준선이다.

### 3. 리팩토링 대상 파일을 식별한다

**이번 이슈에서 바뀐 파일만** 본다. 이슈와 무관한 파일을 건드리면 리뷰가 어려워지고 회귀 위험만 커진다.

```bash
git diff main...HEAD --name-only 2>/dev/null \
  | grep -E '(apps|packages)/[^/]+/src/' \
  | grep -vE '\.test\.tsx?$' \
  | grep -v '/generated/'
```

**브랜치 상황에 따라 다르게 잡는다.**

| 상황                             | 명령                               |
| -------------------------------- | ---------------------------------- |
| 기능 브랜치에서 작업 중          | `git diff main...HEAD --name-only` |
| `main`에서 작업 중, 아직 커밋 전 | `git status --porcelain`           |
| `main`에서 작업 중, 이미 커밋함  | `git diff HEAD~1 --name-only`      |

제외 대상: 테스트 파일(`*.test.ts`/`*.test.tsx`), Prisma 생성물(`src/generated/`), 설정 파일.

**대상이 비면 멈추고 말한다.** 브랜치를 잘못 짚었을 가능성이 크다.

### 4. 점검 기준으로 검토한다

| 기준                | 무엇을 보는가                           | 신호                                                        |
| ------------------- | --------------------------------------- | ----------------------------------------------------------- |
| **중복 제거**       | 같은 로직이 반복되는가                  | 두 곳 이상에 같은 조건식·계산이 있다                        |
| **네이밍 명확성**   | 의도를 드러내는 이름인가                | `data`, `result`, `temp`, `handle` 같은 이름                |
| **단일 책임**       | 하나가 너무 많은 일을 하는가            | 함수 이름에 "그리고"가 들어간다                             |
| **불필요한 복잡도** | 매직 넘버, 과도한 중첩, 불필요한 추상화 | `if` 3중 이상, 설명 없는 숫자, 구현체가 하나뿐인 인터페이스 |
| **컨벤션 불일치**   | `CLAUDE.md`의 패턴과 어긋나는가         | 기존 참조 파일과 다른 방식                                  |

**중복은 세 번째부터 뽑는다.** 두 번 나왔다고 바로 공통화하면, 나중에 둘이 다른 방향으로 갈라질 때 억지로 묶인 코드가 남는다.

**추상화를 줄이는 것도 리팩토링이다.** 구현체가 하나뿐인 인터페이스, 한 번만 쓰이는 헬퍼는 인라인하는 편이 읽기 쉽다.

### 5. 대상 목록을 개발자에게 보고하고 승인받는다

```
[GATE] 무엇을 왜 고칠지 승인받을 때까지 코드를 고치지 않는다
```

각 항목에 담을 것:

- **파일·줄**
- **어떤 기준에 걸렸는가** (위 5가지 중)
- **어떻게 바꿀 것인가**
- **왜 지금인가** — 없으면 "안 고쳐도 된다"는 뜻이다

리팩토링은 안 해도 동작하는 작업이라, **근거 없이 손대면 순수한 위험**이다. 승인 게이트가 있는 이유가 이것이다.

### 6. 하나씩 고치고 매번 전체 테스트를 돌린다

```bash
pnpm test
```

- 한 번에 **변경 하나**. 여러 개를 묶으면 깨졌을 때 원인을 못 찾는다
- 통과하면 다음으로
- **깨지면 즉시 롤백한다.** 고쳐서 맞추려 들지 않는다

```bash
git checkout -- <파일>
```

깨졌다는 건 그 리팩토링이 동작을 바꿨다는 뜻이다. 되돌리고 다른 접근을 찾거나, 그 항목을 포기한다. **테스트를 고쳐서 맞추는 것은 절대 금지다** — 그 순간 안전망이 사라진다.

### 7. 전후 변경 요약을 낸다

| 항목           | 담을 것                                           |
| -------------- | ------------------------------------------------- |
| 고친 것        | 파일·줄, 적용한 기준, 전후 요약                   |
| 포기한 것      | 승인은 받았으나 테스트가 깨져 되돌린 것과 그 이유 |
| 손대지 않은 것 | 테스트가 없어 건드리지 않은 파일                  |
| 테스트         | 시작·종료 모두 전체 통과 확인                     |

## 제약

- **새 기능 추가 금지.** 동작이 하나라도 바뀌면 리팩토링이 아니다
- **테스트 파일 수정 금지.** 테스트가 안전망인데 안전망을 움직이면 의미가 없다
- **`src/` 밖 수정 금지.** 설정·문서·CI는 대상이 아니다
- **3단계에서 나온 파일 목록 밖은 건드리지 않는다.** "지나가다 보니 이것도" 가 리뷰를 어렵게 만든다
- 시그니처를 바꾸지 않는다. 공개 API가 바뀌면 그건 리팩토링이 아니라 설계 변경이다

## 이 저장소에서 특히 볼 것

| 항목                          | 확인                                                                                                                      |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| **Red 단계 `eslint-disable`** | `tdd-red`가 남긴 `require-await`/`no-unused-vars` 억제 주석. **구현이 들어갔으면 지운다.** 남아 있으면 실제 경고를 가린다 |
| 매직 넘버                     | 시간·횟수·금액은 `packages/shared`의 규칙 상수로 뽑는다. 테스트에서 주입 가능해진다                                       |
| zod 스키마 위치               | API와 웹이 함께 쓰는 타입은 `packages/shared`에. 한쪽에서만 쓰면 그 자리에                                                |
| CSS                           | 하드코딩된 hex·px가 있으면 `globals.css` 토큰으로. 새 토큰이 필요하면 그것도 보고 대상                                    |
| 에러 처리                     | 에러 코드가 문자열 리터럴로 흩어져 있으면 상수로 모은다                                                                   |

## 흔한 실수

- **빨간불에서 시작하기.** 안전망이 없으면 리팩토링이 아니라 도박이다
- **여러 개를 한 번에 고치기.** 깨졌을 때 어느 것이 원인인지 못 찾는다
- **테스트를 고쳐서 맞추기.** 가장 하기 쉽고 가장 나쁜 실수다
- **깨진 걸 고쳐서 살리려 하기.** 롤백이 먼저다. 그 접근이 틀린 것이다
- **범위 밖 파일 손대기.** "김에 이것도" 가 회귀의 시작이다
- **두 번 중복을 바로 공통화.** 세 번째까지 기다린다
- **근거 없는 개선.** "더 깔끔해서"는 근거가 아니다. 무엇이 어떻게 나아지는지 말할 수 있어야 한다
